# Agent 工作规矩 · 口径分析 / 影响评估（analysis）

> 适用：功能评审、差距分析、影响评估、口径变更论证、行业对标。
> 开工前先按 `memory/project_memory/README.md` §三 读完总入口，再进本目录。

## 一、证据原则（SKILL.md §3.2，本轮最大教训）

- **每个结论同时给「业务事实 + 代码证据（file:line）」**，并标注 【实码】/【行业事实】/【推断】 三分。
- 「不可达分支 / 死代码」必须用函数实际返回值范围或调用链证明，**不能凭注释或函数名推断**。
- **不信任历史文档的能力清单**。2026-11-18 本轮实码复核纠正了 5 处文档低估：
  「无宽放/评比」「无标准时间」「无置信度」「无证据帧」「无改善闭环骨架」全部不成立。
  → **动作**：任何「缺失」结论落笔前，先 `grep` / `Read` 至少 2 个落点文件。
- 文档与代码不一致时**以实际运行代码为准**，把偏差写进 `risk_log.md` 并更正文档。

## 二、本轮沉淀的分析范式（可复用）

1. **先盘「已有地基」，再谈「差距」**：列出每条行业能力对应的现有文件/规则集，
   判断是「零 DDL / 仅规则集发布 / 需迁移」哪一档，再排优先级。
   默认结论应是「复用现有地基的最小改动」，而非「新建大模块」。
2. **品类边界先判**：本系统属「问题发现品类」，拿「标准工时品类」的尺子量会误判。
   对标前先说清比较的是哪一层（采集/分解/浪费与 VA/产出/治理）。
3. **厂商数字一律标注来源性质**：提速 90%、年省数百万美元等多为厂商自述或内部建模，
   未经第三方审计，**不得作为验收基准或投资决策依据**。
4. **反证义务**：任何「差异化 / 落后 / 已具备」判断必须写「什么证据出现我改判」，
   且反证数据源要现成可查。
5. **哲学过滤是硬门**：每条建议先过「帮 IE 更快看出问题 → 留；帮管理层管住 IE → 砍」，
   明确列出「行业有但按哲学应砍/缓」的功能及理由。

## 三、口径变更的动作顺序（不可颠倒）

`business_rules.md` 先改 → 影响面清单（哪些模块/导出/测试依赖该口径）→ 用户确认 →
改代码 → `migrate.ts`（若涉实体）→ 真起 API → 双端回归 → `progress.md` 记实际数字。

**不可逆口径**（改 `hand` 语义、改 `std_time` 定义、对外 ±x% 声明、PMTS 覆盖 ST）
一律逐项确认 + ADR + 双轨并存，不覆盖历史。

## 四、收口

- 结论回写 `progress.md`（含证据路径与验证命令/实际输出）、`todo.md`（带 P1/P2 与推荐项）、
  `risk_log.md`（偏差与未决，每条带推荐项）。
- 向用户说明提交状态：分支、是否已提交、未提交文件数。
- 本类任务**只读**；不擅自改生产代码。
