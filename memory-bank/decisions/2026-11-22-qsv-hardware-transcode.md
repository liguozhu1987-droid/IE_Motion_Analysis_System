# 决策：上传转码改为硬件编码优先（QSV → NVENC → libx264）

## 目标

缩短视频上传转码等待，降低转码期间的 CPU 占用（转码是串行队列，会阻塞后续上传）。

## 可选方案

| 方案 | 实测（86s 1080p HEVC 源） | 结论 |
|---|---|---|
| 软件 libx264（原实现，硬编码） | 17.4s | 基线 |
| 仅硬件编码 h264_qsv | 11.9s | 编码卸载到 GPU，CPU 近零 |
| QSV 硬解 + 硬编 | 失败（本机核显无 HEVC 硬解） | 不可用 |

## 最终选择

上传转码复用派生路径已有的 `resolveEncoder`（探测顺序 QSV → NVENC → libx264），逐个候选尝试，失败 `invalidateEncoderCache()` 后回退下一个。

## 理由

1. 与派生路径（proxy/index）使用同一探测机制，避免两套逻辑分叉。
2. 硬件不可用时自动回退软件，不降低可用性。
3. 探测「通过」不等于全片稳定（历史坑：QSV 单帧探测过、全片第 24 帧失败）→ 必须保留运行时回退。

## 风险

- 硬件编码画质与 libx264 略有差异（`-global_quality 23` 对 `-crf 23`），分解看动作足够。
- 不同服务器 GPU 差异 → 探测失败即回退，无功能风险。

## 备注

硬件编码**不能**解决 HEVC 上传的等待问题（瓶颈在解码），根治方案是浏览器装 HEVC 扩展走原生直通。见 `facts/2026-11-22-video-playback-pipeline.md`。
