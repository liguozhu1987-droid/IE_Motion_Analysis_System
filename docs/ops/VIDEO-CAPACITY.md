# 视频派生容量参数（基于目标机实测）

> 目标机：6 核 Xeon E7-4850 v4 @2.10GHz / 32GB 内存 / 磁盘空闲 150GB；同机运行 NestJS + SQL Server + IIS ARR。
> 压测机：Intel i5-8265U（4 核 8 线程 @1.6GHz，8GB 内存），**明显弱于目标机**，因此耗时类结论偏保守。
> 压测脚本：`app/api/test/video-capacity-bench.cjs`（直接调用编译产物 `buildProxy/buildSprite/buildIndex`，与生产代码同路径）。

## 1. 参数—实测依据—调整场景

| 参数 | 推荐值 | 实测/推算依据 | 什么情况下调整 |
|---|---|---|---|
| `VIDEO_DERIVE_CONCURRENCY` | **2** | 8 线程机上：并发 1 峰值 96.2%/均值 46.1%；并发 2 峰值 100%/均值 **90.5%**（≈7.24 核）；并发 3 峰值 100%/均值 **99.3%**（≈7.95 核），且吞吐从 23.4s/条劣化到 28.6s/条。目标机 12 线程，2 并发约吃 8~9 线程，给 API/SQL/IIS 留 3~4 线程 | 若目标机实测 2 并发 CPU 均值 < 60%，可升 3；若 SQL Server 出现明显延迟或转码排队，降 1 |
| `VIDEO_DERIVE_TIMEOUT_MIN` | **30** | 单条 10 分钟 720p 代理 29.1s；并发 2 时整条视频（proxy+sprite+index）推算 30 分钟视频约 3 分钟，1080p 解码再乘 ~1.5 ≈ 4.5 分钟。30 分钟阈值留 6 倍以上余量；180 分钟上传上限的极端情况推算 17.5~26 分钟，仍在阈值内 | 若开放 4K/更高码率上传，或允许 `VIDEO_MAX_MIN` > 180，按「单任务实测最坏耗时 × 5」上调 |
| `VIDEO_RUNNING_STALE_MIN` | **35** | 必须大于单任务超时，否则健康长任务会被僵尸回收逻辑误判并重复领取。取 30 + 5 分钟缓冲 | 与 `VIDEO_DERIVE_TIMEOUT_MIN` 同步调整，始终保持 +5 分钟以上 |
| `VIDEO_DERIVED_MAX_GB` | **60（目标机）/ 90（2026-11-06 本机）** | 目标机：150G 空闲，系统/SQL/日志/临时留 20G、源视频留 50G，剩余 80G × 0.8 ≈ 64G → 60G。本机：D: 可用 202,271,416,320 字节 = 188.38GiB，`floor(188.38 × 0.5 ÷ 10) × 10 = 90G`（留一半给 OS/仓库/源视频/临时）。实测派生 25.6MB/分钟 ≈ 1.55GB/小时 → 60G ≈ 40 小时、90G ≈ 58 小时派生视频 | 源视频总量长期超预算时，先扩盘或依赖保留期策略，不要直接抬高该值（会挤压系统盘） |
| `VIDEO_DERIVED_DU_SEC` | **60** | 每轮 du 对 `derived/` 做递归 stat；派生目录文件数通常为「视频数 × 3」，60s 一轮成本可忽略 | 派生文件数 > 5 万时可调大到 300 |
| `VIDEO_ORPHAN_SWEEP` | **0（默认关）** | 共享存储瞬时不可见会批量误删派生行；P0-1 已提供巡检能力，默认不自动删 | 确认源视频目录为单机本地盘后，可设 1 |
| 编码器 | **libx264（用户决策 2026-11-06：不追加 GPU）** | 见下节实测：目标机无核显，QSV 不可用；NVENC 需独显且目标机未探测到 | 仅当未来明确追加 GPU 预算，并在目标机实跑 NVENC 1 帧验证可用后才考虑 |
| `VIDEO_MAX_MIN` / `VIDEO_MAX_MB` | 180 / 2048 | 业务允许的最长上传与单文件上限（非本次实测项，保持现状） | 由业务确认 |

## 2. 编码器实测结论

ffmpeg 6.1.1（gyan essentials build）编译清单包含 `libx264`、`h264_qsv`、`h264_nvenc`、`h264_amf`、`h264_mf`。

实跑 2 秒 1280×720 编码验证：

| 编码器 | 实跑结果 | 说明 |
|---|---|---|
| `libx264` | **成功（exit 0）** | 软件编码，目标机唯一确定可用 |
| `h264_qsv` | 成功（exit 0） | **仅压测机可用**（i5-8265U 带核显）；目标机 E7-4850 v4 无核显、平台不支持 QSV |
| `h264_nvenc` | **失败** | 压测机无 NVIDIA GPU；「编译进去」不等于「硬件可用」 |

**QSV 建议：目标机不启用。** 代码里的探测顺序是 QSV → NVENC → libx264，目标机上 QSV 会探测失败并自动回落 libx264，无需额外开关；不要为了 QSV 改服务器配置。若未来加装 NVIDIA 独显，需在目标机实跑 `h264_nvenc` 1 帧验证非空后才算「可用」。

## 3. 压测原始数据

条件：源视频 `testsrc2` 合成 1280×720@25fps、10 分钟、libx264 超快档 CRF23（466.21MB，合成耗时 34.6s）；派生固定 libx264（与目标机实际路径一致）。

| 场景 | 墙钟耗时 | CPU 峰值 | CPU 均值 | 等效占用核数（均值） | 产出 |
|---|---|---|---|---|---|
| 单条 proxy | 29.1s | 100% | 59.8% | 4.78 / 8 线程 | 256.34MB（854×480，15000 帧） |
| 单条 sprite | 15.4s | 86.2% | 50.8% | 4.06 / 8 线程 | 1.62MB（600 帧，10×60） |
| 单条 index | 0.8s | 18% | 18% | 1.44 / 8 线程 | ~0MB（JSON，15000 帧 CFR） |
| 并发 1 条 proxy | 25.4s | 96.2% | 46.1% | 3.68 / 8 线程 | 256.34MB |
| 并发 2 条 proxy | 46.7s（两条合计） | 100% | 90.5% | 7.24 / 8 线程 | 2×256.34MB |
| 并发 3 条 proxy | 85.8s（三条合计） | 100% | 99.3% | 7.95 / 8 线程 | 3×256.34MB |

换算（10 分钟视频）：

- 代理：256.34MB / 10min = **25.63MB/分钟 ≈ 1.54GB/小时**
- 精灵图：1.62MB / 10min = **0.162MB/分钟 ≈ 9.7MB/小时**
- 索引：可忽略（KB 级）
- 派生合计：约 **25.8MB/分钟 ≈ 1.55GB/小时**

> 注意：压测源是合成画面，编码复杂度与真实车间视频不完全等价；真实视频的代理体积通常在同类量级，但像素噪声高的画面可能偏大 10%~20%。该数据已比 SPEC 里「每 10 分钟 400–750MB」的早期估算（即 40–75MB/分钟）更低，说明早期估算偏保守。

## 4. 磁盘预算：150GB 分配逻辑

| 用途 | 预留 | 依据 |
|---|---|---|
| 系统 / SQL Server / 日志 / 临时 | 20GB | 同盘还要跑 SQL Server 数据与日志、Windows 临时目录、应用日志；不预留在磁盘写满时会直接伤数据库 |
| 源视频 `storage/videos/*.mp4` | 50GB | 假设单条 30 分钟 720p 源视频约 1.4GB（按实测 466MB/10min 推算），约可留 35 条。**真实相机码率可能高 3~10 倍，此假设需业务确认** |
| 派生 `storage/videos/derived/` | 80GB × 0.8 = **64GB → 取整 60GB** | 0.8 为安全系数；派生是可再生缓存（LRU 淘汰后按需重生成），不值得占满剩余空间 |

容量换算公式：

```
可承载派生视频小时数 = VIDEO_DERIVED_MAX_GB × 1024 / 25.8MB每分钟 / 60
```

三档示例（按实测 25.8MB/分钟）：

| 上限 | 可承载派生时长 | 约合 30 分钟视频条数 |
|---|---|---|
| 50GB | ≈ 33 小时 | ≈ 66 条 |
| 100GB | ≈ 66 小时 | ≈ 133 条 |
| 200GB | ≈ 132 小时 | ≈ 265 条 |

> `derived` 是工作集缓存，不是「所有历史视频都必须装下」：超过上限后 LRU 淘汰最久未访问的 proxy，源视频保留；用户再次打开该视频时按需重生成（目标机单条约 1~3 分钟）。

## 5. 触顶行为与未覆盖风险（如实说明）

- 派生目录超 `VIDEO_DERIVED_MAX_GB`（目标机 60 / 本机 90）：触发告警（日志必发 + 邮件通道，冷却 `ALERT_COOLDOWN_MIN`），随后按 `last_accessed_at` 升序淘汰 proxy（`status='evicted'`，删 `proxy.mp4`），**源视频永不触碰**；sprite/index 不淘汰。若 proxy 全淘汰后仍超限（sprite/index 就超了），会再告警并提示扩盘/人工清理。
- **源视频保留策略已落地（2026-11-06 用户决策）**：默认保留 10 天（`VIDEO_RETENTION_DAYS`），到期前 3 天（`VIDEO_RETENTION_NOTICE_DAYS`）邮件提醒上传者；上传者本人或管理员可选择「再保留 10 天」或「永久保留」；到期仍未选择则**硬删**源文件 + 派生文件/行（不做回收站），并写审计（来源 `auto_expired`/`manual`）。删除失败保留记录、写 error 日志 + 计数 + 告警邮件（1 小时节流），下一轮重试。详见 [DEPLOY-CONFIG.md §12](../deployment/DEPLOY-CONFIG.md)。
- **源视频仍没有总容量配额**：`VIDEO_MAX_MB=2048` 只限制单文件大小；选择「永久保留」的视频不参与到期清理。若长期保留量把磁盘吃满，仍会出现上传/转码写临时文件失败、派生任务写输出失败、SQL Server 数据/日志写入受影响。上传前剩余空间预检仍属 P0-2 待办；本次只落了保留期策略，**不能替代总容量配额**。
- **归档概念已作废**：早期「10 天只归档不删」草案被 2026-11-06 用户决策覆盖，代码中不存在 `archived_at`，不存在「归档/活跃」双状态；只保留 `retention_status`（auto/extended/permanent）与到期硬删一套口径。
