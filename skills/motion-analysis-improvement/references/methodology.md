# 动作分解增值分析方法论

本文件沉淀自 A12 QR 工位（28步、86.36秒）实战分析，适用于任何「视频动作分解表」样式的 Excel（列含 STEP / CT / 动作描述 / 移动部位）。分析必须遵循「先工时地基 → 动素增值非增值判定(VA/RNVA/NVA) → 按要素性质 5W2H 提问识别问题 → ECRS 拟定改善方案 → 适用性确认与收益计入」的顺序，全部产出用简体中文、表格优先、量化优先。

## 0. 输入表识别与读数

- 典型表头：STEP｜Start｜End｜CT｜Work Description｜Distance。
- B/C/D 列常为 Excel 时间序列值（按天的小数存储），**秒 = 原值 × 86400**；表内显示 `mm:ss.0`。
- 先确认唯一工作表、数据行数、合计行（通常最后一行 D 列为总 CT）；记录带问号的动作描述（疑点标记）。
- Distance 列给出肢体部位（大臂/小臂/手腕/低头仰头/迈1步/弯腰45度）与设备并行状态（如「遮阳帘运行」）——这是动作经济原则与人机联合作业分析的关键输入，不可丢弃。

## 1. 5W2H 提问（在增值分析之后、措施拟定之前）

**顺序纪律：先做动素三分类增值判定（VA/RNVA/NVA），再按要素性质做 5W2H 提问**——性质决定提问重点：

- **VA 动素**：重点问 How（如何缩短动作等级与距离、双手并用）。
- **RNVA 动素**：重点问 Why/Can（为何必要、能否取消、合并或系统替代）。
- **NVA 动素**：重点问 Why 存在与 How 消除（取放距离、等待、姿态）。

提问维度：What（做什么、是否必要）／Why（为何做、能否取消）／Who（谁做、能否换人或机器）／Where（在哪做、能否改位置）／When（何时做、能否换时序）／How（怎么做、能否简化）／How much（花费多少、量化）。

操作要求：疑点分组**必须覆盖全部动作要素**（可按工艺段落分组），每组标注「要素性质」；输出列固定为：疑点编号｜对应STEP｜要素性质｜5W2H提问｜核心问题(识别的问题)｜分析结论(倾向性答案)｜对应拟定措施编号。每条给出倾向性答案与对应措施编号。

必问的典型疑点：①起身/坐下等待；②重复扫码/重复取放同一工具；③手工撕背纸等精细动作；④清理脏污（带问号）；⑤长时检查是否全程有效、含多少人机闲余；⑥重复按完成按钮；⑦弯腰/低头等违反动作经济原则的姿态；⑧双手作业有无单手闲置。

## 2. 三分类增值判定（核心）

### 2.1 两套正交分类体系（不得混用，核心口径）

**主分类维度（增值性，汇总统计用）**——按精益价值判定，写入明细 F 列「类别归属」，只用三个枚举：

| 类别 | 代码 | 定义 | 改善原则（不在清单列中显示，口径页声明） |
|---|---|---|---|
| 增值 | **VA** | 直接作用于产品、改变装配连接/标识/防护状态，客户愿意付费 | **尽量缩短** |
| 必要非增值 | **RNVA** | 工艺/质量/设备条件下不可省但不直接创造客户价值（检验、追溯扫码、触发报工） | **尽量取消，无法取消则尽量缩短** |
| 非增值 | **NVA** | 对产品状态无贡献、纯消耗时间（取放、步行、弯腰、等待） | **尽量消除** |

**动素类别（18动素学口径，另列）**——按动素名称客观判定（生成器由「动素名称」公式自动推导），属动作方法层：

| 动素类别 | 包含动素 |
|---|---|
| 有效动素 | 伸手(TE)、握取(G)、移物(TL)、放置、定位(P)、松手(RL)、检查(I)、装配(A)、使用(U)、拆卸(DA) |
| 辅助动素 | 寻找(SH)、发现(F)、选择(ST)、思考(PN)、预置(PP) |
| 无效动素 | 持住(H)、可避免延迟(AD)、不可避免延迟(UD)、等待 |

**正交关系（核心）**：两套体系互不推导——有效动素不一定增值：检查(I)属有效动素但为必要非增值(RNVA)；伸手/握取/移物/放手属有效动素但多为非增值(NVA)；无效动素必为非增值，但非增值不一定是无效动素（如检查）。**增值比例、汇总统计一律以增值性为准；动素类别只用于动作方法分析，另列统计、不参与增值比例计算。**

历史反面案例（已纠正）：曾把精益增值三分法的枚举值直接命名为「有效动素/辅助动素/无效动素」，与动素学分组名称正面冲突，导致「伸手/握取/移物/放手/检查」这些第一类有效动素被错标为「无效/辅助动素」。正确做法即上表：两列分立——动素类别由公式按名称客观判定，增值性由分析判定（数据＋下拉枚举）。

### 2.2 双重标注规则（必须显式声明）

「动素增值分析」明细同时输出三列：D列「动素名称」保留 18 动素学原名（装配A、使用U、拆卸DA、检查I、伸手TE、握取G、移物TL、放手RL、定位P、迟延UD 等）；E列「动素类别」按动素名称公式客观判定（有效/辅助/无效动素）；F列「类别归属」为增值性主分类（增值VA/必要非增值RNVA/非增值NVA，数据填写＋下拉枚举）。三者正交、互不否定：名称与类别用于动作方法设计，增值性用于价值统计。

> 若不声明此口径、把检查(I)计入增值(VA)，增值比例会从约16%虚高到约60%，掩盖「人等机闲余」这个最大改善靶心——必须守住这条底线。

### 2.3 收益归集防重复

- 每一步的「预期缩短或消除秒数」为该步主线 CT 净压缩量；同一步被多措施改善时，**按主改善措施归属，不重复计列**。
- 无量化收益的步骤写数字 0，不留空、不写文字，避免 SUM 口径漂移。
- 措施总和（M类）必须与逐步缩短总和严格相等；在交付前交叉校验。

### 2.4 时序约束与可行性折算（防止「简单合并」虚增收益）

对「多次同样的操作」（典型为反复扫码、反复取放同一工具、多次按确认键），**先做时序可行性判定，再谈合并与工时节省**。机械地把 N 次操作合并成 1 次、把 N 次工时全额计入节省，是错误做法——扫码往往与设备启动、质量门禁、报工追溯绑定，必须按设计顺序执行。

四级判定矩阵：

| 级别 | 判定特征 | 改进方向 | 工时节省处理 |
|---|---|---|---|
| **A 时序锁定** | 动作是后续工序的触发信号或质量门禁（如扫框架码启动设备、检点确认后放行） | 保留动作，可优化扫码方式（固定式/免持），但不得取消 | **0**，不并入节省 |
| **B 系统可合并** | 同系统内的重复采集/记录，可由一次采集多写实现 | 提出「一次扫码双记录」建议，但须标注「需IT确认、保留必要时序」 | **按实现概率折算**（建议系数 0.5~0.8），不写全额 |
| **C 工具可替代** | 取放/瞄准类动作，可由固定式、悬挂式、支架式工具消除 | 固定式扫码器、枪座一体化、滑道呈现 | **按实际扫码点覆盖率折算**（建议系数 0.7~1.0）；覆盖不到的点位保留手持动作 |
| **D 纯浪费** | 无时序依赖的多余动作（等待、折返、重复放置、故延） | ECRS 直接取消 | 可全额消除 |

操作要求：
1. 每个「重复操作」逐条标注级别 A/B/C/D，写入措施的问题点与验证指标，例如「扫框架码为设备启动信号，时序锁定不可取消，保留于插线后、检查前」。
2. 折算后的节省 = 原工时 × 系数；系数须写明依据（IT 确认结论、扫码点布置方案、现场复核结果）。
3. 折算只影响「节省秒数」，不改变动作本身的分类与改善方向。
4. 验证指标必须包含「时序合规率=100%」，防止现场为追 CT 跳过必要扫码或检点。

反面案例（本技能须避免）：把 6 次取放枪 + 3 次扫码全额计为 5.0 秒节省并建议「合并为一次操作」——其中扫框架码是启动信号，两次报工扫码分属报工与追溯，时序与系统均不支持简单合并；正确做法是保留时序、按 B/C 级折算，节省约 2.85 秒。

### 2.5 设备/天窗自动运行与检测的提速上限（≤10%，防止「无措施硬砍设备时间」）

对**设备自动运行、天窗/遮阳帘自动运行，以及运行窗口内的检测/检查作业**，若无专项提速改造或可靠措施支撑，其工时改善幅度**上限为10%**。不得把设备/检测时间当作普通「人机闲余」随意压缩到20%~50%。

判定与处理：

| 情形 | 判定 | 节省处理 |
|---|---|---|
| 无专项措施，仅靠「检点定量化」「闲余显性化」等定性说法 | 自动运行/检测时间属工艺与设备固有节拍，不受控于作业员 | **压缩≤10%**（原时长×0.10），且须写明检点定量SOP等支撑措施 |
| 设备提速改造、非标设备行程/节拍优化、检测自动化等**专项措施且经实测验证** | 属可靠措施支撑 | 可按实测改善计入，但须附改造方案与3-5循环实测数据，经ECN验证 |
| 把检测/自动运行时间整体压缩到12-15s之类「经验值」 | 无可靠依据，属虚增 | **不予采信**，回退到10%封顶 |

操作要求：
1. 自动运行/检测步骤的改善手法中必须显式标注「≤10%封顶」及支撑措施，不得只写「压缩闲余」「转备料」。
2. 措施效果与验证指标写「检测时长压缩≤10%且有XX措施支撑；漏检率=0」，不得写无依据的大幅净节省。
3. 与之配套的「检点优先、备料在后」人机并行仍可实施，但**收益不通过压缩检点时长实现**；备料前移须在不干扰检点专注的前提下进行，其收益已在备料步骤就近化中单列，避免重复计量。
4. 验证指标须包含「检测时长压缩≤10%经3-5循环跟拍确认」与「漏检率=0」。

反面案例（本技能须避免）：遮阳帘运行检查24.82s，仅以「有效检查定量化至12-15s」为由缩减10s（约40%），无专项提速措施支撑——正确做法是10%封顶仅计2.48s，并把10s版本明确标注「无措施支撑不予采信」。

### 2.6 增值比例计算

```
增值比例(VA占比) = 增值(VA)总秒数 ÷ 单循环CT
必要非增值占比(RNVA) = 必要非增值(RNVA)总秒数 ÷ 单循环CT
非增值占比(NVA) = 非增值(NVA)总秒数 ÷ 单循环CT
```
所有占比在生成时由 Excel 公式计算（见「踩坑」章节），并同步写入缓存值供预览器显示；公式口径在「口径与说明」页写明。

### 2.7 适用性确认流程（拟定方案 → 用户选择 → 收益计入）

1. 措施清单中全部措施为**拟定方案**（措辞用「拟定，待现场验证/需IT确认」），不是最终确定方案。
2. 生成器在清单尾部自动追加两列用户输入区（黄色）：
   - **M列「是否适用」**：下拉 `适用 / 不适用`，默认留空（留空 = 尚未评审）；
   - **N列「预期缩短或消除(秒)」**：留空，仅当该行标记「适用」后由用户填写秒数（可参考 L 列「测算参考(秒)」）。
3. 汇总指标「措施确认情况」区块全部公式联动：已采纳条数 `=COUNTIF(M列,"适用")`；已确认节省合计 `=SUMIF(M列,"适用",N列)`；改善后CT（按已确认项）`= 现状CT - 已确认节省合计`。未确认任何措施时该区块等于现状。
4. L 列「测算参考(秒)」为分析侧测算值（只读），与动素明细「测算可优化(秒)」归属一致，生成器交叉校验两列合计相等，不等则拒绝生成。
5. 措施间收益可能重叠：汇总备注「不作简单相加」；重叠收益的措施写测算参考 0 并注明不重复计列。
6. **汇总联动纪律（最终口径 vs 参考口径）**：汇总中所有「改善后」类指标（已确认节省、改善后CT、UPH、CT降幅）只联动用户确认的数据——`SUMIF(M列="适用", N列)`；「动素增值分析」的测算可优化值与措施清单「测算参考」列属分析侧未确认测算，只能列示于汇总「分析测算参考（未经确认）」区块并显式标注，不得进入最终结果。未确认任何措施时，改善后CT等于现状CT（不预支测算值）。区块内附测算一致性校验公式：明细测算合计 vs 措施测算参考合计须一致，显示「不一致」说明数据被单侧修改。

## 3. 人机联合作业分析（最大收益来源）

画出人机时间轴：设备自动运行窗口内，人是否只做检查？检查为视听主导作业、双手空闲，则可「检点优先、备料在后」并行——窗口内预取后续物料（标签、塑料袋、胶带）、预撕背纸、预开袋口。
- **节省的是串行段排队备料的时间，不是删检查时间**。
- 必须配套检查 SOP 定量化（定检点 + 定时长 + 目视化检点表）与「检点全确认才解锁报工」的互锁，否则并行会牺牲检点专注度。
- 典型收益：本案例设备窗口 30.79 秒，有效检查 12-15 秒，净节省约 10 秒。

## 4. ECRS + 动作经济原则

### ECRS
- **E 取消**：可机器化/系统化的动素整体删除（撕背纸→预剥离打印机；重复扫码→一次扫码双记录；重复按钮→一次触发）。
- **C 合并**：双枪合一；两次扫码合并；检查+备料并行。
- **R 重排**：报工前移至设备窗口；打印时机前移；套袋与贴标顺序优化。
- **S 简化**：固定式扫码器；袋口撑开治具；高位磁吸放置座；定长预裁。

### 动作经济四方面（逐一识别）
1. **动作数量**：可取消/合并的动作清单，动作数从 N 步压至约 0.7N。
2. **动作距离**：大臂/迈步/起身/弯腰等长距离动作 → 就近化（滑道、定位盒、磁吸座、固定扫码器），动作等级从 4-5 级降到 2-3 级。
3. **轻松作业**：弯腰45度、低头仰头、起坐、精细捏撕 → 高位化、镜面辅助、坐立两用凳、机器替代。
4. **双手作业**：识别单手闲置环节；备料并行时双手分工写入标准作业；禁止「边检点边备料」（牺牲专注度）。

### 三维度归类
- **现场物品布置**：每个取用点的位置问题 → 定点定位/就近/悬挂/滑道/磁吸。
- **身体运用**：动作等级表（1手指→2手腕→3前臂→4上臂→5肩/躯干），指出可降级动作。
- **工具设备运用**：工具改进清单（固定扫码器、预剥离打印机、撑袋治具、裁纸机定位盒）与系统改造（一次扫码双记录）。

## 5. 防错（Poka-yoke）与标准化（作为措施清单中的运用方法，不单设工作表）

- 输出结构不含「防错设计」「落地与ECN」工作表；防错技术作为改善措施清单「运用方法」列的取值（防错(断根/保险/检测/警告/顺序)），防错措施以拟定方案行进入清单，接受同样的「是否适用」评审。
- 防错优先级：漏检放行 > 漏包装流转 > 扫码错误 > 效率类。
- 能做成断根/保险型（物理上不可能出错）优先；受成本限制的做检测/警告型，但**必须与「不允许报工」的系统互锁绑定**，否则等于没有防错。
- 典型装置：电子检点表+扫码互锁；双码匹配；套袋光电；封口色标传感器；「插头即钥匙」完成确认座；码制前缀校验+声光反馈；来料预封+防尘盖；双卷位+低量安灯。
- 检查标准化三件套：量化检点表（编号/位置图示/内容/判定标准/方法/合格样照+NG限度样照/确认方式）、限度样照板、NG实物样本。
- **硬约束（写入结论与前提）**：防错互锁必须与效率改善同步或先行发布；禁止「先提效后防错」。落地验证门槛（小批量≥50循环、漏检率=0、误报率≤5%）写入措施行验证指标，不再单独成页。

## 6. 输出清单字段契约与工作表结构

输出 5 个工作表：汇总指标 / 动素增值分析 / 5W2H提问 / 改善措施清单 / 口径与说明。

- **动素增值分析**（10列）：STEP｜动作描述｜CT(秒)｜动素名称｜动素类别(动素学，按名称公式客观判定)｜类别归属(增值性主分类：增值VA/必要非增值RNVA/非增值NVA，下拉枚举)｜具体改善手法｜对应措施编号｜测算可优化(秒)｜时间占比。「改善原则」不设列。
- **5W2H提问**（7列）：疑点编号｜对应STEP｜要素性质｜5W2H提问｜核心问题(识别的问题)｜分析结论(倾向性答案)｜对应拟定措施编号。
- **改善措施清单**（14列 = 数据12列 + 输入区2列）：编号｜对应5W2H｜对应STEP｜问题点(5W2H识别)｜拟定改善方案(ECRS)｜运用方法｜改善维度｜落地难度｜责任成员｜实施批次｜验证指标｜测算参考(秒)｜＋是否适用(下拉)｜＋预期缩短或消除(秒)(留空待填)。验证指标必须可量化（漏检率=0、拦截率=100%、CT±10% 等）。

## 7. Excel 公式联动与缓存值（必做，不可降级为静态值）

汇总表必须与明细及用户选择联动：改任一处（CT、三类归属、节省秒数、是否适用、措施批次），所有汇总自动更新。联动纪律：所有「改善后」类指标只联动评审确认数据（SUMIF 适用×N列），分析测算值仅入「分析测算参考（未经确认）」区块（详见 2.7 第 6 条）。做法是 **写 Excel 公式 + 注入缓存值**：

- 公式由 `scripts/build_checklist.py` 按真实坐标写入（COUNTIF/SUMIF/COUNTIFS/SUM/COUNTA/IF+OR 保护），坐标锚点在代码里集中定义、由锚点推导，不写死默认行号。
- 「增值性」代码列写公式由「三类归属」推导（IF 嵌套），改分类时代码自动跟随；「是否适用」联动用 SUMIF/COUNTIFS 只统计「适用」项。
- openpyxl 写入的公式没有缓存值，预览器与 `data_only=True` 会读到空白。生成后必须调用脚本内置的缓存注入：按 `(sheet名, 单元格坐标)` 把 Python 侧算好的值写回 xlsx 的 `<f>` 对应 `<v>` 节点，保留公式文本不变；**字符串结果必须设 `t="str"`**（如增值性代码列），数值结果须移除 `t` 属性，否则 Excel 报修复。
- 校验双重读取：`data_only=False` 应能看到 `=` 公式，`data_only=True` 应能看到数值；两者都通过方可交付。

### 环境踩坑

- 本机 `recalc.py` 报 `0xC000001D Illegal instruction`（editor_sdk 不可用）；bash 的 `python3` 无 openpyxl 且 pip 安装同样报错。可用解释器为 `C:/python/python.exe`（自带 openpyxl 3.1.2）。
- 因此**不能用 recalc.py**，改为上面的「公式 + 自注入缓存」方案，既保留联动又保证打开可见数值。
- Windows 控制台默认 cp1252/cp936，`print` 中文路径会 UnicodeEncodeError——脚本入口统一 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`。
- 同名覆盖：迭代重生成直接覆盖同一输出文件，避免留下带时间戳的多余副本；被 Excel/预览器独占锁定报 PermissionError 时，自动改用 `XXX_公式联动版.xlsx` 文件名交付并在回复中说明。
- AIGC 合规标识：交付前对成品执行 `aigc_label.py --platform WORKBUDDY`，须在最后一步（任何重序列化会覆盖标识）。
- 自检脚本不要 `import build` 之类的项目脚本——其顶层代码会重写交付文件。用 `json.load` 读数据文件即可。
