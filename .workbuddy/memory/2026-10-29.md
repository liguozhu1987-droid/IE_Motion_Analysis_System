### 启动/重启系统服务踩坑（约 15:30，运维）

- **现象**：多次「重新启动」后端/前端，新实例反复 failed（EADDRINUSE: 3001/5173 已占用），一度误判代码崩溃。
- **根因**：此前 Bash `run_in_background` 启动的后端(`node dist/src/main.js`)/前端(vite)，shell 壳被环境回收时 **node 子进程未一并杀掉，沦为孤儿**持续占端口；新实例即端口冲突失败。oKyprY 的 exit 1 是壳回收上报，非业务崩溃。
- **前端额外坑**：vite 实际装在 `app/node_modules`（非 `app/web/node_modules`）；`npm run dev` 在后台 shell 偶发 PATH 缺失 exit 127。改用 `cd app/web && node ../node_modules/vite/bin/vite.js` 直启最稳。
- **正确重启流程**：①PowerShell `Stop-Process` 杀监听 3001/5173 的 node 孤儿（先 `Get-NetTCPConnection -LocalPort 3001,5173 -State Listen` 取 OwningProcess，确认命令行是项目进程再杀）；②确认端口释放；③`cd app/api && node dist/src/main.js` + `cd app/web && node ../node_modules/vite/bin/vite.js`（均后台）；④探测 /health + 登录验证。
- **实证（15:32）**：clean 重建成功——后端 J6s7gd(PID 27892) / 前端 S7WqYS(PID 26840)，health 200 + 登录 200。那些 failed 通知是端口冲突噪音，非真实宕机。
- **重要判死准则（追加，22:15 复核）**：`run_in_background` 的后台 bash 壳被环境回收时**几乎总上报 exit 127/1**，但里面的 node 服务**常常继续存活**（或环境把它重新挂到新壳）。因此：**「任务 failed」≠「服务宕机」——永远用 `/health` 探测 + 登录验证判真实状态，不要看后台任务状态**。本次 J6s7gd 报 failed exit 127，但 3001 上的 node 后端(PID 10316，创建 22:12:57，父 bash 仍存活)实测 health 200 + 登录 200，确证是壳回收噪音。真正需处理的情况只有两种：①端口被旧孤儿占住导致新实例 EADDRINUSE；②日志出现 Nest 未捕获异常使 node 真退出（届时端口会空、/health 不通）。
