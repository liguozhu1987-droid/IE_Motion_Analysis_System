## v3.15 分解工作台单屏化整改（用户 3 项反馈：切换太累 / 视频太小黑边太宽 / 竖向堆叠）

### 做了什么
- **取消二切一**：删掉「属性检查器 ↔ 时间线/清单」模式条与 `panelOpen` 状态。检查器常驻右列（`overflow-y:auto` 内部滚动），时间线改成通栏条（`.wb-tlstrip`，可收起为 36px 单行）——填属性和拖边界同屏，零切换。
- **视频按画面比例定宽**（消黑边的根因解法）：不是"让视频在容器里 contain"（容器 2.66:1 时必然左右黑边），而是**让舞台宽度等于画面宽度**。`--wb-stage-w = (主区实测高 − 控制栏/边框) × videoAr`，`useLayoutEffect` + ResizeObserver 观察 main/stage/screen 三方，`Math.min(needW, mainW-344-12)` 兜底检查器最小宽。1366 实测画面 676×380 = 1.779（16:9）精确贴合。
- **竖向压缩**：`shell-main.wb-route` 定高 `calc(100vh-48px)` + `overflow:hidden`；顶栏 38px（h1 与 meta 用 flex baseline 并排，省 14px）；视频控制栏把传输条与记录条合并成一条恒定 41px；时间线条 145px（刻度 16 + 3 轨×28）；交付条 36px；`main.container-wide` padding 6/10；`.wb` gap 6。
- 空态改为铺满画面的虚线作业面（图标 + 主文案 + 说明 + "点击选择文件"胶囊），不再是一大片黑。

### 关键坑（跨会话有效）
1. **`useLayoutEffect` 依赖必须含 `loaded`**：工作台加载态提前 return，首帧 `mainRef/screenRef` 全空 → 直接 return 后依赖不变就再也不会跑，舞台宽卡在错误值（660px）。表现为"公式对、结果错"。
2. **外壳必须"定高"不能"min-height"**：`.shell{min-height:calc(100vh-48px)}` 时 `.wb` 按内容自然高度铺开 → 1600 屏恰好装下看不出来，1366 屏整页溢出 78px、交付条被推到屏外。改成 `height` + `overflow:hidden` 后 flex 才真正分配。
3. **恒定高度是自适应的前提**：控制栏若允许 `flex-wrap`，舞台宽变→换行→高度变→再算宽度，来回抖动。改 `nowrap` + 固定 height:41，非画面高度成为常量，公式一次收敛。
4. **横向滚动条是浮层**：`::-webkit-scrollbar{height:8px}` 时 sh==ch（不报纵向溢出）但滚动条压在最后一条轨道上；给 `.wb-tl .timeline` 补 `padding-bottom:9px`。
5. 窄舞台用 **`@container (max-width:720px)`**（宿主 `.wb-stage{container-type:inline-size}`）收起 −1s/+1s/↑/↓ 与 fps 徽标，控制栏 1366 下 scrollW==clientW 不裁切。

### 登录问题排查（admin 无法登录）
- 现象：admin/123456 登录失败。DB 实况 `t_user`：status=locked、failed_count=5、locked_until 未到 → **不是密码错，是连错 5 次触发锁定**（LOGIN_MAX_FAIL=5 / LOGIN_LOCK_MIN=15，见 src/core/config/configuration.ts）。
- 处置：`UPDATE t_user SET status='active', failed_count=0, locked_until=NULL, must_change_pwd=0 WHERE username='admin'` → 再 POST /api/auth/login 返回 200。密码哈希仍对应 123456（bcrypt.compareSync 验证过）。
- 遗留设计坑（待决策）：①users.service.update 设 status='active' 时**不清 locked_until**，后台点"启用"仍登不上；②status 白名单只有 active|disabled，锁定的用户无法在界面里标回；③唯一管理员被锁 = 只能进 DB 捞。建议加"解锁"动作（清 failed_count+locked_until）并写审计。

### 登录问题二次排查（同日下午）
- 现象：用户再次反馈 admin/123456 登录不了。
- 诊断流程：①DB 查 `t_user`：admin 状态 active、failed_count=0、locked_until=null、must_change_pwd=0，**账号数据正常**；②bcrypt.compareSync('123456', hash)=**true**，**密码正确**；③`curl POST /api/auth/login` 返回 **HTTP 000（连接拒绝）** + 端口检查 3001 无监听 → **根因：后端 API（NestJS, 3001）当时未运行**，前端 `/api` 代理打到 3001 连不上。
- 处置：`cd app/api && node dist/src/main.js` 后台拉起 API → 再次 POST 登录返回 **HTTP 200 + token**，登录恢复。
- 经验：**登录不通先分两步查——①账号状态（DB）；②API 是否在跑（3001 监听）**。账号正常却连不上，多半是 API 进程没起（不是密码/锁定）。
