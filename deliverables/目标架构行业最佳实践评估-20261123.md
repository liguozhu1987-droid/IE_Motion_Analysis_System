# 目标架构行业最佳实践评估（Deep Research）

> 日期：2026-11-23　方式：5 路并行检索 → 25 个来源 → 104 条断言 → 25 条进入 3 票对抗校验（13 确认 / 12 推翻）→ 综合
> 评估对象：本项目的目标架构六要点（要素快照 SSOT、单一纯函数内核、统一 Opportunity + ScoringService、唯一 ImprovementWriter、compare_token、经验回流 + HITL）
> 结论性质：**架构层判断**，未审计实现代码。

---

## 0. 结论

**部分符合行业最佳实践，不是全面符合。**

- **符合的部分（正确性最关键处）**
  - 确定性规则内核置于原始 CV/LLM 输出之上，与作业测量标准 MTM 的立场一致：纯视频只得到实测时间，必须叠加方法层才能得到可追溯的标准时间。
  - Human-in-the-loop 采纳/否决 + 结构化反馈持久化，是生产级 ML / 制造 LLM 的通行做法。
  - 用确定性 `ScoringService` 而不是 LLM 打分，规避了 LLM-as-a-Judge 已量化的自我偏好偏差——这是本架构的明确优点。
- **未被证据确立为“公认最佳实践”的部分**
  - 「要素快照 = 单一事实源」「只算一次、其他模块只读」在方向上常见，但本次用来背书的厂商权威（Databricks medallion-as-SSOT、Microsoft CQRS 读模型零逻辑）在对抗校验中 **0-3 被推翻**。存活的原文只是「medallion 是推荐做法而非强制要求」。
  - 因此 SSOT + 单内核应作为**可辩护的工程选择**保留，靠自身理由（可追溯、可复算、防口径分裂）成立，不要再引用这些厂商模式作为“行业标准”背书。
- **明确分歧**
  - 工业视频参考架构（NVIDIA VSS）普遍把实时特征抽取与下游行为分析拆成独立服务、经消息代理（Kafka/Redis Streams/MQTT）解耦；本项目是单体进程内纯函数内核。规模增大时这是具体分歧点（2-1 分裂票，中等置信度）。
- **最大缺口**
  - 六点架构**没有描述 LLM 评测体系**。Anthropic 指引要求 CI 回归 eval + 分层评估；HITL 反馈只是反馈层，不构成评估 harness（高置信度，3-0×2）。
- **最值得调整的三点**
  1. 为规则与 LLM 机会生产者增加自动化 eval harness；
  2. 为「经验回流注入提示词」加偏差护栏（衰减/上限/漂移监控/留出集）；
  3. 规模扩大时，把分析从单体内核改为事件驱动解耦（不是现在）。

## 3. 六点架构逐条判定

| 架构点 | 判定 | 理由 / 调整 |
|---|---|---|
| 1. Element Store + SnapshotService 作为 SSOT | **可辩护，但非权威最佳实践** | 建议把快照定义为不可变、显式 `(task, version, source)` 的事实；文档中用它自身的目标（可追溯、防口径分裂）论证，而不是引用 CQRS/medallion |
| 2. 单一纯函数分析内核 | **符合领域最佳实践方向** | MTM 支持“方法层叠加在观测层之上”；保持纯函数、规则注入、可复算 |
| 3. 统一 Opportunity + ScoringService | **方向正确，且规避 LLM 评分偏差** | 当前代码仍是三套评分公式（`suggestions/engine`、`ai-suggest/calculator`、`ai-waste/scoreIssues`）；目标架构的统一是实质改进 |
| 4. 唯一 ImprovementWriter | **良好工程实践，但无直接外部权威** | 保留；它带来审计与一致写入的收益，属于“可辩护选择”而非“行业强制” |
| 5. compare_token 保证上下文一致 | **合理** | 未被本次检索直接覆盖；但“解读对象与展示对象严格一致”是可靠工程约束，保留 |
| 6. 经验回流 + HITL | **HITL 符合；回流闭环需要护栏** | 现有实现只取 Top-5 否决模式、权重封顶 5；无时间衰减、无漂移监控、无留出集 |

## 4. 最值得调整的三点（含代码落点）

### 4.1 增加自动化 eval harness（最高优先级）

**为什么**：六点架构没有任何评测体系；HITL 反馈不能替代 eval（高置信度 3-0×2）。

**落地建议**

1. **黄金样本集**：按工位/任务标注少量真值（浪费点、浪费类型、建议是否可采纳）。项目已有前置项：AI 自动分解要求 ≥20 段人工标注真值（`test:eval` 目前 SKIPPED(78)，不得用 AI 候选伪造基线）。
2. **CI 分层 eval**（不依赖真实 LLM 网络）：
   - 规则内核：固定要素输入 → 断言 CT / VA-RNVA-NVA / 浪费集合与规则版本；
   - 校验器：固定 LLM 原始输出 → 断言 R1-R3 / W1-W3 的 drop / flag 结果；
   - 评分：固定机会条目 → 断言 `est_save_s / priority / annual_yuan`（含未配置参数时 null）；
   - 提示词回归：断言提示词中出现的 `waste_type` 全部 ⊆ 动态白名单（可直接捕获当前「等待延迟 / 返工重做」不匹配问题）。
3. **线上质量指标**：建议采纳率、否决率与原因分布、校验剔除率、人工编辑距离、同工位重复生成率。
4. **触发时机**：每次提示词/模型/规则版本变更都跑；与现有 `npm run test:gate` 同级。
5. **归属**：指定 eval 的 owner（IE + 开发各一人），否则会退化为一次性脚本。

### 4.2 为经验回流加偏差护栏

**现状（代码事实）**：`ai-suggest.service.ts` 的 `topNegativeExamples` 只取权重前 5，`aggregateFeedback` 权重上限 5（`Math.min(5, weight+0.5)`），无时间衰减、无漂移监控、无留出集。

**建议**

- **衰减**：按 `last_reject_at` 做时间衰减，避免陈旧否决长期支配提示词。
- **上限与分层**：按 waste_type 限制注入条数，避免某一类否决淹没其他类。
- **留出集**：保留一部分否决原因不注入，用于检验“回流是否真的降低同类低质建议”。
- **漂移监控**：按周统计各类建议的采纳/否决率；显著变化时告警并允许一键停用回流。
- **不要把 HITL 当唯一质量信号**：它受选择偏差与用户熟练度影响；与 4.1 的 eval 组合使用。
- **若未来引入 LLM 评审**：生成与评估模型分离，并先做偏差标定。

### 4.3 规模触发时再事件驱动解耦（不要现在做）

**触发条件（建议写进架构决策记录）**：

- 并发视频分析流 > 单进程可承受（例如 > 10 路同时分析）；
- 分析请求 p95 延迟影响交互；
- 需要多实例部署或独立扩缩容分析节点；
- 需要跨工位/跨产线批量重算。

**届时做法**：保留快照存储为事实源，把“分析内核调用”与“LLM 机会生产”抽成队列消费者，经消息代理解耦；先把接口契约（`SnapshotRef → AnalysisResult → Opportunity`）稳定下来，再拆进程。当前单体 + 纯函数内核在内部、单厂、按工位分析的规模下是合理选择。

## 5. 必须带上的限制（caveats）

1. **证据强度不均**：最强厂商背书被 0-3 推翻；存活表述仅“推荐而非强制”。
2. **来源性质**：多条来自厂商参考架构/自述（NVIDIA VSS、MTM 协会、AWS 博客），不是独立基准或法定标准；MTM Association 是私人协会，非 ISO。
3. **分裂票**：NVIDIA 事件驱动、HITL 两条均为 2-1，中等置信度。
4. **原文核实受阻**：arxiv / AWS / ScienceDirect 全文在验证时被网络封锁，部分引用为轻度改写/外推。
5. **时效性**：LLM eval 与 LLM-as-judge 偏差是快速演进领域（2024–2026），具体数值会过时。
6. **范围**：仅依据六点架构表述与 13 条核验声明，未审计实现代码。
