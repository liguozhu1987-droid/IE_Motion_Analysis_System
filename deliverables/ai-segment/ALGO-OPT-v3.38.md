# AI 自动动作分解 · 算法优化与根因分析（v3.38b）

- 版本：v3.38b（在 v3.37 双检测器基础上优化切分与分类）
- 触发问题（用户）：
  1. 「为何输出的动作时长大量固定为 1.1 秒？」
  2. 「为何缺少动作类型判定？」
  3. 「请结合真实工作场景复杂性，参考行业最佳实践，给出可落地优化方案与判定依据」
- 测试样本：`SH-FA9-A12-PA10-1.mp4`（上海 SHFA9 / PA10 工位实拍，391.8s，1920×1080，HEVC，固定机位，单人，双手戴手套）
- 结论先行：**「固定 1.1 秒」不成立（数据证伪），但「在微停顿处过切」成立；「缺少类型判定」完全成立（代码实证）。两者均已修复并有全片实测数据。**

---

## 一、问题核实：先看数据，再谈原因

### 1.1 「大量固定 1.1 秒」——半成立

v3.37 全片 183 段时长直方图（0.1s 桶）：

```
0.4s  3 ███
0.5s  6 ██████
...
1.0s 12 ████████████
1.1s 10 ██████████
1.2s 11 ███████████
1.3s 14 ██████████████   ← 最大单桶
1.4s 13 █████████████
...
6.1s  1 █
```

- p10 / p50 / p90 = **1.0 / 1.7 / 3.9s**，变异系数 0.58 —— 时长**连续分布**，不存在按固定 1.1s 定时切分（代码里也没有任何定时器逻辑，切点全部来自能量曲线的静止区间）。
- 但观感有真实依据：**51.9% 的段落在 1.0–1.9s 区间**，且相邻段时长差 ≤0.3s 的比例达 60.7% —— 看起来「整齐」。

**过切的实锤**：对同一视频的运动能量曲线重放「连续非静止区间」（即真实运动爆发），只有 **56 个、中位 0.8s，其中 33.9% 是 <0.3s 微爆发**；而产品输出 183 段。算法把每次 ≥200ms 的微停顿都当成了止点，把 56 个真实动作节奏切成了 183 段。

**为什么微停顿不是动素边界**：真实装配中「伸手 → 握取」本是一个拿取要素，中间的调整握姿/取向/犹豫只有 200–400ms；换手、对位犹豫同理。`MICRO_STILL_POINTS = 2`（200ms 即切）把这些全部当边界，切出的段自然集中在 1–2s。

### 1.2 「缺少动作类型判定」——完全成立

代码实证（v3.37 `motion.ts` / `segmentation.ts`）：每条候选硬编码 `type: '其他'`；页面层又硬编码一次（`AiSegmentPage.tsx` 里 `type: '其他'`，把算法结果覆盖掉）。这是 v3.33 一期裁权的设计（「切分先行、分类依赖精度」），但代价是每条候选都要人工选类型，省下的时间又还回去。

更深一层：**帧差法只保留「能量」，丢弃了空间语义**（质心轨迹、方向、位移），想分类也没有输入特征。

## 二、行业最佳实践参照（调研结论）

| 实践 | 做法 | 对本项目的启示 |
|---|---|---|
| Retrocausal Kaizen Copilot（学术，2024） | 视频 → 自动生成 MODAPTS/MTM 码 → AI 编码 + 工程师确认 | AI 提议、人审终裁；分类挂在既有 PMTS 标准上，**不发明新词表** |
| Coats GSD RealMotion（工业，2025） | AI 检出 GSD 码，工程师验证后才生效；45min 人工实测 → 15min | 先证后上；AI 输出必须可解释、可核对 |
| IndustryASM / 装配动作分割研究 | 动作分类体系分四类 taxonomy，按「是否接触物体 / 是否位移」分层 | 分类要**按可观测特征定义**，不按主观语义 |
| 骨骼图网络时序动作分割（TAS） | MoF（Motion of Frame）指标 74–93% | 学术界用骨骼/关键点；产线视频无骨架时帧差是现实替代 |

**共同模式**：① AI 只提议，人审终裁；② 分类体系挂在既有标准（MODAPTS/GSD）上；③ 分类必须可解释（给出判据）；④ 先验证再上线。

本项目完全对应：库里已有公司动作标准库 `motion_standard` MS1.1（拿取/放置/装配/操作/检查等 28 个类型，每个带 `desc`/起止点/`format` 描述格式/VA 判定），**分类直接挂它，不造新词表**。

## 三、优化方案（四项，全部新增、零改既有）

### 3.1 分级止点（消除过切）

```
静止区间时长 → 分级
  ≥ 500ms（LONG_STILL_POINTS=5）  → 确定边界
  200–500ms（MICRO_STILL_POINTS=2）→ 合并候选（先切开，由合并回路决定去留）
  < 200ms                        → 忽略（噪声）
```

### 3.2 合并回路（把微停顿切开的段还原）

v3.38 首版判据 `bothShort`（两段都 <1.2s 才并）**空转**——本视频中位段长 1.7s、51.9% 段落在 1.0–1.9s，条件永不成立（183→178 只并掉 5 条）。v3.38b 修正为按「合并后仍是合理单动作」判断：

- ① 同主导侧（B 与谁都能并，L/R 必须同侧 —— 左手拿完 ≠ 右手装）
- ② 合并后 ≤ 4000ms（比 MAX_SEG_MS=6000 更紧，宁少并勿过度）
- ③ 至少一侧有真实运动事件（两侧皆死 = 两段等待，不该并成一个动作）

### 3.3 运动学分类（帧差法丢失的空间语义补回来）

在抽帧循环里同步计算 ROI 内**质心位移**与**路径长度**（不动手部关键点，只用像素统计），分类规则全部可解释：

| 判据（按序） | 类型 | 依据 |
|---|---|---|
| 整段能量 < 3 且峰值 < 4.5 | 等待 | 整段能量≈静止 |
| 质心位移 ≥ 4.5% 画面 | 移物 | 拿起来搬到别处 |
| ≥1.5s 且能量 < 9 且位移小 | 目检 | 长时低幅（看/翻找） |
| 能量 ≥ 8 且 ≤2.5s 且位移小 | 装配 | 原地高能短动作（按/压） |
| 位移 ≥ 2.2% 或路径 ≥ 6.7% | 拿取 | 中等位移（伸手→握取→收回复合） |
| 都不匹配 | 其他 | 运动学不典型 → 人工定（宁缺勿错） |

**阈值判定依据**（全部来自样本能量分位数，非拍脑袋）：ROI 能量 p5=2.36 / p50=6.22 / p90=11.94 / max=19.41 →
- 死段 3.0（略高于 p5，留余量）
- 目检上限 9（p75=9.11 附近：低于「爆发」水平）
- 装配下限 8（p75–p90 之间：爆发区间）

### 3.4 描述骨架（挂在公司标准库 format 模板上）

分析前从 `motion_standard` 规则集拉取 format 模板，按类型生成描述骨架，人只替换占位符：

```
装配 → 装配[对象于：][位置：][距离：]
目检 → 目检[对象：][属性：]
移物 → 移物[对象：][距离：]
```

与分解工作台的描述规范**同一个标准库、同一套写法**；标准库拉不到时退化为「类型：」前缀，仍满足 V1 非空。

### 3.5 置信度分层（v3.38b 修正的设计错误）

v3.38 首版把「类型置信」`confAdj` 当段置信起点，导致「等待」类(0.4) 全被压 low、「目检/装配」(0.75) 全变 mid —— **类型判得准不准 ≠ 这个段该不该纳入**。v3.38b 解耦：

```
conf（段置信，决定 tier 与默认纳入）：
  0.90 起点（长静止边界）
  0.75 合并边界（微停顿回填，建议核对）
  0.50 时长异常（<300ms 或 >6000ms）
  0.40/0.50 段内无运动事件（帧差分不清「人在等」还是「机器自动」，必须人工确认）
cls（类型建议）：只做标记「类型待确认」，永不降档
```

## 五、踩过的坑（全部实锤，勿重蹈）

1. **合并判据 `bothShort` 空转**：写「两段都 <1.2s 才并」，而目标场景中位段长 1.7s —— 条件永不成立，合并回路形同虚设（只并掉 5/183）。判据必须对着**目标分布的中间段**设计，不能对着理想值设计。
2. **`conf = cls.confAdj` 混用两维置信**：类型置信 ≠ 段置信。「等待」被压 low 的同期，分类又把它判成「目检」—— 同一特征被分类和置信做相反判断，逻辑死局。
3. **`/低/.test(conf)` 误匹配「低**幅**」**：测试统计把 11 条全 0.90·高 的结果统计成 高6/低5（假失败）。tier 必须取「· 」后的档位词，不能全文搜索。
4. **测试脚本漏抓 type/desc**：DOM 抓取只取前 6 列，类型在 td[6]、描述在 td[7] —— 分类上线后端到端零验证，是「测试盲区」而非「功能正常」。
5. **refresh token 轮转 + reload 竞态**（测试脚手架）：后端 refresh 一次性轮转且带重放检测（`auth.service.ts:120-124`，重放会吊销该用户全部会话）。测试注入 R1 后页面首刷拿到 R2，若 `reload` 早于 localStorage 写回，页面用已吊销的 R1 → 触发重放检测 → 401 → 退回登录页 → `.aip-head` 超时（表现为「页面无故打不开」，而 API 侧工位明明存在）。修法：先 goto `WEB/?b=N#/target`（query 变更=完整文档加载），`waitForFunction(localStorage token ≠ 注入值)` 等首刷写回，再 reload。
6. **`baseOf(points)` 在合并循环内重复调用**：每段调 2 次全序列中位数（O(n log n)），全片耗时 +30%（527s→684s）。提到循环外算一次，输出完全一致。

## 六、已知限制（遗留项）

1. **运行间抖动**：同一 30s 视频三次分析得 11/12/11 段，差异仅在 19.3–22.1s 一处（多切出 0.8s+1.0s 两小段）。根因是 seek 抽帧的像素级差异使静止判定在阈值附近翻转。对产品影响有限（人工核对流程下边界差 ≤0.8s），但「同视频重跑结果不同」仍是缺陷。**修复方向**：能量曲线加 3 帧中值预平滑（未做，避免影响分类特征）。
2. **「目检」与「等待/机器自动」帧差上同形**：都表现为长时间低能量。已按「疑似长等待/机器自动」标 low 强制人工确认，但**无法自动区分**——这是帧差法原理性局限，要根治需引入物体检测/工位状态机（后续期）。
3. **ROI 写死** 0.18–0.78 / 0.30–0.80：换工位（手在画面角落、机位角度不同）须重标并复测。
4. **光照突变/机位漂移无专门护栏**：仅绝对上限 6s 兜底。
5. **手别仍是建议值**：左右分区能量相关仅 0.29–0.38，双手同活跃占 25%，不确定时记 0.75 中档标「手别待确认」。
6. **动作浪费识别仍未做**：依赖动素分类精度，建议切分与分类验证有效后单独开期。
