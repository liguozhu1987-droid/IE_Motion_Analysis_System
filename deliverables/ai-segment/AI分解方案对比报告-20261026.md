# AI 视频自动分解：行业落地方案 vs 当前系统技术方案对比报告

> 对比基准：`AI视频分解落地方案推荐.txt`（以下简称「推荐方案」）
> 当前系统：v3.33→v3.41 六代演进的 AI 自动分解模块（`#/ai-segment/:stationId`，前端 `app/web/src/ai-segment/`，后端 `ai-waste`/`ai-suggest` 模块）
> 报告日期：2026-10-26 ｜ 实测样本：SH-FA9-A12-PA10 真实工位视频 391.8s

---

## 一、结论摘要

1. **总体路线高度一致**：两者都拒绝「端到端大模型看视频」作为主链路，都采用「轻量感知 + 规则/可解释判定 + LLM 仅做辅助 + 人工终裁」。当前系统的产品哲学（AI 只提议、人确认、LLM 禁产数字）与推荐方案的精神完全同向，且在「LLM 边界」上比推荐方案**更严格**（推荐方案允许 LLM 产出「每循环减少 1～2 秒」类预期效果，当前系统铁律禁止）。
2. **当前系统的差异化优势在成本与隐私**：感知推理全在浏览器端（帧差能量 0.82×实时、MediaPipe wasm 离线随包），**视频零上传、零服务器 GPU、零推理费用**——比推荐方案的 YOLO 本地/服务器部署更轻。
3. **当前系统的主要差距有五项**：①无对象/工具/物料感知（推荐方案的 8～15 类检测完全缺失）；②无 SOP 步骤对齐能力；③浪费识别证据链弱（LLM 只吃文字、无证据帧锚定）；④无量化验收基线（没有标注真值，只有代理指标）；⑤工位 ROI 写死、无逐工位配置。
4. **建议按 P1（低成本高信任）/P2（能力补齐）/P3（按需演进）三档吸收**，总投入约 5～8 人日即可覆盖 P1+P2 全部条目，不需要引入 GPU 服务器或标注团队。

## 二、两方案概览

### 推荐方案（行业落地方案）

```
视频 → FFmpeg/OpenCV 预处理（1～2fps 抽帧/切片/ROI）
    → YOLO / YOLO-Pose / MediaPipe 检测人、手、工具、物料（8~15 类）
    → LSTM / 多尺度窗口 / 状态机 判定动作序列
    → SOP 步骤对齐（顺序约束、漏步/重复/顺序错误判定）
    → IE 规则库识别 9 类浪费（等待/多余动作/重复/搬运/转身/双手不平衡/顺序异常/瓶颈/过度加工）
    → 小 LLM/VLM 仅处理低置信片段 + 生成建议
    → 用户采纳/修改/忽略
```

分三阶段：POC（云端多模态做 baseline，验收：动作准确率≥70%、边界误差±2s、浪费精确率≥60%、建议有效率≥30%）→ 低成本主链路（1~2 月）→ 持续优化（工位专用 YOLO 微调、动作-浪费-改善映射库）。

### 当前系统

```
视频（本地 object URL，零上传）
  → 浏览器抽帧（100ms 定步长 seek）
  → 感知：帧差运动能量（默认）｜MediaPipe HandLandmarker（可选）   [v3.37/v3.33]
  → 时序：分级止点（≥500ms 长静止=边界；200~500ms 微停顿=合并候选）+ 合并回路   [v3.38b]
  → 分类：运动学 6 类规则（等待/移物/目检/拿取/装配/其他，全可解释，阈值取自能量分位数）
  → 描述：挂公司动作标准库骨架（MS1.1 format 模板）
  → 候选层：置信三档（高≥0.80/中 0.55~0.80/低<0.55），四规则降档（R1 时长/R2 手别/R3 人工边界/R4 覆盖）
  → 写入：候选按接受序重排时间链 →「封存旧版→开新版→提交纯 AI 要素」三步链，source=ai_assisted   [v3.41]
  → 浪费识别（独立页）：ai-waste = LLM 读要素描述 + 规则引擎 waste_triggers/ECRS 映射 → W1-W3 校验 → 服务端算数   [P3-9]
  → 改善建议：ai-suggest = LLM 候选 + 三轮校验 + LLM 禁产数字 + 永远待审   [v3.30]
```

## 三、逐层对比

| 层次 | 推荐方案 | 当前系统 | 对比结论 |
|---|---|---|---|
| **预处理/抽帧** | FFmpeg/OpenCV，1~2fps | 浏览器 seek 100ms 定步长（等效 10fps 能量采样） | **当前更细**；成本相当（浏览器解码 vs ffmpeg），且免上传 |
| **感知层** | YOLO（人/工具/物料等 8~15 类）+ YOLO-Pose + MediaPipe Hands | 帧差能量 ROI（默认）+ MediaPipe Hands（可选） | **推荐方案强**：有对象语义（contact_status/ROI_overlap）；当前只有「动没动」，无「动了什么」 |
| **时序动作识别** | LSTM / 多尺度窗口 / 状态机 | 分级止点 + 合并回路 + 运动学规则（本质是可解释状态机） | 当前等价于「状态机」路线（推荐方案中成本最低一档），无学习型时序模型；实测切点 96.9%~100% 压在局部能量低点，边界质量有据 |
| **动作标签** | 10~20 个（含扫码/套袋等业务动作） | 6 类通用动素（等待/移物/目检/拿取/装配/其他）+ 标准库描述 | **各有取舍**：业务动作需逐工位训练/配置；当前 6 类零训练零配置但语义粗（「扫码」会被归「使用/目检」级） |
| **SOP 对齐** | 步骤顺序约束，判定漏步/重复/顺序错误/超时 | **无** | **差距明确**。但当前系统有动作标准库（词表/模板）与程序分析工具，具备挂接基础 |
| **浪费识别** | IE 规则库直接吃感知特征（9 类规则+证据字段），规则化而非模型化 | ai-waste：**LLM 读已分解要素的文字描述** + 规则触发词/ECRS 映射 | **层次不同**：推荐方案从视频特征判浪费（可给时间点+证据帧）；当前从「分解结果文本」判浪费——依赖描述质量，浪费与时间点/画面的锚定弱。规则化思想一致（当前触发词/ECRS 走规则引擎） |
| **改善建议** | 规则模板+ECRS+知识库+小 LLM；LLM 可产预期效果 | ai-suggest：LLM 候选+三轮校验+**LLM 禁产数字（服务端重算）**+永远待审 | **当前更严格**：推荐方案的 JSON 示例让 LLM 直接写「每循环减少1～2秒」，正是当前系统明令禁止的幻觉风险点 |
| **置信度处理** | ≥0.8 直接展示 / 0.5~0.8 小模型复核 / <0.5 转人工 | 三档展示；低档强制人工确认；mid 档提示「边界建议核对」 | **基本对齐**（0.80/0.55 阈值几乎重合）。差距：推荐方案 mid 档触发「小模型复核」，当前 mid 档只做提示 |
| **证据链** | evidence_frames 证据帧 + 时间点 + 规则来源 + 置信度 | 时间点 + 置信度 + 类型 + 规则来源（能量分位数依据），**无证据帧** | **差距明确**。浏览器 canvas 已在解码视频，抽 2~3 张关键帧做证据零架构成本 |
| **人工决策** | 采纳/修改/忽略 | 候选逐条接受/拒绝/改手别改类型 + 批量二次确认 + Ctrl+Z 整批撤销 | **当前更完整**（撤销栈/焦点策略/写入隔离三步链） |
| **人工反馈闭环** | 确认结果回流规则库与训练集（微调 YOLO） | 采纳/拒绝进 source 统计（采纳率），**不回流算法参数** | **差距**：当前无再训练对象（规则法），但人工修正（类型改动）可作为逐工位阈值/模板自适应的信号源 |
| **成本** | 本地轻量模型为主；YOLO 需本地/边缘 GPU 或服务器 | **纯浏览器端，零服务器、零上传、0.82~1.3×实时**；MediaPipe wasm 21MB 离线随包 | **当前显著更优**（与用户成本约束强对齐） |
| **可解释性** | 规则来源+证据帧 | 全规则可解释（阈值全部来自实测能量分位数并写入文档） | **当前同档**，缺的只是视觉证据帧 |
| **量化验收** | 明确验收线（≥70% 准确率/±2s/≥60%/≥30%） | 代理指标（覆盖 95.8%、段中位 2.9s、切点能量对齐 96.9%、写入 6 项校验），**无人工标注真值** | **差距明确**：没有 ground truth，「准不准」始终无法回答 |

## 四、当前系统领先点（应保持，勿被方案带偏）

1. **视频零上传 + 浏览器推理**：比推荐方案的 YOLO 部署路线成本低一个量级，且天然规避视频数据出域问题（现场敏感）。
2. **LLM 边界更严**：「LLM 禁产数字」+「永远待审」+「三轮校验/W1-W3 落库」——推荐方案 9.2 节的 JSON 里 LLM 直接写 expected_effect 数字，恰是当前系统已封死的幻觉口子。
3. **写入工程更完整**：候选与工作台隔离（v3.41 三步链：封存→开新版→纯 AI 提交）、V1/V2/V3 校验、时间链重排、采纳率统计——推荐方案对此完全未涉及（它止步于「用户确认」）。
4. **阈值全部实测可溯源**：6 类分类阈值取自真实工位视频能量分位数（p5/p50/p90），拒绝拍脑袋；推荐方案的规则阈值（如 idle>2s、单手<20%）未给标定方法。
5. **真实工位已验证过失败模式**：手套对比度导致 MediaPipe 失效（左手检出 0.3%）→ 已切换帧差主链路并有决定性证据（切点能量对齐 96.9% vs 随机 28.7%）。推荐方案的 MediaPipe 路线在该实拍样本上会直接翻车。

## 五、当前系统差距点（按影响排序）

| # | 差距 | 影响 | 严重度 |
|---|---|---|---|
| G1 | **无对象/工具感知**：不知道「动了什么」（物料/工具/扫码枪），无法判「重复扫码」「搬运距离」等依赖物体状态的浪费 | 浪费识别天花板受限；分类只能到动素级、到不了业务动作级 | 高 |
| G2 | **无 SOP 步骤对齐**：不能判漏步/顺序错误/重复步骤 | 推荐方案中 IE 价值最高的能力之一（顺序异常浪费）缺失 | 高 |
| G3 | **浪费识别证据链弱**：ai-waste 从文字描述判浪费，无时间点回指、无证据帧；「等待浪费」这类时间型浪费本可从候选段特征直接规则判出 | 用户信任与审核效率；浪费与画面无法互证 | 高 |
| G4 | **无量化验收基线**：没有标注真值集，动作边界误差/类型准确率/浪费精确率均无法量化 | 无法回答「AI 到底准不准」，无法评估任何优化的真实收益 | 中高 |
| G5 | **工位 ROI/参数写死**：0.18–0.78/0.30–0.80 只适配 PA10 机位；光照突变/机位漂移无护栏 | 换工位即失效，规模化推广的第一阻塞点 | 中高 |
| G6 | **人工修正不回流**：类型改动/拒绝原因未沉淀为逐工位先验 | 同类工位重复犯错；推荐方案「结果缓存/工位专用模板」未实现 | 中 |
| G7 | mid 档置信无复核动作（仅提示） | 与推荐方案的「小模型复核」相比少一层兜底 | 低 |

## 六、优化建议

> 原则：延续「工具做薄」与三铁律；**不引入 GPU 服务器、不建标注团队**；每项独立可交付、可回归。

### P1｜低成本高信任（建议先做，合计约 3 人日）

| 项 | 内容 | 对应差距 | 成本 | 预期收益 |
|---|---|---|---|---|
| P1-1 **证据帧锚定** | 候选表/检查器加「证据帧」：点击候选时用已有 canvas 管线抽取起止+中点 3 帧（可先纯前端预览不落库，二期随候选入 t_element） | G3 | 0.5 人日 | 用户信任与审核效率直接提升；对齐推荐方案 evidence_frames |
| P1-2 **逐工位 ROI 配置化** | t_station 或工位配置页存 ROI 矩形 + 采样帧率；AI 分解页加「框选 ROI」校准入口（拖拽画框→存库）；无配置时退回现默认值 | G5 | 1 人日 | 解锁换工位推广；推荐方案「每个工位单独配置 ROI」落地 |
| P1-3 **时间型浪费规则直判** | 候选段的「等待/长低能段」特征（时长、能量、双侧静止）直接在本地规则判为疑似等待浪费并连同候选一起展示——不等 LLM；ai-waste 的 LLM 只处理文字型/综合型浪费 | G3 | 1 人日 | 浪费识别从「LLM 读文字」前移到「规则读特征」，与推荐方案 §8 的规则化思想对齐，且零 LLM 成本 |
| P1-4 **验收真值集（最小版）** | 选 2~3 段真实视频做**片段级**标注（推荐方案 §14：不做逐帧精标）：人工标起止+类型；脚本算边界误差中位数/类型准确率，作为后续所有优化的基准线 | G4 | 1~1.5 人日（含标注） | 回答「准不准」；对齐推荐方案验收目标（±2s/70%），超线才考虑上 P3 的模型路线 |

### P2｜能力补齐（P1 验证后，约 3~4 人日）

| 项 | 内容 | 对应差距 | 成本 | 说明 |
|---|---|---|---|---|
| P2-1 **轻量对象感知（不加 YOLO）** | 先用 MediaPipe Pose（wasm，与现 Hands 同基建）补人体/肩部关键点：修手套失效帧的手部推断、判「转身/弯腰」；帧差 ROI 内做左右物区划分近似「物料位移」。**评估 onnxruntime-web 跑 YOLO11n int8 的浏览器可行性后再决定是否上检测** | G1 | 1.5~2 人日 | 推荐方案 §5 的 8~15 类在单工位场景可裁剪到 3~5 类（人/手/物料/工位区）；浏览器 int8 量化单帧约 30~80ms，仍零服务器 |
| P2-2 **SOP 对齐（规则版）** | 复用动作标准库/程序分析已有的步骤定义，把候选序列按「预期动作序列」做顺序对齐（LCS/编辑距离），标出漏步/重复/顺序异常为低置信提示（不自动定罪） | G2 | 1~1.5 人日 | 对齐推荐方案 §7；「扫码重复」类浪费的前提是有对象感知（P2-1），MVP 先做「动作序列级」对齐 |
| P2-3 **人工修正回流** | 记录候选的拒绝/类型改动/手别改动，按工位聚合为「先验表」（该工位平均段长/常见类型分布/误判模式），下次分析时做逐工位阈值与合并参数微调（本地缓存即可，先不进库） | G6 | 0.5~1 人日 | 推荐方案 §10「结果缓存/反馈闭环」的规则法等价物 |
| P2-4 **双手不平衡规则** | 现有左右能量轨道已具备数据基础：左接触占比<20% 且右>70% 持续≥2s → 疑似双手不平衡（推荐方案 §8 原规则），进 P1-3 的规则直判清单 | G3 | 0.5 人日 | 零新增感知成本 |

### P3｜按需演进（触发条件明确后再做，不建议现在投入）

| 项 | 触发条件 | 内容 |
|---|---|---|
| P3-1 逐工位 YOLO 微调 | P1-4 基线显示类型准确率 <60% 且 P2-1 仍不达标；且有 ≥5 个同型工位的数据 | 标注 + 服务器/边缘训练（推荐方案阶段 3） |
| P3-2 LSTM/动作 Transformer | P3-1 之后仍需业务动作级（扫码/套袋）识别 | 推荐方案 §6.1 中成本档；当前规则法的可解释性优势会被牺牲，需权衡 |
| P3-3 云端多模态 POC 对照 | 需要评估天花板或做新工位冷启动 | 推荐方案阶段 1 的 baseline 用法；注意视频出域合规 |

### 明确不建议照搬的推荐方案内容

1. **「小 LLM/VLM 复核 mid 置信片段」**：与用户成本约束冲突；当前 mid 档仅 97/136 条，逐条调 VLM 成本不可控。替代：P1-3 规则直判 + 低档人工确认（已具备）。
2. **LLM 产出 expected_effect 数字**（推荐方案 §9.2 示例）：违反当前「LLM 禁产数字」铁律，保持现状。
3. **1~2fps 抽帧**：当前 100ms 能量采样是边界精度的来源（止点定位），降到 1~2fps 会直接损失 ±2s 内的边界能力；但 YOLO 类重感知可按 1~2fps 跑在能量定出的候选段内（事件触发，推荐方案 §10 的正确打开方式）。

## 七、路线图建议（合并视图）

```
现在 ──► P1（证据帧 + ROI 配置 + 等待/双手规则直判 + 真值集）   ~3 人日
     ──► 用真值集回答「准不准」，决定 P2 优先级
     ──► P2（Pose 关键点 + SOP 规则对齐 + 修正回流）            ~4 人日
     ──► 基线仍不达标才触发 P3（YOLO 微调 / 时序模型）
```

每一步都保持：AI 只提议、规则可解释、LLM 不碰数字、视频不出浏览器、候选不混写手工版本。
