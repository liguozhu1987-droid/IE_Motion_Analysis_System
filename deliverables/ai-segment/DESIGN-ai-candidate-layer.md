## 0. 三条硬约束（用户已拍板，不可协商）

| # | 约束 | 对设计的直接后果 |
|---|---|---|
| 1 | 推理在浏览器端（MediaPipe），**视频不上传** | 分析过程必须显式写"本机完成、视频不出机器"；无网络进度、无服务端任务队列、无服务端超时重试 |
| 2 | 一期**只做动作切分候选** | 不出现"浪费识别""动素分类准确率""改善建议"任何字样；预测类型一律标「建议」，且允许为空（`其他`） |
| 3 | AI 分段时间戳**绝不直接写入 `start_ms`** | 候选是**独立数据层**，不进 `draft` 数组；只有 IE 按 I/O 或点击接受才落值。这条决定了下面 §4、§6 的全部结构 |

**由此推导的第四条（本项目 AI 三铁律的延续）**：候选**永不自动接受**，包括"高置信度全自动"也不做。置信度只影响"是否预勾选"，不改变"必须有人按下接受"。

## 1. 一期明确不做（写在这里防止范围蔓延）

- ❌ 不做候选持久化（刷新即失效，见 §12）→ 因此**不做**"候选云同步/多人协同审阅"
- ❌ 不做候选的拖拽/裁边（接受后用现有 I/O 回路精修，见 §6.5）
- ❌ 不做已标注区间的"重切分"（人工已定稿，AI 不插话，见 §5 R3）
- ❌ 不做连续进度百分比动画、不做"AI 思考中"拟人化文案
- ❌ 不改检查器（`wb-inspector`）任何结构 —— 折叠态 `display:none` 吃按钮的坑（㉚）直接绕开
- ❌ 不改控制栏 41px 高度与按钮序列（宽度核算见 §4.3，**已无余量**）

## 2. 候选层视觉编码（四重编码，颜色永不单独表意）

> 现场现实：车间/会议室投影仪普遍偏色 + 男工色觉异常率约 8%。所以"AI 候选 vs 人工块"必须靠**形状**分辨，颜色只是第四重辅助。

### 2.1 编码表

| 维度 | 人工块（现有 `draft` 要素） | AI 候选 · 待审（pending） | 编码类型 |
|---|---|---|---|
| **填充** | VA 三分色**实底**（teal/amber/red） | 中性石墨 **45° 斜线纹理**（`repeating-linear-gradient`），底 6% 灰 | ① 纹理（最强，缩到 8px 宽仍可辨） |
| **边框** | 1px **实线** | 高/中 = 1px **虚线**；低 = 1px **点线** | ② 线型（形状） |
| **顶部置信条** | 无 | 块内顶部 4px 内 3 个 2×4px pip，实心数 3/2/1 = 高/中/低 | ③ 计数（形状，灰度可读） |
| **色彩** | VA 语义色 | 石墨中性（**刻意无色相**） | ④ 仅辅助 |
| **圆角** | 0（v3.17 直角边） | 0（**沿用直角**，不靠圆角区分 —— 圆角在小块上不可读） | — |
| **握把** | 左右 9px `.grip`，`ew-resize` | **无握把**（不可拖，指针 `pointer` 而非 `ew-resize`） | ⑤ 可交互性差异 |

> 为什么候选层「无色相」：`--teal/--amber/--red` 已被 VA/RNVA/NVA 占满，`--blue` 是选中环，`#e0483c` 是播放头。再引入第四个语义色（尤其紫/青紫系）会立刻触发"AI 模板味"并让 8 色同屏。**候选的本质是"还没落定"，视觉上就该是"未填实的线稿"，而不是"另一种颜色的块"。**

### 2.2 三档的完整差异化（必须同时成立，去掉任意一条仍有 ≥3 条可辨）

```
高 (≥0.80)  纹理 pitch 10px ｜ 虚线 border ｜ pip ×3 ｜ 文字 --ai-ink 满不透明 ｜ 预勾选
中 (0.55–0.80) 纹理 pitch 6px ｜ 虚线 border ｜ pip ×2 ｜ 文字 90% ｜ 预勾选 + 「需复核」标
低 (<0.55)  纹理 pitch 3px ｜ 点线 border ｜ pip ×1 ｜ 文字 62%（--ai-ink-weak）｜ 不预勾选
```

### 2.3 候选块 DOM 结构（关键：**不得有 `.grip`**）

```html
<div class="block cand pending tier-mid"
     data-cand-id="c6"
     style="left:calc(10500ms*60/1000); width:calc(1300ms*60/1000 - 2px)"
     tabindex="0" role="option" aria-selected="false"
     aria-label="AI 候选 6，右手，目检，置信度 0.72 中，10500 至 11800 毫秒">
  <span class="cand-pips" aria-hidden="true"><i class="on"></i><i class="on"></i><i></i></span>
  <span class="blk-seq">#6</span> 目检
</div>
```

- `width` 沿用现有口径 `dur*PX_PER_SEC - 2`（`PX_PER_SEC=60`），相邻候选之间自然留 2px 缝，**不需要额外的边界处理**
- 宽度 < 42px 时隐藏 `类型` 文本，只留 `#seq` + pips；宽度 < 22px 只留 pips（此时 `aria-label` 与 `title` 承担全部信息）
- 候选块 `top:3px; bottom:3px`（与人工块同高 = 22px @28px 轨道），**不额外占竖向空间**

## 3. 置信度：三档还是连续？→ 三档呈现 + 连续存储 + 硬规则回调

### 3.1 结论

- **数据层保留连续分数**（0–1，两位小数），UI 只呈现三档。
- 阈值：`高 ≥ 0.80`，`中 0.55 – 0.80`，`低 < 0.55`。阈值必须落配置（前端 `AI_CONF_THRESHOLDS` 常量），换模型只调常量不改 UI。
- **为什么不做连续表达**：可读性（22px 高 × 最窄 10px 宽的块装不下数值条）+ 决策价值（0.63 与 0.66 不产生不同动作，三档对应的是三种**动作**：接受 / 接受但复核 / 不勾选）。这是**决策粒度**，不是测量粒度。
- 连续分数在 tooltip 与候选页签表格里给到小数两位，需要细看的人有得看。

### 3.2 硬规则回调（分数之外，必须覆盖模型输出）

| 规则 | 条件 | 动作 | 依据 |
|---|---|---|---|
| **R1 时长护栏** | 候选时长 `< 0.30s` 或 `> 6.0s` | 强制降为**低**，不预勾选 | 现场动作要素典型 0.5–3s；0.3s 以下无标注价值（噪声），6s 以上几乎必是"多动作未切" |
| **R2 手别不确定** | 手别置信度 `< 0.60` | 强制降为**低** | 手别错 → 落到错轨 → 后续 V2 同手链校验口径被污染，代价高于收益 |
| **R3 人工边界贴边** | 候选与任一人工块边界距离 `< 80ms`（≈5 帧） | **不生成该候选**（该区间归人工） | 避免制造 1–4 帧的碎缝隙，直接违反 V2 同手链"零重叠零缝隙"口径 |
| **R4 已标注区不重切** | 时间段已被人工块覆盖 | 不生成候选 | 人工优先；也彻底消除候选与人工块的空间重叠 → 同轨共存的指针歧义归零（见 §4.1） |

> R4 是整套方案的**简化基石**：因为候选永远只填充"未标注区间"，所以同一轨道内**候选之间不重叠、候选与人工块也不重叠**。轨道可以继续是扁平的绝对定位序列，不需要分层 z-index、不需要碰撞检测、不需要堆叠轨道。

## 4. 轨道组织：不新增「AI 候选」轨，叠加到 L/R/B 轨（带数字核算）

### 4.1 决策与理由

**决策：候选渲染在它被预测的那只手所在轨道（L/R/B）内，作为同轨独立数据层的「幽灵块」。**

理由（按权重）：

1. **手别语义必须保留**。候选自带手别预测，放进单一「AI 轨」会丢掉"这是哪只手"这一 IE 的第一判据；而若在 AI 轨里再按手别分三条子带，就是 6 条轨（见 4.3，物理上不可能）。
2. **零竖向成本**。见 4.2 核算：1366 下加第 4 轨溢出 21px。
3. **接受即无位移**。候选接受后，块原地变成人工块（纹理→实底、虚线→实线、pips→消失），**时间和位置一个像素都不动**。空间连续性 = 用户能信任"我接受的就是我看到的"。
4. **R4 已消除同轨重叠**。候选只填空白，因此不需要 z-index 分层与命中纠偏。
5. 复用现有坐标系统（`PX_PER_SEC`、`lane` 的 `getBoundingClientRect`、双击 seek 的换算），不引入第二套时间→像素映射。

代价（诚实列出）：

| 代价 | 缓解 |
|---|---|
| 候选与人工块共享指针区域，命中测试必须靠"不重叠"这一前提（R4 保证），一旦将来放开 R4 就要重做分层 | 把 R4 写成硬约束并加断言（§11 A3） |
| 30 条候选撒在三条轨里，视觉噪声大，"一眼看全候选"难 | ①候选页签的**表格视图**是审阅主路径（不依赖眼睛扫轨道）；②「隔离审阅」模式（§6.6）把人工块压到 18% 不透明度 |
| 候选选中态与要素选中态共享视觉位置 | 用"双层焦点环 + 候选专属信息位"区分，且两者**互斥**（§9 冲突 C1） |

### 4.2 1366 竖向核算（加第 4 条常驻轨会怎样）

现有口径（`styles.css` 实测值）：

```
.wb-tlstrip-body { height: clamp(116px, 13vh, 124px); }
轨道内容高 = 刻度尺 16 + 3 轨 × 28 = 100；+ .timeline padding-bottom 9 = 109
```

| 视口 | `.wb-tlstrip-body` | 内容 109 的需求 | 余量 | 加第 4 轨（+28）后需求 | 结果 |
|---|---|---|---|---|---|
| **1366×768** | 116（13vh=99.8 → clamp 取下界 116） | 109 | **7px** | 137 | **溢出 21px** → `.wb-tl`（`overflow:auto`）出竖向滚动条，最后一条轨被 8px 滚动条 + 9px 底距压住，≈17px 不可见 |
| 1600×1000 | 124（13vh=130 → clamp 取上界 124） | 109 | 15px | 137 | 溢出 13px → 同上 |
| 1920×1080 | 124（同上） | 109 | 15px | 137 | 溢出 13px → 同上 |
| 全屏（F，1080p） | `clamp(120px,17vh,150px)` = 150 | 109 | 41px | 137 | **仅全屏可容纳** |

两条替代方案也已核算，均否决：

- **A. 四轨压到 21px**：4×21 = 84 = 3×28，竖向零成本。但块高 = 21 − 3 − 3 = **15px**，而候选块需要"4px 置信 pip 条 + 10.5px 文字"，实测需 ≥ 22px → **装不下**，只能把字号降到 9px（低于本项目轨道级 10.5px 的既有下限）→ 可读性崩塌，且人工块同步被压扁（改的是全局轨道高度，等于动了已定稿的 v3.15）。
- **B. 时间线条从 145 长到 173**：在 1366 必须从视频偷 28px（`--wb-stage-w` 由主区实测高度反推，改高度会连带重算宽度）→ 画面 676×380 → 626×352（**面积 −14%**），且 v3.15「四档视口单屏无滚动」的验收口径要全部重跑。为一个可选功能牺牲核心画布，不划算。

**结论：日常视口下第 4 条常驻轨不成立。候选叠加入轨。**

### 4.3 控制栏 41px 宽度核算（说明为什么触发入口不放控制栏）

1366 下舞台宽 676px，控制栏内部实测宽度需求：

| 组 | 内容 | 宽（约） |
|---|---|---|
| 播放 | `.wb-play` | 30 |
| 传输 | ←帧 / →帧 / −1s / +1s（含左分隔线） | 130 |
| 时间码 | `00:00.000` + `f145` + `30fps` | 144 |
| 倍率 | 0.5× 0.75× 1× | 90 |
| 循环开关 | `↻ 循环关` | 52 |
| 记录组（文字版） | ＋新增 / I起点 / O止点 / 分割 / 同上 | 282 |
| **合计** | | **728 > 676** |

→ 现有 @container 查询已把「分割/新增/同上」降为图标（约 30px each），合计 ≈ 648，**余量仅 28px**。
**加任何按钮都会把「同上」或「分割」重新挤进 `overflow:hidden` 裁切区**（v3.23 的痛点根因）。

**结论：触发入口不上控制栏。** 入口位置见 §6.1。

## 5. 状态机

```
                 ┌──────────────── 分析（本机 MediaPipe）────────────────┐
                 │                                                      ↓
 [无候选]  ──触发──►  analyzing ──完成──►  pending(候选块)  ──┬─接受─► accepted
    ▲                 │ 中止（保留已完成部分）                 │          │
    └─────────────────┴──────────────────────────────────────┘          │ 立即成为 draft 要素
                                                    └─否决─► rejected    │ （start_ms/dur_s 落值）
                                                              │          ↓
                                                              │      IE 用 I/O 精修 / 改手别 / 改类型
                                                              │          ↓
                                                              │      提交分解（V1/V2/V3 校验）
                                                              ↓
                                                   记入 rejectedRanges
                                              （再次分析该区间不再出候选）
```

**数据隔离（最关键的一条）**

| 数据 | 归属 | 是否参与提交校验 | 是否持久化 |
|---|---|---|---|
| `candidates[]` | 候选层（新增 state） | ❌ 完全隔离 | ❌ 会话内 |
| `rejectedRanges[]` | 候选层 | ❌ | ❌ 会话内 |
| `draft[]` | 既有要素层 | ✅ V1/V2/V3 | 提交后入库 |

> 这张表是"AI 绝不直接写 `start_ms`"的工程落点：**候选层与 `draft` 没有任何共享写入路径**，`draft` 只在"接受"这一个动作上被 `push`。

## 6. 交互流程

### 6.1 触发入口：顶栏 `wb-top-acts`，与「复用要素」并列

**位置理由**：
- 语义同类 —— 「复用要素」和「AI 切分」都是**批量灌入要素**的捷径，不是一个一个记录（控制栏记录组）也不是交付参数（交付条）。
- 宽度可行 —— 顶栏 1366 下合计约 1020px，加 116px 后 1136 < 1366，无裁切风险；顶栏不参与 `--wb-stage-w` 反推，改它不影响舞台。
- 单屏不破 —— 顶栏恒定 38px，只换内容不加行。

```html
<button class="wb-top-btn ai" title="AI 自动切分：在本机浏览器逐帧分析，生成动作候选（视频不上传，不写入要素，需你逐条确认）">
  <svg width="16" height="16" aria-hidden="true">…波形+竖虚线切分…</svg>
  AI 切分
</button>
```

**不提供全局快捷键**（长任务，误触代价高）。Ctrl+K 工具箱内提供条目「AI 自动切分」，kbd 位显示 `—`。

**禁用条件**：无视频 / 分析中 / 无写权限（`!canWrite`，与「复用要素」同口径）。禁用时 `title` 说明原因，不做灰按钮无语义。

### 6.2 分析中（诚实的进度表达）

覆盖层挂在**视频画面**（`.wb-screen` 内绝对定位），不是全页遮罩 —— 时间线与检查器仍可用。

```
┌──────────────────────────────────────┐
│  [扫描条：1px 轨 + 40px 亮段 1200ms 循环] │
│  阶段一 正在加载姿态模型               │   不确定态
│  阶段二 正在逐帧分析 12.4s / 18.0s      │   确定态（真实指标）
│  阶段三 正在合并动作边界               │   不确定态
│  已检出 9 条候选 · 已用 41s            │   真实计数
│  本机分析，视频不上传                  │   硬约束 1 的显性承诺
│                          [ 停止 ]      │   次要按钮
└──────────────────────────────────────┘
```

**为什么不给"均匀上涨的假进度条"**：
- 阶段一（wasm/模型首次下载 ~10MB）与阶段三（边界合并）**时长不可预测** → 用不确定态的扫描条，绝不画百分比。
- 阶段二**可给真实进度**：MediaPipe 是按时间戳线性逐帧处理的，`已处理时长 / 视频总长` 是真实比值，直接把扫描条切成确定态（填充比例 = 真实比值）。这是唯一"配得上进度条"的阶段。
- 全程显示**已检出候选数**（真实计数），即使进度条不准，用户也知道"有产出，不是卡死"。

**分析期间的交互让位**（不写这条必踩）：
- 播放按钮 `disabled`，`Space / L / J / K` 在 `onKeyDown` 顶部直接 return（`Esc` 例外）。原因：视频解码 + 逐帧推理抢同一线程，会让 `currentTime` 抖动、时间码乱跳，用户会判定"程序坏了"。
- 时间线仍可滚、可点选人工块（只读浏览），`I/O/S/N/D/Del` 等改写边界类操作同样让位（推理期改 `draft` 无意义且会与"接受"后的坐标校对打架）。
- 「停止」= 中止并可保留已完成部分；再次触发从头分析（不做断点续算，一期）。

### 6.3 分析完成

- 时间线条头部出现第三页签：`候选 · 10`（`<span class="cnt">`），**不自动展开时间线条、不自动切页签**（v3.15 单屏/不打断原则）。
- Toast（复用 `.wb-toast-flash`）：「本机分析完成 · 10 条候选（高 5 / 中 3 / 低 2）— 点「候选」页签审阅」。若时间线处于收起态（36px 单行），Toast 里额外给一个「审阅」按钮（点了才展开条 + 切页签）—— 呼应 v3.19 的教训："折叠态必须留可见入口"。
- 时间线轨道上候选块立即出现（无需切页签），这是"背景可见、细节入表"的双路径。

### 6.4 逐条接受 / 否决

**两条路径，共享同一 handler：**

| 路径 | 操作 | 说明 |
|---|---|---|
| 轨道块（看上下文） | 单击=选中候选（互斥清空要素选中）｜双击=定位播放头｜`Enter`=接受｜`Backspace`=否决 | 与人工块保持"单击选中、双击定位"的肌肉记忆一致 |
| 候选页签（逐条核对） | `↑↓` 移动行｜`Space`=播该段（复用现有片段播放语义，播到止点即停）｜`Enter`=接受并下一条｜`Backspace`=否决 | **主路径**：表格有 44px 级命中区，10px 宽的块不可能承载按钮 |

**「接受」的完整语义（一步到位，不设二次确认 —— 单条可撤销）**

```
接受(cand):
  1. draft.push({ start_ms: cand.start_ms, dur_s: durToGrid(cand.dur_s),
                  hand: cand.hand, type: cand.type ?? '其他',
                  va_class: TYPE_DEFAULTS[type], desc: 自动生成占位 })
  2. candidates 中移除该条（渲染色 → 实底，pips 消失，**位置零位移**）
  3. setSelected(新要素 key)  · setSelectedCand(null)
  4. seek(cand.start_ms)      · 播放头落在该要素起点（便于立刻按 Space/L 核对）
  5. document.activeElement.blur()   ← v3.27 铁律，见 §8
  6. toast undo 通道：「已接受 #9 装配 · 撤销（30 秒内）」
```

**`desc` 自动生成**：`接受`只保证"时间段有主"，不承诺类型正确。类型默认 `其他`（VA 默认值 RNVA，与 `TYPE_DEFAULTS` 一致），`desc` 写 `动作要素` 生成的结构化描述（如「目检 前横梁」），并在检查器里以 `--ai-ink-weak` 提示「类型来自 AI 建议，请确认」——但**不阻断**提交（避免造出新的校验墙）。

### 6.5 衔接现有 I/O 精修回路（IE 的核心工作流，必须原样接上）

```
接受 → 播放头在起点 → (自动失焦) → 按 L 看到止点 → 不对就 ←→ 逐帧 → 按 I / O 改边界
     → , / .  [ / ] 微调 → Ctrl+Enter 记录并跳下一条 → 回到候选页签 ↑↓ 选下一条
```

设计约束（不做会让回路断掉的三个决定）：
1. **接受后播放头必须落在起点**（不是"不动"）。理由：接受是显式动作，用户下一步必然要看这一段；而"单击块不跳播放头"的铁律（v3.22）针对的是**选中**，不是**接受**。
2. **接受后必须 blur**（§8）。否则焦点留在候选表格行 / 按钮上，`L/I/O` 全被吃，回路第一步就死。
3. **候选块本身不可拖拽**。拖拽精度问题（60px/s 下 1 帧≈1.3px）在 v3.19 已经定过口径：**粗调拖拽、精修键盘**。候选不需要"粗调"——它的起点是模型给的，人不该用鼠标去猜；接受后用 I/O 才是正确工具。少一套拖拽就少一整类握把重叠/命中偏移缺陷（v3.29 的 `.grip` 重叠坑）。

### 6.6 「隔离审阅」模式（低成本解决"轨道上候选太多看不清"）

时间线条头部（候选页签激活时）出现开关 `隔离`：
- 开 → 人工块 `opacity: .18`，候选块 100%，非当前手别的轨道 `opacity: .35`
- 关 → 全部 100%
- **不改变任何布局、高度、坐标**，纯滤镜级降权 → 零回归风险

### 6.7 低置信度处理

| 场景 | 处理 |
|---|---|
| 默认勾选 | **不勾选**（低置信度不进任何默认批量） |
| 轨道呈现 | 点线边框 + 3px 密纹理 + 1 pip + 文字 62% 不透明 |
| 表格呈现 | 行整体 `opacity: .6`，置信列显示 `0.47 低 · 待确认`（**文字**表达，不靠颜色） |
| 选中后 | 时间线条信息位显示 `候选 #7 · 0.47 · 低置信度 — 建议先按 Space 试看再决定` |
| 排序 | 仍按时间排（不放到末尾）—— 挪位置会让用户在轨道与表格之间对不上号 |
| 绝不 | 自动接受、静默丢弃、二次分析时跳过 |

### 6.8 批量接受的三级防误操作闸门

> 用户原话级别的问题：全接受 30 段是不可逆的破坏性操作。设计上的答案是 ——**根本不存在"全部接受"按钮**。

**闸门 1：范围永远是"勾选的 N 条"，不存在"全部"**
- 主按钮文案恒带数量：`接受勾选的 8 条`
- 唯一的"全选"入口是 `全选高置信度（5）`，**不提供 全选中/全选低**
- 预勾选规则固定：高 ✅ / 中 ✅（标「需复核」）/ 低 ❌

**闸门 2：条件触发二次确认（`n > 5` 或 勾选含低置信度 或 勾选含「时长护栏降级」条目）**

弹窗（**必须 `createPortal` 挂 `body`**，见 §9 C13）：

```
┌─ 接受 8 条候选？──────────────────────────┐
│  将新增 8 个要素（现有 3 → 11）             │
│  覆盖 3.4s → 18.0s · 左手 2 / 右手 4 / 双手 2 │
│  其中 3 条标「需复核」：置信度 0.58–0.72     │
│  ─────────────────────────────────────  │
│  接受后可用 I/O 精修边界；30 秒内可整批撤销   │
│                    [ 取消 ]  [ 接受 8 条 ] │
└─────────────────────────────────────────┘
```
- 主按钮文案 = **动作 + 数量**（`接受 8 条`），不用"确定/OK"
- 取消是默认焦点（`autoFocus` 在取消上），`Esc` = 取消
- 弹窗内**不显示**"全部/剩余全部"任何选项
- 勾选含低置信度时，那一行用 `--red` 语义色 + `!` 字标（**字标是主体，颜色是辅助**）

**闸门 3：可撤销，且是"整批一次"**
- 复用现有 `.wb-toast-undo` 单级 30s 通道，`payload` 从"单条删除"升级为**操作组**：`{ kind: 'delete' | 'accept', items: Element[] , label }`
- 一次批量 = 一个 undo 步（`Ctrl+Z` 不在现有快捷键里，走 toast 按钮 + 工具箱「撤销上一次操作」）
- Toast：「已接受 8 条候选 · 撤销（30 秒内）」
- **代价如实说**：单级通道意味着"批量接受"会覆盖尚未过期的"删除撤销"。可接受（都是 30s 窗口内的连续操作，覆盖概率低）；若将来要求多级，是独立任务。

**否决的批量**：`否决勾选的 N 条`。否决本身非破坏（不产生要素），但会让该区间在后续分析中**不再出候选**（记入 `rejectedRanges`）—— 所以也给 30s 撤销 + toast 说明后果：「已否决 8 条（该区间再次分析时不再提示）」。

| 切工位 / 组件卸载 | 同上，静默清空 | — |

## 8. 焦点策略（v3.27 铁律，逐条落在候选层上）

> 项目铁律：任何"提交/记录"类动作后不得把焦点留在输入框/按钮，必须 `blur()` 回 `body`，否则 `L/I/O` 被吃。

候选层需要执行 `(document.activeElement as HTMLElement)?.blur()` 的**全部路径**：

| # | 触发 | 为什么 |
|---|---|---|
| F1 | `接受`（单条，来自轨道块 Enter / 表格 Enter / 详情位按钮） | 之后用户固定要按 `L` 看 / `I/O` 修 |
| F2 | `接受勾选的 N 条`（弹窗确认后） | 同上；且弹窗按钮若保持焦点，`Space` 会重复触发确认 |
| F3 | `否决`（单条 / 批量） | 之后要按 `↑↓` 继续审 —— 焦点在按钮上 `↑↓` 会被当成滚动 |
| F4 | `立即分析` 触发后（按钮自身 blur） | 分析中虽然让位快捷键，但结束后要能立刻按 `L` 复核首条 |
| F5 | 分析完成/中止的 toast 出现后 | toast 内按钮不进 Tab 序的默认落点，不做 `autoFocus` |
| F6 | `隔离` / `全选高置信度` 开关后 | 属于"设置类"，不留焦点更省心 |

**反例保留（与 v3.27 一致）**：候选表格的「编辑描述」若能跳进描述框，那是**显式编辑意图**，允许聚焦（与现有清单「编辑」按钮同口径）。

**弹窗例外**：二次确认弹窗内焦点**必须**在弹窗内循环（`autoFocus` 取消按钮 + `Tab` 不逸出），关闭时把焦点**归还给触发按钮**还是 `body`？→ **归还 `body`**。理由：确认后紧接着要按 `L`，归还触发按钮会让 `Space/Enter` 重复触发批量接受（最危险的一种重复触发）。这条要单独写进实现注释。

## 9. 与既有交互的冲突清单（19 条，逐条给规避方案与验收断言）

| # | 既有交互（现状） | 候选层可能怎么撞坏 | 规避方案 | 验收断言 |
|---|---|---|---|---|
| **C1** | 选中态共享：`selected === element.key`（v3.22 单击=选中/取消） | 候选若复用 `selected` 会撞 key 空间，误选中/误删 | 候选用**独立 state** `selectedCand`，key 前缀 `cand:`；两者**互斥**：选候选时 `setSelected(null)` 且取消片段循环，选要素时 `setSelectedCand(null)`。所有既有 `selected` 逻辑零改动 | A1：选中候选后 `selected===null` 且无片段循环 |
| **C2** | 双击块=定位播放头（`onDoubleClick` → `seek`） | 候选块双击冒泡到 `.tl-lane` 的 `onDoubleClick`，重复 seek | 候选块 `onDoubleClick` 内 `stopPropagation()` 后自行 `seek(候选内相对位置)` | A2：双击候选块只 seek 一次，`playhead` 值唯一 |
| **C3** | 单击空白道=只定位不取消选中（v3.19 回滚的结论） | 候选块单击若不 `stopPropagation`，会走 lane 的 `onClick` | 候选块 `onPointerDown`/`onClick` 全部 `stopPropagation()`（与人工块一致） | A1 覆盖 |
| **C4** | `S` 分割：`splitAtPlayhead()` 找覆盖播放头的要素 | 播放头在候选内时，`S` 会"无目标"→ 用户以为坏了 | **不扩展 `S` 到候选**（避免两套分割语义）。命中候选且未命中要素时，`flash` 文案改为「当前是 AI 候选，接受后才能分割（Enter 接受）」 | A4：播放头在候选内按 S，`draft` 无变化 + 出现该文案 |
| **C5** | `Del` 删除选中要素（30s 撤销） | 选中候选时按 `Del` 若走原分支会删掉最后选中的要素（状态残留） | `Delete/Backspace` 分支最前插入：`if (selectedCand) { rejectCandidate(selectedCand); return; }`，且必须 `if (selected) …` 之前 | A5：选中候选按 Del → 候选被否决（进 undo 通道），`draft.length` 不变 |
| **C6** | 撤销：单级 30s `lastDeleted` | 批量接受若走另一套撤销，两个 toast 同屏打架（`.wb-toast-undo` 只容一个） | 升级为**操作组**：`lastOp = { kind:'delete'\|'accept', items, label }`，复用同一 toast 与按钮 | A6：连续「删除一条」→「批量接受」只出现一个 undo toast，且撤销回滚的是后者 |
| **C7** | `Esc` = 关帮助 + 取消选中 + blur | 候选选中后 Esc 不清候选 → 状态残留，`Del` 会误否决 | `if (selectedCand) setSelectedCand(null)` 并入同一分支；**分析中 Esc = 中止分析**（覆盖层是准模态，关闭模态是通用预期），中止非破坏（保留已完成候选） | A7：Esc 后 `selectedCand===null`；分析中 Esc → 状态回 idle 且已产出的候选数不为 0 |
| **C8** | `Ctrl+K` 工具箱（24 项，打开时屏蔽全局快捷键） | 新增「AI 自动切分」条目；若不屏蔽，工具箱内输入会触发全局键 | 复用既有 `typeMenuOpenRef` 式屏蔽；候选项归入「要素结构」组 | A8：工具箱内键入 `s` 不触发分割 |
| **C9** | 时间线收起态（36px 单行） | 分析完成后若自动展开条 → 违反 v3.15 单屏 | **不自动展开**；页签徽标 + toast 内「审阅」按钮（点了才展开）；`.closed` 时页签随条隐藏，入口只在 toast | A9：分析完成时 `tlOpen` 保持用户原值 |
| **C10** | 检查器折叠态 `display:none`（坑㉚：折叠吃掉面板内按钮） | 若把候选详情/批量按钮放进检查器，折叠时按钮消失 | **候选层一行代码都不进检查器**。详情位复用时间线条头部的 `.wb-panel-sel` 槽位；批量操作在候选页签内 | A10：折叠检查器后候选层所有操作仍可用（逐个点击可用） |
| **C11** | 时间线条 body 高度自适应（清单页签 184px，会压视频） | 候选页签若用 `is-list` 同高，1366 下视频再缩 68px | 候选页签独立高度 `clamp(148px, 19vh, 196px)`（1366 → 148px，视频 380→348，676×380→619×348，面积 −8.4%，小于现有清单页签的 −15.6%） | A11：1366 下四档无整页滚动（`scrollH === innerH`） |
| **C12** | 磁吸/拖拽：`.grip` 左右 9px，`min(9px, 45%)`（v3.29 窄块重叠坑） | 候选块若渲染 grip，会与人工块握把重叠/误拖 | 候选块**不渲染 `.grip`**，`cursor:pointer` | A12：候选块内 `.grip` 数量 = 0 |
| **C13** | **CSS 恒等 transform 坑**（检查器 `wb-in` 动画 `fill:both` + `to` 含 `translateY(0)` → 成 fixed 包含层，弹窗飞出去 2346px） | 批量确认弹窗若挂在 `.wb` 子树内，会被错算位置 | 弹窗与工具箱/TypeSelect 一致：**`createPortal(document.body)`**；同时新增动画**不写 `transform`**，只用 `opacity` | A13：1366/1600/1920 三档弹窗 `getBoundingClientRect()` 居中且 `top > 0` |
| **C14** | 分析中与播放争线程 | 分析时按 `L` 播放 → 时间码抖动 / 抖动引起 `onTimeUpdate` 高频重渲染 → 逐帧推理更慢，恶性循环 | `analyzing` 时 `onKeyDown` 顶部 `if (analyzing && e.key !== 'Escape') return;`；播放按钮 `disabled`；`<video>` 不 `pause()`（保持帧可取），但禁用一切 seek 入口 | A14：分析中按 L 视频 `currentTime` 不变、无播放态 |
| **C15** | 提交分解（V1/V2/V3） | 若候选进了 `draft`，会被当要素提交（直接违反硬约束 3） | 候选独立数组；`submit` 只读 `draft`；断言 `draft.length` 在提交前后与 `candidates.length` 无关 | A15：分析出 10 条候选、接受 0 条时提交，`element_count` 与接受前一致 |
| **C16** | 手别快捷键 `1/2/3`（`setHandOfSelected`） | 选中候选时按 1/2/3 无目标（静默失效） | `selectedCand` 时 `1/2/3` = **改候选的手别预测**（候选可在接受前改手别，块跳到对应轨道），与要素语义一致 | A16：选中候选按 2 → 候选移到 R 轨，接受后要素 `hand='R'` |
| **C17** | `↑↓` = 跳到上/下一要素边界（`jumpBoundary`） | 候选表格内 `↑↓` 会被全局抢走，无法逐行移动 | 表格容器 `onKeyDown` 内 `stopPropagation()`（表格是自管键盘的焦点域，与 `inField` 同理）；全局处理器加 `if (e.defaultPrevented) return;` | A17：候选表格内 `↑↓` 只移动行，播放头不动 |
| **C18** | 片段循环 + 空格播放（`segLoop`，Esc/再点块取消） | 候选块"再点一次取消"若也清片段循环，会造成"点候选顺手取消了要素循环" | 选候选 → 显式 `setSelected(null)`（循环随之停，这是**语义正确**的：选中对象换了）；不接受"静默保留循环" | A18：选中候选后 `segLoop` 相关提示消失 |
| **C19** | 版本/复测（`version+1`，封存只读） | 候选是纯前端，与版本无关，用户可能以为"候选被存下来了" | 分析完成 toast 与候选页签脚注常驻一行小字：「候选仅本次会话有效，刷新丢失；确认后请提交分解」 | A19：该小字在候选页签可见 |

## 12. 已知限制（必须显性告知用户，不许藏在文档里）

1. **候选不持久化**：刷新页面 / 切工位 / 换视频即丢失。文案落在候选页签脚注 + 分析完成 toast。若用户中途要离开，唯一保障是「接受并提交分解」。
2. **一期不保证类型准确**：类型是"建议"，默认 `其他`，需要 IE 改。UI 不出现任何准确率数字（没有验证过就不许写）。
3. **分析耗时随视频长度线性增长**：18s 视频约 40–60s；不给"预计剩余时间"（不可靠），只给已耗时与已检出数。
4. **本机算力差异大**：低端办公机（无独显、Chrome 单线程 wasm）可能慢 3–5 倍。分析中允许停止。
5. **不在移动端/小程序提供**（MediaPipe + 大视频 + 触屏精修三者叠加体验不可控，一期明确不做）。

```css

  --ai-hatch-pitch-mid:   6px;
  --ai-hatch-pitch-low:   3px;
```
