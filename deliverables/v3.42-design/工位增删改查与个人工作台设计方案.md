> 状态：**设计文档，未写代码**。基于现状侦察（2026-10），供用户决策后进入实施。

## 一、现状盘点（侦察结论）

### 1.1 工位 CRUD 现状

| 能力     | 后端                                                               | 前端                         |
| ------ | ---------------------------------------------------------------- | -------------------------- |
| 新建     | ✅ `POST /stations`、`POST /stations/from-cmc`（station:write）      | ✅ 新建向导 CreateStationWizard |
| 查询     | ✅ `GET /stations`、`GET /stations/:id`、版本清单                       | ✅ 产线总览卡片 + 对象树             |
| **编辑** | ✅ **`PATCH /stations/:id` 已存在**（station:write）                   | ❌ **无入口**                  |
| **删除** | ✅ **`DELETE /stations/:id` 已存在**（级联清理 ai-waste/ai-suggest/要素/改善） | ❌ **无入口**                  |

**结论：「仅支持新建」的观感来自前端 UI 缺编辑/删除按钮，后端能力已就绪。** 需求 1 主要是前端工作（补按钮 + 编辑弹窗/复用向导 + 删除确认），后端仅需按新归属模型补过滤与唯一性校验。

### 1.2 隔离与归属现状

- `t_station` 现有字段：`tenant_id / line_id / name / ct / tt / version / updated_by / created_by`。
- **无 `owner` 归属字段**（`created_by` 是审计性质，不做数据过滤）。
- `BaseRepository` 强制 `tenant_id` 过滤 → 现隔离粒度是 **租户级**：同一租户内所有用户看全部工位，无用户间隔离。
- `name` 无唯一约束（migrate.ts 仅 FK）；`station_id` 主键全局唯一（后端自动生成）。
- 权限：25 权限点 / 5 角色（sys_admin=`*`、ie_admin=模块通配、ie_engineer / line_leader / viewer 递减），PermissionsGuard 默认拒绝。

## 二、角色与权限模型

### 2.1 双层模型：RBAC 定能力上限，ACL 定资源可见范围

行业最佳实践（云文档/项目管理类产品通用）：**RBAC（角色→权限点）+ 资源级 ACL（归属→资源集）正交叠加**。最终可操作性 = `min(RBAC 能力, ACL 角色)`。

| 层           | 机制            | 回答的问题              |
| ----------- | ------------- | ------------------ |
| RBAC（现有，不动） | 25 权限点 + 5 角色 | 你**这类人**能不能做这类操作？  |
| ACL（新增）     | 工位归属 + 协作者    | 这个**工位**在不在你的可见范围？ |

### 2.2 各角色可见/可操作范围（目标态）

| 角色              | 可见工位范围                        | 可操作（写）范围             |
| --------------- | ----------------------------- | -------------------- |
| sys_admin       | 全租户全部                         | 全租户全部                |
| ie_admin        | 全租户全部                         | 全租户全部                |
| **ie_engineer** | **我的 + 共享给我**（默认）；可切换「全部」只读浏览 | 我的 + 共享给我且为 editor   |
| **line_leader** | 我的 + 共享给我 + **本产线全部**         | 我的 + 共享（editor）+ 本产线 |
| viewer          | 我的 + 共享给我（只读）                 | 无                    |

说明：

- 不为此新增权限点——共享能力挂 `station:write`（能建工位的人才能共享自己的工位），避免权限点膨胀（现有 25 点已够细）。
- admin/leader 的「看全部」不做开关硬隔离，维持现状视图；**普通用户（engineer/viewer）默认过滤为「我的+共享」**，这是本设计的核心行为变化。

## 三、工位归属与隔离策略

### 3.1 数据模型变更

```sql
-- t_station 新增
owner_user_id  nvarchar(32)  NULL      -- 归属人（FK t_user）；存量迁移 = created_by
-- 新增唯一约束（同归属人内名称唯一，允许跨用户同名）
UQ_station_owner_name (tenant_id, owner_user_id, name)
```

### 3.2 同名工位区分机制（用户 A、B 都建「SHFA1线PA10」）

- **名称允许跨用户重复**：唯一键落在 `(tenant_id, owner_user_id, name)`，A 和 B 各自可以有一个同名工位，互不可见。
- **`station_id` 仍是全局主键**（后端自动生成含随机段），它才是路由、API、时间线引用的唯一标识；**同名的两个工位 station_id 不同**，用 `owner_user_id` 段 + 拥有人展示来区分。
- **展示层消歧规则**：
  - 卡片/对象树标题 = 工位名；命中同名时在名称旁缀归属徽标（`@张三` / `@李四`）；
  - 共享列表、对比页、改善任务页凡引用同名工位处一律显示 `工位名 · 拥有人`；
  - 对象树分组天然隔离（我的/共享分组内通常不同名），全量视图（admin）内同名才触发徽标。
- **编码（station_code/工位编码）策略**：CMC 导入工位编码来自主数据属客观事实；手动新建留空时后端自动生成（v3.23 规则不变），生成串中不掺用户信息，唯一性靠 station_id 主键兜底。

### 3.3 隔离实施要点

1. **GET /stations 增加可见性过滤**（服务端，非前端过滤）：
   - admin/leader：不过滤（现状）；
   - engineer/viewer：`owner_user_id = me OR station_id IN (协作者表中 my 授权)`。
2. **写路径校验**：PATCH/DELETE/要素写入除 station:write 权限外，新增资源级判定「我是 owner / 我是 editor 协作者 / 我是 admin」——否则 403（越权操作他人工位）。
3. **看板与聚合**（集团看板/产线总览指标）不受影响：继续租户级聚合（统计不暴露明细，无需按人过滤）。
4. **存量迁移**：`UPDATE t_station SET owner_user_id = created_by WHERE owner_user_id IS NULL`；created_by 为空的挂到执行迁移的管理员，migrate.ts 增列 + 一次性脚本。
5. **CMC 建位**：from-cmc 创建的工位 owner = 操作人，天然进入「我的」；主数据事实（公司/产线）仍以 CMC 为准，二者不冲突。

## 四、共享与协作机制

### 4.1 协作模型：工位级授权 + 产线级批量共享

主场景是「**同一条产线多人协同分解**」，因此两层都要：

```sql
-- 工位级协作者
t_station_collaborator (
  station_id  nvarchar(32),   -- FK t_station
  user_id     nvarchar(32),   -- FK t_user（仅本租户内）
  acl_role    nvarchar(16),   -- 'editor' | 'viewer'
  granted_by  nvarchar(32), granted_at datetime,
  CONSTRAINT PK PRIMARY KEY (station_id, user_id)
)
-- 产线级批量授权（把该产线我名下现有+未来新建工位共享给某人）
t_line_share (
  tenant_id, line_id, grantor_user_id, grantee_user_id,
  acl_role nvarchar(16), granted_at datetime,
  CONSTRAINT PK PRIMARY KEY (tenant_id, line_id, grantor_user_id, grantee_user_id)
)
```

- 可见性判定优先级：**owner > 工位级协作者 > 产线级授权**（并集）。
- `acl_role` 决定操作上限（editor≈station:write 能力 / viewer 只读），**再与 RBAC 取交集**：viewer 角色的人即使被授 editor 也只能读。

### 4.2 协作交互设计

- 工位卡片新增「共享」按钮（仅 owner 与 admin 可见）→ 弹窗：
  - 本租户用户搜索（复用用户管理页的用户清单接口）；
  - 授权人 + 角色（editor/viewer）+ 已授权清单（可改角色/移除）；
  - 支持「整线共享」tab：选产线 + 授权人 + 角色 → 写 t_line_share。
- 被共享人侧：对象树出现「共享给我」分组；卡片归属徽标显示原主；无「共享」按钮（非 owner）。
- **冲突规则（多人同时改同一工位）**：
  - MVP 采用**乐观最后写入**（现状 submit=整版删除重插，天然整版覆盖）+ 卡片显示 `updated_by/updated_at` 提示他人最近改动；
  - 明确不做实时协同编辑（成本高，与「人拆AI校」单机作业面哲学不符）；
  - 复测开新版本机制（v3.41）天然提供版本快照，误覆盖可回看历史（只读）。

### 4.3 级联与清理

- 工位删除 → 先删 t_station_collaborator（加进 stations.remove() 级联链，**铁律：新增引用 t_station 的子表必须同步进级联**）；
- 产线共享随产线下线/工位清空自然失效（按 grantor 查询，无需清理）；
- 用户被禁用：其协作者授权保留但登录被拦（现状账号锁定机制），owner 工位由 admin 接管（PATCH owner_user_id）。

## 五、个人工作台菜单结构

### 5.1 原则

- 普通用户（engineer/viewer）登录默认落在**自己的工作视图**，不为他们展示集团级入口的干扰；
- admin/leader 保留现有三分区，增加视角切换；
- 复用现有页面（产线总览 StationListPage）做**视角化改造**，不另起新页——菜单只加一个锚点。

### 5.2 菜单结构（目标态）

```
顶栏业务区（改造）：
  我的工作台（默认首页，所有角色）
  集团看板（can('group:read') 才显示）
  改善任务
  配置区 / 系统区（现状不动）
```

### 5.3 「我的工作台」页面结构（StationListPage 视角化）

```
┌ 页头：我的工作台 ──────────────── [+ 新建工位] ┐
│ 视角 Tab：● 我的(12)  ○ 共享给我(3)  ○ 全部(41)*│
│            *「全部」仅 admin/leader 可见        │
├──────────────────────────────────────────────┤
│ 左：对象树（同步分组 我的/共享/全部）              │
│ 右：工位卡片网格（现有卡片 + 新增操作）            │
│   卡片操作行：分解工作台 | 分析 | 对比 | 导入 | 导出 │
│              | 共享(仅owner) | 编辑 | 删除(仅owner/admin) │
│ 卡片角标：@拥有人（同名/共享场景显示）              │
└──────────────────────────────────────────────┘
```

- 「我的」：owner=me 的工位，按产线分组；空态引导新建/导入；
- 「共享给我」：协作者/产线授权得到的工位；卡片带 `@原主` 徽标与角色标（可编辑/只读）；
- 「全部」：现状租户全量视图（admin/leader 默认落此 Tab，engineer 看不到该 Tab）；
- 普通用户隐藏「集团看板」入口（无 group:read 权限本来就看不了，同时菜单降噪）。

### 5.4 编辑/删除交互（补齐需求 1）

- **编辑**：卡片「编辑」按钮 → 复用 CreateStationWizard 的编辑模式（预填 line/name/ct/tt/program），PATCH 提交；仅 owner 与 admin 可见（有 station:write 且在 ACL 范围内）。
- **删除**：卡片「删除」ghost danger 按钮 → 二次确认弹窗（**列名级联影响**：该工位 N 个要素 / M 条改善建议 / AI 建议·浪费批次将一并删除）→ DELETE；仅 owner 与 admin 可见。遵循 v3.27 焦点策略（确认后 blur 回 body）。
- 权限不足时按钮直接不渲染（前端 `can()` + owner 判定双重控制），后端仍有资源级 403 兜底。

## 六、可选实施路径对比

| 维度       | **方案 A：owner 列 + 共享表（推荐）**                    | 方案 B：工作空间 Workspace 模型                             | 方案 C：每用户=一租户                 |
| -------- | --------------------------------------------- | -------------------------------------------------- | ---------------------------- |
| 思路       | t_station 加 owner_user_id，新增协作者/产线共享两张表       | 新增 t_workspace（个人/团队空间），工位挂 workspace_id，共享=空间成员管理 | 复用现有租户隔离，注册即建租户              |
| 改动量      | **小**：1 列 + 2 表 + 过滤/校验插桩 + 前端视角 Tab（约 2-3 天） | 大：全部查询路径加一层 join，迁移脚本，向导/对象树/看板全动（约 5-8 天）         | 极小（代码近零）                     |
| 数据隔离     | 用户级，清晰                                        | 空间级，最清晰，可扩展团队空间                                    | 机制上最彻底                       |
| 共享协作     | 工位/产线两级授权，够用                                  | 空间成员天然支持，粒度粗但好管理                                   | **需要跨租户打洞，破坏隔离模型**           |
| CMC/看板影响 | 无（聚合仍按租户）                                     | 看板聚合需跨 workspace 重算                                | **CMC 单一数据源被撕裂，看板/主数据联动全破坏** |
| 风险       | 低（存量迁移一条 UPDATE）                              | 中（查询回归面广，23 表联动）                                   | 高（语义混乱，CMC 铁律冲突，**不推荐**）     |
| 演进性      | B 的子集：未来可把 owner+共享平滑升级为 workspace            | 行业标准做法，支持后续审批流/团队管理                                | 无                            |

**推荐：方案 A 起步，预留 B 的演进路径**。理由：

1. 用户产品哲学是「工具做薄」——当前真实痛点是「同一产线几名 IE 协同 + 各自数据不打架」，工位级授权完全覆盖；
2. A 的 `owner_user_id` + 协作表在语义上是 workspace 的退化形式，未来引入团队空间时表结构可平滑迁移（工位从「挂人」改「挂空间」，协作表变空间成员表）；
3. 方案 C 与 CMC 铁律（公司/产线/项目以 CMC 为单一数据源）正面冲突，直接排除。

## 七、实施阶段建议（决策通过后）

| 阶段               | 内容                                                         | 交付判据                                         |
| ---------------- | ---------------------------------------------------------- | -------------------------------------------- |
| **P1 前端补齐 CRUD** | 卡片编辑（向导编辑模式）+ 删除（确认+级联提示）入口；后端 PATCH/DELETE 验证             | UI 测试：编辑改名生效、删除后对象树/卡片消失、无权限角色按钮不渲染          |
| **P2 归属与隔离**     | owner 列 + 存量迁移 + 服务端可见性过滤 + 写路径资源校验 + 「我的工作台」视角 Tab + 同名徽标 | engineer 只见自己的+共享的；A/B 各建同名工位互不干扰；admin 全量可见 |
| **P3 共享协作**      | 协作者/产线共享两表 + 共享弹窗 + 「共享给我」分组 + ACL×RBAC 交集 + 级联进 remove()  | 共享后对方可见可编辑（editor）/只读（viewer）；移除授权即刻失效       |

各阶段独立可交付、可回归（回归基线见用户偏好：契约 62+53 / smoke 143 / UI 314+22，清库后先 seed）。

## 八、开放决策点（请拍板）

1. **普通用户是否默认隐藏「集团看板」入口**？（本方案倾向隐藏；如需保留只读浏览可选否）
2. **删除工位的权限是否允许 line_leader**？本方案默认仅 owner+admin；若 leader 常需清理本线工位可放开。
3. **产线级共享是否 P3 一并做**？若 P2 后已满足协作需要，产线级授权可后置。
4. **存量工位归属**：一律归 created_by（建位人）是否有例外（如演示数据归 admin）。
