### 0.2 八个关键判断

1. **分类维度是"任务"，不是"产线"，也不是"项目号"**。任务 = 产线 × 项目 × 时间段 × 轮次的一次分解改善活动；同一物理工位在不同任务下各有自己的要素集，历史不互相覆盖。这是本版最大的结构性变更。
2. **一个工作簿 = 一个分解任务**，不跨任务合并。跨期对比走 `baseline_task_id` 指针 + `#/diff`，不靠把两期数据塞进一张表。
3. **sheet 按"分析职责"分，不按"工位"分**。动作分解（事实层）、增值非增值分析（分类层）、动作分析（改善层）三张表各司其职，靠 `工位编码 + 序号` 关联，不互相堆列。
4. **四类时间独立成列且互斥穷尽**：手作业 / 机器 / 走动 / 等待，每要素只落一桶，`Σ四桶 = Σ标准工时 = CT`，三级可校验。判定依据是**可配置的动作类型 → 时间桶映射**，不新增采集字段。
5. **"只关注焦点"落成可执行的焦点要素规则**：命中浪费触发器 / 占 CT 比超阈值 / NVA 且超时的要素才进「04_动作分析」表，按改善潜力降序取每工位 Top5、全任务 Top30；其余要素的分析列一律留空。这与公司 `VA Template` 的 `Select` / `IF Improved` / `Action` 三列语义一致。
6. **信息克制写进硬约束**：分析数据表 ≤ 12 列、焦点表 ≤ 9 列、汇总页 ≤ 14 列；每要素最多 1 个浪费类型、1 个 ECRS、1 条 ≤24 字改善方向；长文本（VA 改判理由、AI 证据、完整措施、原始读数）一律不进 Excel，留在系统页面，说明页注明取数入口。
7. **口径不新增第二套计算**：全部复用 `analyzeStation` / `buildLineAnalysis` / `buildMotionDetail`；四类时间与焦点标记是**导出时的派生列**，不落库、不改引擎、不回写正式 ST（延续项目铁律）。
8. **现有单工位 CSV 保持不变**，继续承担"回导"职责；本 XLSX 仅供阅读 / 评审 / 打印归档，两者不合并、不互为模板。

### 0.3 口径裁定说明（针对编写期间的两种并行解读）

同一需求曾出现另一版解读，本定稿明确**不予采用**，理由写在前面以免后续会话回摆：

| 被废弃的解读 | 与用户原话的冲突 | 本定稿 |
|---|---|---|
| "每个工位 × 每种分析各一张 sheet"（20 工位 → 40+ 张，并引入分卷 ZIP / 总索引） | 用户第 3 点原话："每个工位一个 sheet **指的是每种分析一个 sheet**，例如动作分解 1 个 sheet，增值非增值分析一个 sheet" —— 是**分析类型**决定 sheet 数，工位数不参与 | **固定 6 张 sheet**，与工位数无关；不需要分卷、不需要 ZIP、不需要 sheet 名截断去重 |
| "机器/走动/等待**不加 3 个稀疏数值列**，改用 1 列『时间归属』枚举 + 表头小计" | 用户第 4 点原话："机器/走动/等待时间**建议单独成列**，根据维护的动作要素类型自动判断" —— 明确要**成列**；且公司 `VA Template` 的 `Work / Machine / Walk / Wait time` 就是四个独立数值列 | **`03` 表 E–H 四个独立数值列**，"稀疏"恰是优点（一行一值、可直接 SUM / 条件格式 / 画组合票）；另设 `99_说明` 给映射表，不占明细列 |

> 说明：另一版中关于 **REFA / MTM-1 真实工厂明细表形态、MTM 代码缺失声明、砍列清单、历史回填两案** 的内容不与用户裁决冲突，已吸收进 §2.5、§1.5、§3.5、§4.5、§11。

## 1. 现状梳理（v0.2 复核）

### 1.1 数据模型

| 实体 | 表 | 关键字段 | 对本方案的意义 |
|---|---|---|---|
| 租户 / 公司 | `t_tenant` | `name`、`region` | 封面公司 / 区域 |
| 产线 | `t_line` | `tenant_id`、`line_id`、`name`、`process_type`、`product_type`、`product_project`、`factory_code`、`cmc_line_id` | 任务的归属产线；`product_project` 是项目编号**快照来源**，不是任务 |
| 项目主数据 | `t_project` | `tenant_id`、`project_id`、`name`、`customer`、`stage` | 任务关联的项目维度 |
| 工位 | `t_station` | `station_id`、`tenant_id`、`line_id`、`name`、`ct`、`tt`、`version`、`program_number`、`owner_user_id` | 物理工位主数据；`version` = 生效 `bol_version` 指针（**每工位独立**） |
| 要素（动素级） | `t_element` | `element_id`、`station_id`、`seq`、`start_ms`、`dur_s`、`hand`、`type`、`desc`、`va_class`、`outlier_flag`、`rating`、`allowance`、`std_time`、`bol_version`、`source` | 所有分析表的数据源；**当前无 `task_id`** |
| 改善任务 | `t_improvement` | `station_id`、`measure`、`est_save_s`、`status`、`priority` | 可选附注；本版默认不进 Excel（避免分析列膨胀） |
| **分解任务** | **不存在** | — | **必须新建，见 §3.2** |
| 规则集 | `t_rule_set` / `app/config/rules/*.json` | `va_rules` RV3.64（44 类）、`waste_triggers` WT01–WT18、`ecrsa_map` M01–M15、`motion_standard` MS1.3 | 类型词表、VA 默认判定、浪费触发、改善措施短句、时间桶配置的单一来源 |

**确认结论（代码核查）**：全库**不存在**分解任务实体；`program_number` 是 CMC 项目号（驾驶舱维度），`product_project` 是产线上挂的产品项目编号，二者都无法表达"同一产线不同时期的两轮分解"。v0.1 用它们代理任务号，会直接把两轮改善的要素混在一起 —— 必须建实体。

已固化的口径（不得改）：

- `CT = Σ 有效要素（outlier_flag=0）的 std_time`
- `std_time = dur_s × rating × (1 + allowance)`
- 三分法 `VA / RNVA / NVA`（RNVA = Required Non-Value Added，必要非增值）
- `检查 = RNVA`（MS1.3 用户裁定，须持续改善）；操作族按**作业对象**条件判定（工夹具=RNVA / 装入产品的物料=VA）
- `机器自动` 的 `RNVA` 仅为占位，**不参与操作工 VA 率**（MS1.2）
- 动素词表 = 经典 19 类 ∪ 公司 28 类，去重后 `va_rules.types` 共 **44 类**
- `desc` 末尾可能带 `[VA改判|…]` / `[VA确认|…]` 标记，长度上限 120
- **版本语义**：每次"开始复测"→ `station.version + 1`，旧版要素以 `bol_version` 留存；复测是**逐工位**的，当前没有跨工位的"轮次"概念 —— 这正是任务实体要补的洞

### 1.2 现有单工位导出

- 前端入口：`WorkbenchPage.tsx` 顶部「导出 CSV」；`StationListPage.tsx` 工位卡片「导出」。
- 服务端：`elements.controller.ts` → `GET /stations/:id/elements/export`，权限 `element:read` + 资源级可见性。
- 实际列（14 个原始字段）：`工位编码, 版本, 序号, 手别, 类型, 描述, 时长s, VA类别, 异常标记, 异常原因, 评比, 宽放, 标准工时, 起点ms`。
- 特点：单 sheet、纯原始字段、无分析结论、无格式、无合计。
- **同一份 CSV 也是导入模板**（`序号/手别/类型/描述/时长s` 必需列）。这构成回导闭环，本方案不破坏它：新导出列结构不复用 CSV 表头，说明页明示「不可回导」。

### 1.3 现有分析能力（可直接复用，不新增计算）

- `analyzeStation` → `metrics`（CT / TT / gap / VA·RNVA·NVA 秒数与占比 / 异常数秒数）、`wastes`、`pending`、`outliers`、`hands`。
- `buildMotionDetail`（v3.48）→ 每要素一行 `seq / type / desc / va_class / std_time / waste_types / directions`；`directions` 来自 `ecrsa_map.mappings[].measure` 短句（8–24 字），**一个要素命中多个触发器时会 join 成多句长文本** —— 这正是用户第 4 点所指"分析列内容过多"的技术根因。
- `buildLineAnalysis` → 每工位 `ct_s / tt_s / va_s / rnva_s / nva_s / va_pct / element_count / outlier_count / waste_count / is_bottleneck` + `balance_rate` + `totals` + `bottleneck`。
- `waste_triggers` 输出带 `factor` 潜在收益因子（来自 `ecrsa_map.mappings[].factor`），可作为**焦点排序**的业务依据，无需新造评分。

## 2. 行业最佳实践：明细页有没有？是什么样？

### 2.1 直接回答

**有，但不存在"一份国际强制标准规定的固定明细页"。** 没有 ISO / IEC 标准规定动作分析明细表的列名、列序或色板；行业存在的是**跨企业高度收敛的表单骨架与计算口径**，来源有三：

1. **工作研究 / 作业测定**（ILO、REFA、工业工程教材、时间研究表）：一行一要素、多循环读数、评比与宽放、`ST = 观测 × 评比 × (1+宽放)`。
2. **预定动作时间标准**（MTM-1 / MODAPTS / MOST）与**丰田标准作业三票**（工序能力表 / 标准作业组合票 / 标准作业票）+ 山积表：动作按代码 / 等级取时，手作业、步行、机器自动、等待四类时间必须分开表达，并以节拍线判断能否装进 TT。
3. **企业自有 IE 表单体系**（本例即 `IRSCN-IE-Method-07` / `IRSCN-IE-Motion-03`）：把上述共识固化成本厂编号、页眉、签署栏与色板 —— 对用户而言，**公司表单就是"组织级最佳实践"，优先级高于任何外部模板**。

因此设计上应"对齐共识骨架 + 映射公司表单"，而不是另造一套列。

### 2.2 明细页的三段式骨架（行业收敛形态）

| 段 | 内容 | 目的 | 本方案对应 |
|---|---|---|---|
| ① 表头元数据 | 研究 / 任务号、产品项目、产线、工位、操作者、观察者 / 制表人、日期 / 班次、方法版本、规则版本、TT、表单编号 | **可追溯、可复测**：换人换期也能对得上 | 各 sheet 第 1–3 行信息区 + `00_封面` |
| ② 要素明细 | 序号、要素描述、断点 / 起止点、动作类型、观测时长、评比、宽放、标准工时、VA 判定、四类时间分列、异常标记 | **一要素一行、断点可复现、时间可加总** | `02_动作分解` + `03_增值非增值分析` |
| ③ 汇总与结论 | CT / TT / 差值、VA·RNVA·NVA 小计与占比、四类时间合计、瓶颈、改善机会（ECRS） | **直接指向决策**，不让读者自己算 | `01_工位汇总` + 各表合计区 + `04_动作分析` |

### 2.3 四条设计原则（含"信息克制"）

1. **事实与结论分层**：原始观测数据不与分析结论混在同一张表 / 同一格；分析结论可重算，读数不可改。REFA 把"读数区"和"计算区"分开、公司把 `PA10-1` 原始分解与 `动作分析-VA` / `改善建议` 分表，正是此意。
2. **时间可加总、可校验**：任何时间列都必须满足 `Σ = CT`，且异常要素剔除有显式标记。评审时第一个被质疑的往往就是"这些数字加起来对不对"。
3. **四类时间必须分列 / 分色**：标准作业组合票的核心价值就是让"人等设备""走动浪费"**看得见**；合成一个总工时列、或只给一个枚举标签而不给可求和的数值，都会削弱改善机会识别。这是行业共识，也正是用户第 4 点的要求。
4. **信息克制（Data Discipline）**：只保留驱动决策的字段，长文本证据另存。行业资料明确把 **"Data Overload — 采集过多无目标数据"** 列为时间研究的常见错误，并要求"keep the time study sheet simple and easy to read to avoid errors"；同时"要素定义必须清晰到两个观察者能测出同一断点"。**用户第 4 点"只关注焦点、不让复杂表架构造成混乱"与这一条完全一致，属于最佳实践而非妥协。**

### 2.4 反模式清单（本方案明确禁止）

| 反模式 | 后果 | 本方案的硬约束 |
|---|---|---|
| 一张明细表 18–20+ 列，横向滚动 | 评审者找不到重点，打印变形 | 分析数据表 **≤ 12 列**，焦点表 **≤ 9 列**，汇总页 ≤ 14 列 |
| 每格塞长文本（全部浪费类型 + 全部改善措施 join） | 行高炸裂、黑白打印糊成一团 | 单要素 **1 浪费 / 1 ECRS / 1 条 ≤24 字措施**；其余在说明页注明"完整证据见系统" |
| 颜色是唯一信息载体 | 黑白打印 / 色弱读者不可读 | 颜色 + 文字标签并用（`增值(VA)` / `★` / `异常`） |
| AI 证据、改判理由、原始读数进明细表 | 事实层被污染，且可能跨模块泄露 | 一律不进 Excel（双模块边界铁律） |
| 分析结论与原始事实混列 | 无法复核、无法重算 | 三张分析表职责单一，靠 `工位编码 + 序号` 关联 |
| 多工位同 sheet 却没有工位编码列 | 数据无法筛选、无法追溯 | 每张数据表首列固定 `工位编码`；表头区标任务号 |
| 数据口径与系统引擎不一致 | 导出与页面数字打架 | 全部复用 `analyzeStation` / `buildLineAnalysis`，导出只做派生与排版 |
| sheet 数随工位数增长 | 40+ 标签页、需要分卷 ZIP、索引维护成本 | **固定 6 页**，结构不随数据量变化 |

### 2.5 真实工厂的三种明细表形态（正面回答"最佳实践长什么样"）

| 形态 | 典型列 / 结构 | 核心纪律 | 本平台差距 |
|---|---|---|---|
| **A. REFA 时间研究记录（Zeitaufnahme，德国 / 欧洲制造业通行）** | 表头（对象 / 方法 / 观察者 / 日期）+ 要素号 / 描述 / 断点 + 每要素多周期读数（≥3 次）+ 平均值 / 修正 / 评比 / 宽放 / 标准时间 + 干扰记录 | 每要素至少测 3 次、先求平均再修正；异常读数单列标记剔除 | **无多周期读数 / CV / 最低重复值** → 本导出只能自称"分析汇总表"，不可冒充观测表 |
| **B. MTM-1 分析表（预定动作时间标准，汽车 / 电子装配常用）** | 手别 / 结构行 / 动作描述 / MTM 代码（如 `M3G1`）/ 数量 × 频次 / TMU / 时间(s) / 增值(是·否) / 距离·条件 | 动作按代码等级取时（1 TMU = 0.036 s）；代码与 TMU 可复算 | **无 MTM 代码与 TMU** → 动作分析表是"近似动作分析"，用词表类型替代，说明页必须写清 |
| **C. 标准作业组合票 / 山积表（TPS）** | 作业步骤 / 顺序号 / 手作业(实线) / 机器自动(虚线) / 步行(波浪线) / 等待(⇔) / 时间轴 + TT 红线 + 质量·安全要点符号 | 四类时间**分列分色**；判断人的循环能否装进节拍；显示人机等待与走动浪费 | 平台有类型可**推导**四类时间，但非采集字段；`03` 表四列 + `01` 汇总即对应此形态的表格版 |

> 三种形态的共同点：**按分析目的拆表**（观测 / VA / 动作 / 组合票各司其职），而不是把全部字段塞进一张"万能明细表"。这正是本方案 §4「每种分析一个 sheet」的行业依据。
> 三种形态的**共同反例**：把 A 的多周期读数、B 的 MTM 代码、C 的图形符号、VA 判定、ECRS 措施、AI 证据全部堆在一张表里 —— 列数失控、无人能读。

### 2.6 行业表单口径要点

- **时间研究表**：表头（study id / 零件号 / 工序号 / 操作者 / 观察者 / 日期 / 方法版本 / 评比刻度）+ 要素表（要素号 / 描述 / 断点 / 频次 / 评比 / 基本时间）+ 读数表（每周期一列 + `is_valid` 剔除异常）。汇总出平均 / 最低重复值 → 正常时间 → 宽放 → ST。多数工厂评比刻度 100（正常=100）或 75（西屋法），宽放按强度分档。
- **动素分析（Therblig）**：Gilbreth 原 18 类、现代常收敛 17 类（Find 并入 Search）；左右手双栏、改善前后双栏、专用符号与色板（各厂自定义）。平台词表是"经典 + 公司"并集，**不得声称是标准 Therblig 表**。
- **VA / NVA 分析**：三分法 VA / NNVA(RNVA) / NVA；`VA 比率` 在**工位层面分母取 CT**，流程层面（PCE）分母取 Lead Time —— 本方案属工位层面，分母 CT，说明页写明以免评审质疑。
- **标准作业组合票 / 山积表**：手作业（实线）、机器自动（虚线）、步行（波浪线）、等待（空白 / ⇔）四类时间叠在带 TT 线的时间轴上。资料明确"四类时间分列是行业共识"，且"等待既可能是增值的（人等设备）也可能是浪费（设备等人）"，因此等待列必须保留原始类型，不能合并进 NVA 后丢掉。
- **Excel 多 sheet 组织惯例**：封面 / 索引放最前、汇总页一对象一行、明细页逐条记录、说明页殿后；前缀命名（`00_` / `01_` / `99_`）；sheet 名 ≤31 字符、禁 `/ \ ? * : [ ]`；冻结表头、深色表头白字、单位写在列名、真数值、两位小数、打印横向 + 重复表头；不要只靠颜色传意；标签页在约 40 张后浏览体验明显下降 —— 本方案固定 6 张，天然规避。

### 2.7 共识 vs 自定义（v0.2 更新）

| 属于行业成熟共识（可直接定） | 属于各家自定义（需用户确认） |
|---|---|
| 一要素一行、按 seq 排序、断点可复现 | 表单编号与页眉版式（IRSCN-IE-Method-07 / Motion-03） |
| 观测时长 / 评比 / 宽放 / ST 四列并列（或按目的拆表） | 动素词表用经典 19 类还是公司 28 类（本平台=并集 44 类） |
| `ST = 观测 × 评比 × (1+宽放)` | 四类时间的**类型归属**（尤其"移物"同名词、转身 / 弯腰） |
| VA / RNVA / NVA 三分 + 小计与占比 | VA% 用全口径还是操作工口径（本方案两者并列，见 §6.3） |
| 手作业 / 机器 / 走动 / 等待分列、Σ=CT | 焦点阈值、TopN、改善潜力权重 |
| 汇总页一工位一行、CT/TT/瓶颈/平衡率 | Route 列是否留空、是否需要改善前后双栏 |
| 封面 / 索引 + 汇总 + 明细 + 说明 | 签名 / 审核栏、A4 横向打印 |
| 冻结表头、真数值、两位小数、黑白可读 | 色板具体色值、文件命名与归档编号规则 |
| 事实层与结论层分离、信息克制、按目的拆表 | 每张表允许的最大列数（本方案定 12 / 9 / 14） |

## 3. 裁决一：分解任务（数据模型与导出范围）

### 3.1 业务定义与层级

> **分解任务** = 在某条产线上、针对某个项目、在**某个时间段**开展的**一次**动作分解与改善活动；一个任务包含若干个工位，每个工位在该任务下有自己的一套要素。

层级（自上而下，逐级一对多）：

```
租户 t_tenant
└── 产线 t_line（PA10 前保险杠预装线）
    └── 项目 t_project（P-2026-018）
        └── 分解任务 t_decomposition_task        ← 本版新增：按「时间段 + 轮次」分类
            ├── DT-2026-011  2026 Q3 基线测时    [2026-07-01 ~ 07-05]  baseline
            ├── DT-2026-014  2026 Q4 线平衡改善  [2026-10-08 ~ 10-12]  kaizen_after → baseline=011
            └── DT-2027-002  年度复核            [2027-01-06 ~ 01-08]  recheck
        └── 工位（t_task_station）：PA10-ST01 / ST02 / … / ST18
            └── 要素 t_element（task_id + station_id + bol_version + seq）
```

三条口径裁定：

1. **任务属于单产线**（不跨线）。需要跨线时建多个任务，不把一条任务拉成大杂烩 —— 符合"工具做薄"。
2. **同一物理工位可归属多个任务**（这正是"不同时期多次改善"的含义），但**同一任务内一个工位只有一套生效要素**。
3. **任务内修订**继续用现有 `station.version` / `bol_version` 机制；**跨任务对比**用 `baseline_task_id` + `#/diff`。两种历史维度正交，不混用。

### 3.2 实体设计（实现阶段按此建表）

**`t_decomposition_task`（分解任务主表）**

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `task_id` | VARCHAR(32) PK | 内部主键 |
| `tenant_id` | VARCHAR(32) | 租户隔离（**所有查询必带**） |
| `task_no` | VARCHAR(64) | 人可读任务号；`UNIQUE(tenant_id, task_no)` |
| `line_id` | VARCHAR(32) | 所属产线（单线约束） |
| `project_id` | VARCHAR(32) NULL | 关联 `t_project`；允许空（历史 / 无项目场景） |
| `project_no_snapshot` | VARCHAR(64) | 项目号快照，防止主数据改名后归档不可追溯 |
| `name` | NVARCHAR(64) | 任务名称，如「2026 Q4 线平衡改善」 |
| `round_type` | VARCHAR(16) | `baseline` / `kaizen_after` / `recheck` / `legacy` / `other` |
| `round_no` | INT | 同产线同项目下的轮次序号（1、2、3…） |
| `period_start` / `period_end` | DATE | **观测 / 活动时间段**（用户第 1 点的"不同时期"） |
| `status` | VARCHAR(16) | `active` / `closed` / `archived` / `legacy` |
| `baseline_task_id` | VARCHAR(32) NULL | 改善前基线任务指针，供跨期对比 |
| `rule_versions` | VARCHAR(128) | `va_rules / waste_triggers / motion_standard` 版本快照，可审计 |
| `owner_user_id` / `created_by` | VARCHAR(32) | 归属人 / 创建人 |
| `created_at` / `closed_at` | DATETIME | 时间戳 |

**`t_task_station`（任务—工位关联 / 快照）**

| 字段 | 说明 |
|---|---|
| `task_id` + `station_id` | 复合主键 |
| `station_code_snapshot` / `station_name_snapshot` | 归档用名称快照（工位改名不影响历史文件） |
| `bol_version` | **该任务锁定的要素版本**；导出只读此版本，不随后续修订漂移 |
| `ct_snapshot` / `tt_snapshot` | 可选；用于归档一致性校验 |
| `seq_no` | 工位在任务内的展示顺序 |

**`t_element` 增列**

| 字段 | 说明 |
|---|---|
| `task_id` VARCHAR(32) | 新增；与 `station_id + bol_version + seq` 共同构成唯一性 |
| `element_id` | **扩长**：现 `elementId()` = `{stationId}-V{version}-{seq}`，跨任务会撞号 → 改为 `{taskNo}-{stationId}-V{version}-{seq}`，实体 `length: 48` → **96，且迁移 DDL 必须同步** |

> ⚠️ 项目铁律提醒（不得跳过）：① `migrate.ts` 是表结构唯一来源；② **实体 length / type 与迁移 DDL 必须同步改**（v3.58.1 审计列 32 位截断教训）；③ 布尔列**一律不写 `type`**，交 TypeORM 按方言推断（v3.60 mssql `boolean` 启动崩溃教训）；④ 改完实体必须显跑 `npm run migrate:prod` **再重启 API**（dist 重建 ≠ 进程更新）；⑤ 隔离测试走 SQLite 全绿 ≠ 生产 mssql 能起，**必须真起一次 API 验证**。

**上线顺序**：① 建表 + 回填（幂等脚本）→ ② 任务创建 / 选择 UI → ③ 复测挂任务钩子 → ④ 导出功能。任务实体未上线前，导出功能不开放。

### 3.3 任务号规则（建议，需确认）

```
DT-{YYYY}-{NNN}          例：DT-2026-011
凭证显示：DT-2026-011 · 2026 Q4 线平衡改善 · PA10 / P-2026-018 · 2026-10-08~10-12 · 改善后复测
```

- `task_no` 租户内唯一、不可变；`name` 可改。
- 封面、每个 sheet 的表头信息区、文件名**三处同时带任务号 + 时间段**，保证文件脱离系统后仍可归档追溯。
- 备选：`{line}-{project}-{YYYYMM}-{seq}`（可读性强但长）；采用哪一种见 §9 P0-1。

### 3.4 版本 / 历史隔离矩阵

| 场景 | 隔离机制 | 说明 |
|---|---|---|
| 同一任务内改要素（修订 v1→v2） | `bol_version` + `station.version` | 现有机制，不变 |
| 同一产线不同时期的两轮改善 | `task_id` | **本版新增**，两轮要素互不覆盖 |
| 改善前后对比 | `baseline_task_id` + `#/diff` | 跨任务读两个快照，不合并导出 |
| 规则版本变更导致判定不同 | `rule_versions` 快照 + 说明页 | 归档时写明当时生效的 RV / MS 版本 |

### 3.5 存量数据迁移策略（必须显式，避免"清库后严禁 seed"的坑）

- 现状：`t_station` 仅余 `ST010`（BJFA1 / 框架组装），其 20 要素 / 4 改善 / 1 AI 建议批次 / 1 AI 浪费批次保留；**严禁 `npm run seed`**（`scripts/seed.ts` 会植入 L01-ST01/02 等，抵消清空）。
- **方案 A（本版推荐，适配当前单工位存量）**：建两张新表 → 建**一个**历史归档任务 `DT-LEGACY`（`round_type=legacy`、`status=archived`、时间段取 `MIN(created_at)~MAX(created_at)`）→ 回填 `t_element.task_id` 与 `t_task_station` → 存量 `element_id` **保持原值不重写**（避免引用断裂），新数据用新编码 → 校验 `GROUP BY task_id` 无孤儿。
- **方案 B（备选，适用于未来多产线历史数据）**：按 `(tenant_id, line_id, project)` 聚合现有工位，各建一条 `round_no=1` / `status=legacy` 的任务，标题「历史数据（自动归集）」，把各工位当前 `station.version` 写入关系表。
- **两案共同声明**：无法还原真实历史轮次，回填只保证"能按任务导出"，**不承诺历史轮次准确**；封面标注「历史数据自动归集，轮次不可考」。
- 迁移步骤：只增列不加约束；回滚时保留列、仅停用任务过滤，不做破坏性删列。

### 3.6 权限与查询影响

- 任务级：`assertTaskReadable` = `tenant_id` 一致 + 任务存在；任务不可跨租户可见。
- 工位级：**仍逐工位走 `assertReadable` / `resolveVisibleStationIds`**（owner ∪ 协作者 ∪ 产线共享 ∪ data_scope 四并集），不因任务实体绕过既有 ACL / 行级权限收口。
- 导出范围只包含可见工位；不可见工位既不出现在弹窗，也不出现在文件（防"导出即泄露"）。
- 所有新增 SQL 必带 `tenant_id` 约束（v3.59.2 line 分支越权教训：绝不依赖候选集兜底）。
- 聚合（平衡率 / 瓶颈）须在引擎计算**之前**按可见工位过滤；dashboard 缓存键带可见范围指纹的既有做法不变。

### 3.7 对其他模块的影响清单（实现前逐项评估，本方案不改）

| 模块 | 影响 | 处置原则 |
|---|---|---|
| 分解工作台 / 工位列表 | 新建工位时要选 / 带 `task_id` | 默认继承当前任务，不新增必填步骤 |
| 分析 / 对比页 | `analyzeStation` 查询条件需带 `task_id` | 纯函数引擎不变，仅调用方传参 |
| AI 分解 / AI 建议 / AI 浪费批次 | 三类批次表也需 `task_id`，否则跨任务串数据 | 延续"模块隔离 + AI 写入版本隔离 + 双来源线"铁律，单独排期 |
| 改善任务 `t_improvement` | 措施应归属任务 | 同上，单独排期 |
| 单工位 CSV 导出 / 导入 | 导入模板需带 `task_id` 或由上下文注入 | **CSV 列结构保持不变**；任务由请求上下文注入，不破坏回导闭环 |
| `#/diff` 对比页 | 支持"跨任务"对比 | 复用 `baseline_task_id`，不新建对比引擎 |
| 审计日志 | 新增 `export` 动作摘要含 `task_no` | 可选（§9 P2） |

### 3.8 导出范围定义（v0.2 定稿）

| 范围 | 取数条件 | 说明 |
|---|---|---|
| **按分解任务（唯一默认）** | `t_task_station.task_id = ?` + `tenant_id` + 逐工位 ACL 过滤 | 一个工作簿 = 一个任务 |
| 按产线 | **降级为"任务下拉的筛选器"**，不再是独立导出范围 | 选产线 → 只列该产线的任务，避免范围歧义 |
| 按项目号 | 同上，仅作任务筛选维度 | 不再用 `program_number` 直接聚合要素 |

- 不支持一次导出多个任务到同一文件（保持"薄"）；需要跨期对比走 `#/diff`。
- 只导出任务锁定的 `bol_version`（`t_task_station.bol_version`），不导出该任务的封存修订版。
- 工位排序：`t_task_station.seq_no ASC`，回落 `station_id ASC`。
- 任务状态 `archived` / `legacy` 仍可导出（归档是主要用途），但弹窗标注"已归档 / 历史归集"。

## 4. 裁决二 / 三：工作簿结构（按分析分表）

### 4.1 新旧结构对比

| 维度 | v0.1（每工位一页） | 并行解读（每工位 × 每分析一页） | **v0.2 定稿（每种分析一页）** |
|---|---|---|---|
| sheet 数 | `3 + 工位数`（20 工位 = 23 页） | `3 + 2×工位数`（20 工位 = 43 页） | **恒为 6 页**，与工位数无关 |
| 组织轴 | 工位 | 工位 × 分析 | **分析职责** |
| 单页内容 | 一个工位的全部事实 + 全部分析（18 列） | 一个工位的一类分析（7–8 列） | 全任务所有工位的**一类**分析（≤12 列） |
| 工位区分 | sheet 名 | sheet 名 | **首列 `工位编码`**（可筛选 / 排序 / 透视） |
| 横评能力 | 需来回切 sheet | 需来回切 sheet | 一张表内直接筛选、排序、做透视 |
| 分卷 / ZIP | 不需要 | >38 工位强制分卷 ZIP | **不需要** |
| 与公司表单 | 偏离（`VA Template` 多工位同 sheet） | 偏离 | **一致** |

### 4.2 固定 6 张 sheet

```
VA分析_{任务号}_{YYYYMMDD-HHmm}.xlsx
├── 00_封面              任务元数据 + 关键结论 + 索引 + 图例
├── 01_工位汇总          一工位一行（管理层横评 / 瓶颈）
├── 02_动作分解          全要素 · 事实层（是什么 / 何时 / 多久）
├── 03_增值非增值分析    全要素 · 分类层（VA 判定 + 四类时间分列 + 焦点标记）
├── 04_动作分析          仅焦点要素 · 改善层（1 浪费 / 1 ECRS / 1 条措施）
└── 99_说明              字段字典 + 口径公式 + 类型→时间桶映射 + 限制
```

- **3 张骨架页 + 3 张分析页**，职责单一；sheet 数不随工位数增长。
- 未分解工位：在 `01_工位汇总` 标"未分解"，`02/03` 表不产生数据行；不再为它单独建 sheet（避免无意义空页）。
- 弹窗可关闭 `04_动作分析`（无 `analysis:read` 时自动关闭并降级），其余 5 页固定。
- sheet 名固定，无需 31 字符截断 / 非法字符清洗 / `~n` 去重逻辑 —— v0.1 与并行解读的一整类风险（sheet 膨胀、分卷、索引维护）直接消失。

### 4.3 三张分析表的职责分工与关联键

| 表 | 唯一职责 | 行数 | 不做什么 |
|---|---|---|---|
| `02_动作分解` | 记录事实：动作是什么、何时发生、观测多久、标准工时多少 | 全要素（含异常） | 不判 VA、不给改善、不放长文本 |
| `03_增值非增值分析` | 回答"时间花在哪、是否增值"：VA 判定 + 四类时间分列 + 占比 + 焦点标记 | 全有效要素（异常行标灰、不计入合计） | 不写浪费类型 / 改善方向 |
| `04_动作分析` | 回答"改什么、怎么改"：**仅焦点要素**，一行一条措施 | 焦点要素（默认 ≤ Top30） | 不重复罗列全部要素、不堆多句措施 |

**关联键**：`工位编码 + 序号`（+ 表头区的 `任务号`）。三表可用同一组键做 VLOOKUP / 筛选对齐；**不靠复制列来"方便查看"**，这是控制列数的关键手段。

### 4.4 信息克制的硬约束（写进实现验收）

| 约束 | 值 |
|---|---|
| 列数上限 | `02/03` ≤ 12 列；`04` ≤ 9 列；`01_工位汇总` ≤ 14 列 |
| 分析单元格文本 | 改善方向 ≤ 24 字（超长截断并加 `…`），完整内容在系统页面；浪费类型 ≤ 1 个；ECRS ≤ 1 个 |
| 长文本落点 | `desc` 原文保留在 `02` 表；VA 改判理由 / AI 证据 / 完整措施 / 原始读数 **一律不进 Excel** |
| 焦点表行数 | 每工位 Top5、全任务 Top30（可配置 20/30/50） |
| 颜色 | 仅用于「增值判定」列与「焦点」列；文字标签始终并存，黑白打印可读 |
| 空值 | 空单元格，不写 `-` / `N/A`；四类时间未命中即留空（便于 SUM） |
| 新增列规则 | 想加一列，先从该表删一列 —— 防止后续需求把表重新撑宽 |

### 4.5 从 v0.1 的 18 列"砍掉清单"（及去向）

| 砍掉 / 迁移 | 去向 | 理由 |
|---|---|---|
| 浪费类型（全量 join）、改善方向（全量 join）、ECRS | `04` 表，且各取 Top1 | 长文本是"内容繁琐"的根因；只在焦点行出现 |
| 来源（manual / ai_assisted）、`element_id` | 不进 Excel，系统页面可查 | 不驱动评审决策；避免跨模块边界混淆 |
| VA 改判 / 确认标记原文、异常原因全文 | 不进 Excel；`02/03` 只留短标签 | 说明页给出追溯路径（工作台 / 单工位 CSV） |
| 终点(s) | 删列，`终点 = 起点 + 观测` | 可复算，省 1 列 |
| 占CT%、焦点 ★ | 移入 `03` 表 | 分类层核心信号 |
| 起点 / 观测 / 评比 / 宽放 / ST | 保留在 `02` 表 | 行业共识的四列并列，审计必需 |
| 动素类型 | 保留在 `02` 表；`03` 表用四类时间列替代 | 分类层不需要再重复一次类型列 |
| 相关改善任务块、异常明细块、签名栏 | 改善任务不进 Excel；签名栏只在 `99_说明` 尾部留打印位 | 产品哲学砍管理功能；避免下部块把表拉长 |

> 说明：评比 / 宽放 / 起点属于**可追溯性字段**，本定稿选择保留在事实层 `02` 表（行业共识），而不是像并行解读那样全部砍掉只在说明页描述 —— 因为导出物要能独立接受审核，不能要求评审者回到系统才能复核 ST 的来历。列数仍通过"分层"控制在 11 列。

| # | 列名 | 取值 / 口径 | 宽 | 格式 |
|---|---|---|---|---|
| A | 工位编码 | 同上 | 12 | 文本 |
| B | 序号 | `seq` | 6 | 整数 |
| C | 作业内容 | `desc` 短显示（≤24 字，超长 `…`） | 26 | 文本 |
| D | 增值判定 | `增值(VA)` / `必要非增值(RNVA)` / `非增值(NVA)` | 16 | 居中 + 三色浅底 |
| E | **手作业(s)** | `time_bucket=manual` → `std_time`，否则空 | 10 | 0.00 |
| F | **机器(s)** | `time_bucket=machine` → `std_time`，否则空 | 9 | 0.00 |
| G | **走动(s)** | `time_bucket=walk` → `std_time`，否则空 | 9 | 0.00 |
| H | **等待(s)** | `time_bucket=wait` → `std_time`，否则空 | 9 | 0.00 |
| I | 标准工时(s) | `std_time`（= E+F+G+H，校验列） | 11 | 0.00 |
| J | 占CT(%) | `std_time / 工位CT × 100` | 8 | 0.0% |
| K | 焦点 | 命中焦点规则 → `★`，否则空（对应公司 `Select` 列） | 6 | 居中 |

- `IF Valued`（公司 K 列）→ 本表 D 列；`IF Improved` / `Action`（公司 L/M 列）**移到 `04_动作分析`**，本表不重复。

- **合计区（表格下方，不给每行加列）**：
  ```
  CT xx.xx s ｜ 手作业 xx.xx ｜ 机器 xx.xx ｜ 走动 xx.xx ｜ 等待 xx.xx ｜ Σ四桶 = CT ✓
  VA xx.xx s (xx.x%) ｜ RNVA xx.xx s (xx.x%) ｜ NVA xx.xx s (xx.x%)
  VA%(全口径) xx.x% ｜ VA%(操作工口径) xx.x% ｜ 操作工作业时间 = CT − 机器 xx.xx s
  ```

| # | 列名 | 取值 / 口径 | 宽 | 格式 |
|---|---|---|---|---|
| A | 工位编码 | 同上 | 12 | 文本 |
| B | 序号 | `seq` | 6 | 整数 |
| C | 作业内容 | `desc` 短显示 ≤24 字 | 28 | 文本 |
| D | 增值判定 | 同 `03` D 列 | 14 | 三色浅底 |
| E | 标准工时(s) | `std_time` | 10 | 0.00 |
| F | 浪费类型 | 命中 `waste_triggers` 的 **Top1** waste 名 | 12 | 文本 |

- 预计可压缩是**规则推导的潜力值，不是收益承诺**；说明页写明"用于排序与筛选，不作为财务节约依据，须现场实测复核"。
- 焦点要素为 0 时仍保留 sheet，写"本任务未识别到焦点要素"，不静默删页。
- 无 `analysis:read` 权限时**整表不生成**（弹窗提示降级），`03` 表的 VA 判定与四类时间仍保留。

### 5.6 `99_说明`

1. **字段字典**：按 sheet 分组，列出每列来源字段、口径、单位、精度。
2. **公式**：`ST = 观测 × 评比 × (1+宽放)`；`CT = Σ有效要素 ST`；`占CT%`；`VA%` 双口径；`平衡率`；`Σ四桶 = ΣST = CT`；`预计可压缩 = ST × factor`。
3. **类型 → 时间桶完整映射表**（§6.1 的 44 类清单），并注明"由 `motion_standard.time_bucket` 配置，未配置回落 `manual`"。
4. **焦点要素规则**（§6.4），含阈值、TopN、排序依据。
5. **三分法定义**（VA / RNVA / NVA），引用平台规则版本；注明与公司 `VA N-VA Define` 表的对应关系；`检查 = RNVA`。
6. **口径声明**：VA% 分母为 CT（工位层面，非 Lead Time）；机器时间不参与操作工 VA 率；四类时间为**类型推导值，非采集字段**；本表为**单循环要素分解汇总表，非 REFA 式原始观测表**；**无 MTM 代码 / TMU，不得冒充 MTM-1 分析表**。
7. **公司表单映射表**（§6.5），列出 `IF Valued / IF Improved / Action / Select / Route` 的去向。
8. **数据边界**：未采集 `cycle_count / CV / 最低重复值 / Route / 步数 / MTM 代码`；仅任务锁定版本；`desc` 标记原文见系统；被砍列的追溯路径（工作台 / 单工位 CSV / 说明页）。
9. **用途与免责**：仅供阅读 / 评审 / 打印归档；不可回导；推导值与标准工时须经现场实测与工程师复核，AI 输出为决策辅助，不替代工程判断；涉及安全 / 质量结论须走 EHS 与质量体系复核。
10. **规则版本与生成信息**：任务号、导出时间、导出人、引擎 / 规则版本、文件校验用合计值；尾部留打印签署位。

## 6. 自动判定与口径（本版核心）

### 6.1 动作要素类型 → 四类时间桶（自动判定）

**判定入口**：`motion_standard.json` 中每个类型新增 `time_bucket` 字段（`manual | machine | walk | wait`），在「动作标准」配置页（`#/standard`）随类型一起维护、随 MS 版本发布。导出时按 `t_element.type` 查表取值；**未配置的类型一律回落 `manual`**，并在 `99_说明` 列出回落清单，保证可审计。

| 时间桶 | 列名 | 类型词（覆盖 `va_rules` 全部 44 类） | 判据 |
|---|---|---|---|
| `machine` | 机器(s) | `机器自动` | 设备自动动作，不由操作工执行 |
| `walk` | 走动(s) | `走动`、`移物`、`移动` | 脚步位移类（含负载走动） |
| `wait` | 等待(s) | `等待`、`可避免延迟`、`不可避免延迟`、`休息` | 人等设备 / 节拍 / 疲劳停顿 |
| `manual` | 手作业(s) | **其余 36 类**：经典 `伸手/握取/定位/装配/拆卸/使用/放手/检查/寻找/发现/选择/思考/预置/持住/其他`；公司 `拿取/放置/粘贴/涂/按/压/抬/推/拉/插/拔/目检/点检/检测/清洁/扫描/翻转/拆/转身/弯腰/操作` | 除上述三类外的全部人工作业 |

**边界裁定（需现场确认，见 §9 P0-3）**：

- `转身` / `弯腰`：是躯干动作但**无脚步位移**，计入 `manual`（Work time），不计 Walk time。公司表单无单列，故**不新设第五桶**以免列膨胀；改善价值由 `04` 表的「动作浪费」焦点规则体现。
- `持住`：手在持住，计入 `manual`；它是头号浪费，由 `waste_triggers WT01/WT02` 识别进焦点表。
- `休息` / `不可避免延迟`：归 `wait`，与标准作业组合票的"等待"口径一致。
- ⚠️ **`移物` 同名词歧义（已知口径风险）**：经典动素的「移物」= 手部搬运物件（VA），公司词表的「移物」= 负载走动（VA），平台 `va_rules` 中二者**共用同一词条**（`util.ts` 已注明"装配/移物 两词共用"）。本版统一按 `walk` 处理，并在说明页明示：**若该要素实为手部移物，Walk time 会高估**；P2 数据治理建议在词表层拆分同名词后再细化判定，本版不引入基于 `desc` 关键词的猜测规则（避免"宁缺勿错"变成"猜错"）。
- **数据质量提示**：若某工位 `manual` 回落占比 > 20% CT，表头加提示「时间归属配置不足，请检查动作类型维护」，与并行解读中的质量门思路一致，但**不因此改回单枚举列**。

### 6.2 四桶互斥穷尽与三级校验

```
逐要素（仅有效要素）： E+F+G+H = I（标准工时）   每要素恰有一桶有值
逐工位：             Σ(E:H) = ΣI = 工位 CT       误差 ≤ 0.01 s
全任务：             Σ各工位 CT = 01_工位汇总 ΣCT  误差 ≤ 0.01 s
```

- 三条写进验收断言（§10）；**异常要素（outlier_flag=1）不参与上述断言**，其 E–H 留空、不计入任何合计。
- 导出前服务端自检，不通过则返回 500 并写明失败工位，**不静默出表**。
- 类型改判 / MS 版本升级后，导出即时重算，**不落库、不回写正式 ST**（延续 CMC 单一数据源与"模拟值不回写"铁律）。

### 6.3 VA% 双口径（处理"机器时间不参与操作工 VA 率"的冲突）

平台现行口径 `CT = Σ全部有效要素 ST`（含机器自动，其 `RNVA` 为占位）；公司 `VA Template` 单列 `Total Machine` 且机器时间不参与操作工 VA 率。两者都是既有事实，本方案**不改引擎、不改 CT 定义**，而是并列呈现：

| 口径 | 公式 | 用途 |
|---|---|---|
| 全口径（平台现行） | `VA% = VA_s / CT` | 与系统页面、驾驶舱一致，**默认主指标** |
| 操作工口径（公司表单） | `VA%_op = VA_s / (CT − 机器时间)` | 评审 / 与公司历史表单对齐 |

- 两个数都写在 `03` 合计区与 `99_说明`，并在 `00_封面` 只展示主指标（避免管理层看到两个数字困惑）。
- `机器自动` 的 `RNVA` 占位在 `03` 表 `备注` 列标 `机器占位`，防止读者把它当成"可压缩的必要非增值"。

### 6.4 焦点要素规则（"只关注焦点"的可执行定义）

**候选（命中任一即入候选池）**

| 规则 | 条件 | 依据 |
|---|---|---|
| F1 | 命中任一 `waste_triggers`（存在浪费证据） | `analyzeStation.wastes` |
| F2 | `NVA` 且 `std_time ≥ 0.5 s` | 纯浪费且有一定体量 |
| F3 | `std_time ≥ 1.0 s` **或** `占CT% ≥ 3%` | 大体量要素（阈值可配置） |
| F4 | `outlier_flag = 1` | **不进焦点表**，仅在 `02` 表标灰 —— 数据质量问题不等于改善机会 |

**排序与截取**

```
改善潜力 = std_time × factor
  factor = 该要素命中的 ecrsa_map.mappings[].factor 最大值；无命中取 0.3（保守默认）
排序：改善潜力降序 → 占CT% 降序 → 工位编码 + 序号（稳定排序）
截取：每工位 Top5；全任务上限 Top30（弹窗可选 20 / 30 / 50）；不足则全取
输出：04_动作分析 只列这些行；03 表 K 列对命中行标 ★；其余行分析列一律留空
```

- 用 `factor`（收益估算因子）排序是**复用既有规则资产**，不新造评分模型、不引入 LLM 产数字。
- 焦点规则是**导出时的派生视图**，不落库、不修改 `va_class`、不删除任何要素（RNVA 只压不删铁律）。
- 阈值 / TopN 须现场用一条真实产线校准后定默认值（§9 P0-4），本版给出的是**待校准建议值，不是结论**。

### 7.2 性能与容量

| 项 | 设计 |
|---|---|
| 取数 | **两条 SQL**：① `t_task_station JOIN t_station`（按 `task_id + tenant_id`）；② `t_element JOIN t_task_station ts ON e.task_id=ts.task_id AND e.station_id=ts.station_id AND e.bol_version=ts.bol_version`，按 `task_id + station_id IN (…)` 一次取回全部要素，内存分组。**禁止按工位循环 N+1** |
| 分析 | 复用 `analyzeStation` / `buildLineAnalysis` / `buildMotionDetail` 纯函数，规则集一次加载；四类时间与焦点标记在导出层派生 |
| 生成 | `exceljs` 流式 `WorkbookWriter` 直接写 HTTP 响应，不落磁盘、不整本驻留内存 |
| 容量 | 典型 20–50 工位 × 50–150 要素 = 1k–7k 行 / 单表；远低于单 sheet 1,048,576 行上限；**6 张 sheet 固定，无需分卷 ZIP** |
| 上限 | 工位 > 200 **或** 要素 > 100k：返回 400「请拆分任务导出」，不静默截断；单表行数 > 50k 时提示"建议筛选工位" |
| 超时 | 服务端生成目标 < 3s（50 工位）；网关 60s；客户端不设短超时 |
| 并发 | 单用户同时只允许 1 个导出任务（按钮 busy）；不做全局队列 |
| 缓存 | 不缓存，即时计算（现行口径）；新增实体后凡涉及聚合缓存键须带 `task_id` |
| 校验 | 生成前跑 §6.2 三级校验，失败不带病出表 |

### 7.3 权限与安全

- 权限：`element:read`（必需）+ `analysis:read`（可选降级）+ `assertTaskReadable`（租户）+ 每工位 `assertReadable`（资源级 ACL / data_scope）。
- 范围只含**可见工位**；不可见工位不出现在弹窗与文件。
- 聚合类指标（平衡率 / 瓶颈 / ΣVA）在引擎计算**之前**按可见工位过滤，避免"筛了行没筛聚合值"。
- 文件不落盘、无临时 URL；`Cache-Control: no-store`；`Content-Disposition` 按 RFC 5987 输出中文名。
- 审计：可选写 `audit_log`（动作 `export`，对象 `task:{task_no}`，摘要工位数 / 要素数 / 焦点数），见 §9 P2。
- **AI 数据边界**：导出不跨模块合并 AI 浪费证据 / AI 建议全文；`04` 表的浪费与措施只来自 `waste_triggers ∪ ecrsa_map` 规则口径，延续双模块边界铁律。

## 10. 建议的验收标准（实现阶段用）

1. **任务隔离**：同一产线建两个任务、各自导入不同要素；分别导出，两文件的要素集合、`ΣCT`、`Σ四桶` 互不串；跨任务查询不出现对方 `task_id` 的行。
2. **结构固定**：任意工位数（含 0 / 1 / 20 / 50 / 200）导出均为**恰好 6 张 sheet**（关闭 `04` 时 5 张），sheet 名固定、无非法字符、无 `~n` 去重、**不产生分卷 ZIP**。
3. **列数约束**：`02/03` ≤ 12 列、`04` ≤ 9 列、`01` ≤ 14 列；分析单元格文本 ≤24 字；每要素 1 浪费 / 1 ECRS / 1 措施。
4. **口径校验（三级，仅对有效要素）**：逐要素 `E+F+G+H = ST` 且恰一桶有值；逐工位 `Σ四桶 = ΣST = CT`；全任务 `Σ工位CT = 汇总页 ΣCT`，误差均 ≤0.01 s；`VA+RNVA+NVA = CT`；异常要素四桶留空、不计入合计。
5. **四类时间自动判定**：改一个要素的 `type`（如 `走动` → `机器自动`）后重导，F/G 列随之互换且合计不变；在 `#/standard` 修改 `time_bucket` 并发布后，导出按新配置生效；未配置类型回落 `manual` 且在说明页列出。
6. **焦点规则**：`04` 表行数 ≤ TopN 且按改善潜力降序；`03` 表 `★` 与 `04` 表行一一对应；异常要素不出现在 `04` 表。
7. **权限**：无权限工位不出现在弹窗与任何 sheet；无 `analysis:read` 时 `04` 表整体缺失且弹窗有提示；聚合值在过滤后计算。
8. **降级与兼容**：现有单工位 CSV 导出 / 导入回归全绿；批量 XLSX 不可回导（说明页明示）。
9. **版式**：冻结 `B5`、筛选可用、三色 + 文字标签并存、黑白打印可读、中文文件名在 Chrome/Edge 不乱码、Excel 打开无修复提示。
10. **性能**：50 工位 × 100 要素导出 < 5 s；200 工位 / >100k 要素返回 400 且不静默截断。
11. **迁移纪律**：改实体后显跑 `npm run migrate:prod` 并**重启 API**，生产 mssql 真起一次验证无 `DataTypeNotSupportedError` / 列截断；隔离测试通过不作为上线依据。
