# IE改善平台 · 系统架构设计 v3.0（企业级演进版）

> **文档定位**：在 MVP v2.1（单机 SQLite 版）验证了业务闭环之后，本文件面向**上线后的真实环境**重做架构：多用户登录与数据隔离、SQL Server 长期存储、Windows Server 部署、AI Agent 赋能、规则库在线管理。读者：开发（2人）、IT 运维、IE 主管。
>
> **与既有文档的关系**：业务规则口径仍以 `MVP详细设计-00~04` + `MVP系统架构设计.md`（v2.1 落地记录）为准；本文件只改**技术架构与工程组织**，不改任何业务口径（3表16字段、10类要素、6类浪费、12条ECRSA、收益公式全部延续）。
>
> **核心原则**：一步到位选型，避免试点转量产时"推倒重来"；同时不推翻 MVP——Service 层业务逻辑 1:1 平移到新框架（见 §13 迁移路径）。

## 3. 技术选型总表

| 决策点 | 选型 | 理由 | 否决的替代 |
|---|---|---|---|
| 后端框架 | **NestJS 10 + TypeScript** | 模块化/DI/Guard/Interceptor 是权限与多租户场景的行业标准；装饰器式权限声明；OpenAPI 自动生成 | 继续原生 http（无 Guard/DI，权限会散落成 if 森林）；Egg/midway（国内生态但 SQL Server 案例少） |
| ORM | **TypeORM 0.3** | 对 SQL Server 支持最成熟（mssql 驱动）；Repository 模式契合分层纪律；migrations 管理 schema 演进；支持多数据源 | Prisma（SQL Server 连接器有限制、迁移能力弱）；手写 SQL（Schema 演进无版本） |
| SQL Server 驱动 | **mssql**（tedious 纯 JS） | 纯 JS 无本地编译，**Windows Server 零坑**；连接池内置 | tedious 直用（重复造轮子）；ODBC 桥（需装 DSN） |
| 开发/演示库 | **sqlite3**（同一套 Entity） | 无 SQL Server 的开发机也能跑全链路；生产只换 DataSource | 每人都装 SQL Express（环境碎片） |
| 认证 | **JWT：access 15min + refresh 7d（HttpOnly Cookie 或 Header 双模式）** | 无状态水平扩展；refresh 轮换+复用检测 | Session+Redis（多一套基础设施）；JWT 单长 token（泄露窗口大） |
| 密码哈希 | **argon2id**（bcrypt 兜底） | 抗 GPU/ASIC | MD5/SHA256（明令禁止） |
| 权限模型 | **RBAC（user-role-permission 五表）+ 权限点常量表** | 内部系统角色稳定；权限点=细粒度字符串（如 `element:write`）；与数据隔离正交 | ABAC（过度设计）；硬编码 if（无法审计） |
| 多租户 | **共享库 + tenant_id 行级隔离（BaseRepository 强制 + TenantGuard 兜底）** | 租户=事业部/法人实体，数量个位数；运维成本最低；预留 schema 级演进 | 独立库（备份/迁移成本×N）；RLS（DBA 依赖重，先应用层） |
| 队列 | **ai_task 表轮询 worker（SQL Server-backed）** | Windows Server 无 Redis 也能跑；失败可重试、状态可查 | BullMQ+Redis（多一套要运维的基础设施） |
| LLM 接入 | **OpenAI 兼容协议网关**（内网 vLLM / Ollama / Azure OpenAI 可配置切换） | 公司内网可跑开源模型，数据不出内网；协议统一换供应商无感 | 绑定单一厂商 SDK |
| 规则存储 | **t_rule_set（JSON 列）+ 文件双源** | RV1.0 的 4 个 JSON 文件直接入库；在线改规则不用重启；文件兜底保底 | 纯文件（改规则要动服务器）；纯 DB（开发期无库不可跑） |
| 前端 | **保持 Vite 6 + React 19 + TS**，新增登录页/权限路由/axios 刷新 | MVP 前端资产（时间线/SVG 图表）全部保留，增量改造 | 换框架（时间线重写，纯浪费） |
| 部署 | **IIS(ARR 反代+TLS) + PM2 或 NSSM（Windows 服务）** | Windows Server 标准姿势；IT 熟悉 IIS 证书与站点管理 | 直接暴露 Node 端口（无 TLS、无进程守护）；Docker（试点机未装） |
| 日志/监控 | **pino + 文件轮转 + /health /ready + prom-client** | 结构化日志可被 Windows 事件日志/Splunk 采集 | console.log（无法采集） |

## 4. 后端架构（NestJS 模块划分）

### 4.1 模块清单

| 模块 | 职责 | 关键文件 |
|---|---|---|
| `CoreModule` | 配置（env fail-fast）、日志、全局错误过滤器、校验管道 | `core/config`, `core/logger`, `core/all-exceptions.filter`, `core/validation.pipe` |
| `DatabaseModule` | 双 DataSource（SQL Server `prod` / SQLite `dev`），BaseRepository | `core/database/*` |
| `AuthModule` | 登录、刷新、登出、改密、登录锁定策略 | `auth/{auth.service,auth.controller,jwt.strategy}.ts` |
| `RbacModule` | 用户/角色/权限 CRUD、权限点字典、JwtAuthGuard/PermissionsGuard | `rbac/*` |
| `TenantModule` | tenant_id 提取与注入、跨租户访问拦截 | `tenant/tenant.guard.ts, tenant.interceptor.ts` |
| `RulesModule` | 规则集入库/查询/版本/生效切换、DSL 加载与启动自检 | `rules/*`（DSL 从 MVP 平移为 TS） |
| `AiModule` | LLM 网关、ai_task 队列表、worker 轮询、月度 token 熔断 | `ai/*` |
| `AuditModule` | 写操作审计（谁/何时/改了什么），AuditInterceptor | `audit/*` |
| 业务模块 | stations/elements/analysis/suggestions/compare/settings | `modules/*`（MVP Service 逻辑 1:1 平移为 TS） |

### 4.2 请求生命周期（权限+隔离的落地顺序）

```
HTTP 请求
 → 全局 Guards（顺序即执行序）：
    ① JwtAuthGuard   校验 access token，注入 req.user（@Public() 路由跳过）
    ② TenantGuard    校验 user.tenant_id 与路径/头中的 tenant 一致（越权→403）
    ③ PermissionsGuard  @RequirePermission('element:write') 命中校验（缺→403）
 → Interceptors：
    ④ TenantInterceptor Repository 查询自动附加 tenant_id 条件
    ⑤ AuditInterceptor  写操作落 t_audit_log（异步，不阻塞响应）
 → Controller → Service（业务+事务）→ Repository（唯一 SQL 出口）
```

**关键设计**：`@Public()` / `@RequirePermission()` / `@CurrentUser()` 三个装饰器让"谁能动什么"在 Controller 上一眼可读，新增接口默认安全（忘记加权限注解的接口必须在 RbacModule 的"默认拒绝"策略下显式放行）。

### 4.3 MVP 业务逻辑平移映射

| MVP 文件（JS） | v3.0 目标（TS） | 改动 |
|---|---|---|
| `features/stations/service.js` | `modules/stations/stations.service.ts` | 逻辑照搬；SQL 改 TypeORM Repository；封存写守卫不变 |
| `features/elements/{service,validation}.js` | `modules/elements/*.ts` | V1/V2/V3 校验逻辑照搬（纯函数，零改动） |
| `features/analysis/engine.js` | `modules/analysis/analysis.engine.ts` | 照搬；规则来源从"文件"改为 RuleService（DB 优先） |

| `features/compare/service.js` | `modules/compare/*.ts` | 照搬；收益参数从文件改 `settings`（入库） |
| `rules/dsl.js` | `core/rules/dsl.ts` | 照搬（纯函数）；`ts` 化 + 单测 |

### 5.2 索引与大数据量策略（t_element 是增长核心）

| 措施 | 内容 |
|---|---|
| 复合索引 | `idx_element_tenant_ver (tenant_id, station_id, bol_version)` 覆盖 95% 查询 |
| 唯一约束 | `UQ (tenant_id, station_id, bol_version, seq)`（从旧 UK 加租户维度） |
| 分区准备 | `created_at` 分区函数（按月），**上线时建分区表**（t_element 预估 10 行/工位/版本 × 数百工位 × 年度版本 ≈ 百万行/年级，分区可平滑支撑到千万级） |
| 归档 | 冷版本（封存>180 天且非最近 3 版）可移 `t_element_archive`（同结构，报表不查）；归档脚本月度跑 |
| 统计信息 | SQL Server 自动更新 + 重建索引维护计划（每周） |
| 连接池 | mssql pool：min 2 / max 20 / idleTimeout 30s（2 人并发远低于此，留余量给报表查询） |

### 5.3 Schema 演进与数据迁移

- **迁移工具**：TypeORM migrations（`synchronize=false` 生产强制）；每个迁移一个 `up/down`，纳入 git。
- **MVP 数据搬迁**：一次性 ETL 脚本 `scripts/etl-sqlite-to-mssql.ts`：读 SQLite → 批量 INSERT SQL Server（每批 500 行事务），`tenant_id='DEFAULT'`，`created_by='seed'`，`bol_version/version` 原样保留；跑完输出对账报告（行数/CT 合计比对）。
- **备份**（SQL Server 维护计划，替代"复制文件"）：每日 00:30 完整备份 + 每 15 分钟事务日志备份 + 每小时差异；备份文件异地副本；恢复演练每季度一次（RPO≤15min，RTO≤2h）。

### 5.4 DDL 风格约定（SQL Server）

- 一律 `NVARCHAR`（中文安全）；JSON 存 `NVARCHAR(MAX)`（不依赖 SQL Server 2016+ JSON 函数，保持应用层解析一致）。
- 金额/时长：`DECIMAL(10,2)`；时间：`DATETIME2(0)`（无毫秒噪声）；所有表带 `created_at DATETIME2 DEFAULT SYSUTCDATETIME()`。
- 迁移脚本先附 SQLite 兼容版（开发用同一 Entity 双跑）。

## 6. 认证与会话管理（AuthModule）

### 6.1 流程

```
登录：POST /api/auth/login {username,password}
 → argon2 校验 → 失败计数(5次锁15min) → 成功签发：
    access (15min, payload: sub/username/tenant_id/roles)
    refresh (7d, HttpOnly Cookie + body 双发, 落 t_refresh_token 哈希)
调用：Header Authorization: Bearer <access>
401 且 token 过期 → 前端静默 POST /api/auth/refresh（Cookie 自动带）→ 轮换：
    旧 refresh 标记 revoked+replaced_by=新 → 重放旧 token=全族吊销（偷窃检测）
登出：revoke 当前 refresh 族
```

### 6.2 关键规则

| 规则 | 值 |
|---|---|
| access token 有效期 | 15 分钟（payload 只放身份，不放权限——权限实时查库，禁用变更即时生效） |
| refresh 轮换 | 每次刷新换发；`replaced_by` 链式；重放检测命中→邮件/日志告警 |
| 密码策略 | 8 位以上，含字母数字；argon2id(memory=64MB, t=3, p=4)；首次登录强制改密 |
| 登录锁定 | 同用户连续失败 5 次 → `locked_until=now+15min`；审计日志记录 IP |

## 7. 角色与权限（RbacModule）

### 7.1 角色定义（种子）

| 角色 code | 名称 | 权限范围 |
|---|---|---|
| `sys_admin` | 系统管理员 | 全部 + 用户/角色管理 + 规则管理（**不分配业务数据所有权**） |
| `ie_admin` | IE 主管 | 全线数据读写、复测、对比、收益参数、规则查看 |
| `ie_engineer` | IE 工程师 | 工位/分解/分析/建议采纳、对比查看 |
| `line_leader` | 产线班长 | 本线查看、建议执行状态更新 |
| `viewer` | 只读 | 查看 |

### 7.2 权限点字典（≈22 条，`module:action`）

```
station:read  station:write  station:retest
element:read  element:write  element:va-override
analysis:read analysis:run
suggestion:generate suggestion:adopt suggestion:status
compare:read   compare:export
settings:benefit-write
rule:read  rule:write
user:read   user:write   role:write
audit:read
ai:use
```

### 7.3 授权判定链

```
@RequirePermission('element:write')  → PermissionsGuard:
  1. user.status=active? 否则 403
  2. roles → role_permissions → permission.code 命中? 否则 403
  3. （租户内）资源级校验在 Service：如 line_leader 仅限 line_id∈管辖线
```

资源级（行级）约束放 Service（`assertCanAccessStation(user, station)`），权限点（操作级）放 Guard——**两级分离**，避免 Guard 里塞业务查询。

## 8. 多租户数据隔离（TenantModule）

### 8.1 策略定稿

| 维度 | 决策 |
|---|---|
| 隔离级别 | **行级隔离**（共享库 + `tenant_id` 列）——租户为个位数，独立库运维成本不划算 |
| 强制手段 | ① `TenantGuard`：token 租户 ≠ 请求租户 → 403；② `BaseRepository`：所有 find/insert/update 自动附加 `tenant_id = ctx`，漏写即编译期可见（泛型约束）；③ 每条迁移给业务表加 `tenant_id NOT NULL DEFAULT 'DEFAULT'` |
| 兜底 | 集成测试：用户 A 永远查不到 B 的工位/要素/建议（`tenant-isolation.e2e.ts` 强制 6 组断言） |
| 跨租户 | 无此需求（平台=公司内网单组织）；预留 `t_tenant` 表支持未来收购/分厂 |

### 8.2 用户与租户的关系

一个用户只属一个租户（1:N）；`sys_admin` 也绑定租户（系统管理员=本租户管理员）。角色按租户隔离（`t_role.tenant_id`），系统角色 `is_system=1` 不可改权限集。

## 9. AI Agent 架构（AiModule）

### 9.1 设计边界（三条铁律的架构落地）

| 铁律 | 架构机制 |
|---|---|
| AI 只建议不执行 | LLM 输出只进 `ai_task.output_json` + 前端展示；`t_improvement` 仍必须 IE 点"采纳"才写 |
| 数字由规则算、LLM 不产数字 | `AiGuardService`：LLM 输出若含数字且任务类型=建议润色 → 正则校验失败即**丢弃回退模板**；est_save_s/priority 永远来自规则引擎 |
| 可关可降级 | 默认 `AI_ENABLED=false`；月度 token 熔断（默认 200K token/月）；失败/超时自动降级为本地模板文案 |

### 9.2 组件

```
AiController（提交任务/查状态）
  → AiTaskService（写 t_ai_task:pending；返回 task_id 立即响应）
  → AiWorkerService（@Interval 5s 轮询 pending → 串行执行 → 回写）
      → LlmGatewayService（OpenAI 兼容协议：baseURL+key+model 可配置）
          提供商：内网 vLLM/Ollama（默认推荐，数据不出内网）| Azure OpenAI | 公网 API
      → OutputSanitizer（禁数字校验 / 长度截断 / 模板回退）
  → CircuitBreaker（连续失败 5 次 → open 10 分钟 → half-open 探测）
```

### 9.3 任务类型（MVP→v3.0 路线）

| type | 状态 | 说明 |
|---|---|---|
| `suggestion_polish` | **v3.0 启用** | 输入=结构化建议卡 JSON（element_ids/waste_type/est_save_s…），输出=`measure` 文案润色 ≤200 字；数字字段走 OutputSanitizer |
| `analysis_summary` | 规划 | 分析结论自然语言摘要（只读，不改数据） |
| `case_retrieve`(RAG) | 闸门后 | 案例≥30 条才做（7.2 闸门），届时向量库独立部署 |

### 9.4 成本与配额

- 月度 token 上限配置化（默认 200K）；`ai_task.tokens_used` 逐条累计；超限→新任务直接 `failed(quota_exceeded)`，前端提示"本月 AI 额度已用完"。
- 超时 30s、重试 2 次（指数退避）；任务保留 90 天。

## 10. 规则引擎与规则库（RulesModule）

### 10.1 双源加载（兼容优先）

```
启动：loadRules()
  ① DB 源：t_rule_set WHERE is_active=1（按 code 取 4+1 条）
  ② 文件源：config/rules/*.json（RV1.0，MVP 资产，开发/演示兜底）

  自检：10 类要素齐全、全部 DSL 表达式可编译 → 否则拒绝启动
```

### 10.2 规则管理（新页面，ie_admin/rule:write）

- 页面：规则集列表（code/版本/生效时间/发布人）→ 编辑 JSON（带 DSL 语法校验+试运行：对某个工位当前版本试算，显示会命中哪些要素）→ 发布（新版本+切换）→ 可回滚上一版。
- 版本规则延续 RV 语义：`RV{major}.{minor}`，W8 冻结动作变为"数据库里锁定 `is_frozen` 标记"而非锁文件。

### 10.3 DSL 兼容

MVP 的 `dsl.js`（比较/AND/OR/NOT/括号/正则 `~=`/内置函数）原样平移为 `dsl.ts`，**语法零变化**——现有 4 个 JSON 文件可原样导入 t_rule_set，规则作者无学习成本。
