1. 为什么"产线驾驶舱"现在是空的三层根因

驾驶舱看起来空，不是前端渲染故障，而是数据、模型、表现三个层面都只有"一条线"的格局。实测数据（CN_AME 库，2026-10-22）：

#层面事实（实测）后果
1数据层 全系统 34 个工位：DEFAULT 租户 33 个全部在 L01 一条线；OTHER 租户仅 1 个（隔离验证用） 没有第二条真实产线，"驾驶舱"无线可驾驶
2模型层 工位只有 tenant_id + line_id 两个归属字段；t_tenant 无区域属性；产线只是字符串编码（无名称/工艺/产品元数据）；改善任务无项目类型 区域 / 工艺 / 产品 / 项目类型四个维度在数据里根本不存在，无法分类展示
3表现层 首页 = L01 的 33 张工位卡片平铺；公司（租户）维度在 UI 完全不可见；没有任何跨线/跨公司的汇总视角 用户看到的是"一个很长的工位列表"，而不是"驾驶舱"——没有汇总、没有对比、没有下钻
结论：驾驶舱空的根因是系统只有"一条线一个公司"的种子数据 + 缺少四个业务维度。要满足"跨公司、跨工艺、跨产品、按区域/公司/产线/项目类型分类展示"的定位，必须：①补维度模型；②补演示数据；③把首页从"工位列表"升级为"多维综合驾驶舱"。

2. 需求解读这个系统到底是什么

用户原话："这个视同是一个跨公司、跨工艺过程的综合系统，兼容不同公司、不同工艺类型、不同产品的工作任务，并能按区域、公司、产线、项目类型等进行分类展示综合结果。"

本质解读：这不是"一个工厂的 IE 工具"，而是集团级 IE 改善运营平台——一次部署服务多家公司（工厂/事业部），每条产线有工艺类型与产品属性，每项改善任务归属项目类型；管理层与 IE 团队需要一个能按任意维度切片、能逐层下钻的驾驶舱。

2.1 六维度模型

把需求中的名词收敛为六个维度，分两类——层级维度（地理/组织归属，用于逐层下钻）与属性维度（业务分类，用于切片筛选）：

维度类型含义示例值落点（数据实体）
区域层级工厂所在地理大区，跨公司汇总华东 / 华南 / 华北t_tenant.region（公司字段，推荐，见 D1）
公司层级法人/事业部/工厂，数据隔离边界本部 / 苏州精密 / 深圳智造t_tenant（已存在，复用）
产线层级物理产线，工位的直接父级L01 装配一线t_line（新建）
工艺类型属性产线的工艺过程分类装配 / 注塑 / 冲压 / SMT / 焊接 / 包装t_line.process_type
产品属性产线生产的产品（类型 + 项目编号双属性，用户确认）类型：电机/控制板/连接器；编号：P-2026-018t_line.product_type + t_line.product_project
项目类型属性改善任务所属项目分类NPI导入 / 量产改善 / 自动化改造 / 布局优化 / 质量改善t_improvement.project_type

2.2 维度层级图

集团视图（跨公司，需 group:read 权限） ├─ 区域（华东 / 华南 / 华北） ← GROUP BY t_tenant.region │ └─ 公司（t_tenant，数据隔离边界） ← GROUP BY tenant_id │ └─ 产线（t_line，新表） ← 工艺类型 · 产品 · 工位数 · 平衡率 │ └─ 工位（t_station，已存在） ← CT/TT/VA/版本 │ └─ 要素（t_element） └─ 改善任务（t_improvement）按 项目类型 切片 ← GROUP BY project_type （任务同时归属工位→产线→公司→区域，可任意维度交叉）

3. 数据模型变更最小增量，存量安全回填

遵循 MVP"薄"哲学：不建规范维度表，不加配置界面，只用 3 处字段/表增量承载全部六个维度。所有变更进 scripts/migrate.ts（表结构唯一事实来源），幂等可重复执行。

#变更DDL 要点存量回填
1t_tenant 增列 region ALTER TABLE t_tenant ADD region NVARCHAR(32) NOT NULL DEFAULT '总部' DEFAULT → '总部'；OTHER → '测试区'
2新建 t_line 产线表 line_id PK / tenant_id FK_t_tenant / name / process_type NVARCHAR(32) / product_type NVARCHAR(64) / product_project NVARCHAR(64) / created_at；约束 FK_line_tenant INSERT … SELECT DISTINCT line_id, tenant_id FROM t_station（L01→装配/电机/P-2025-001；L02→装配/隔离验证/—）
3t_improvement 增列 project_type ALTER TABLE t_improvement ADD project_type NVARCHAR(32) NOT NULL DEFAULT '量产改善' 存量 25 条建议 → '量产改善'
为什么不建 t_region / t_process_type 字典表：区域值是稳定的少数枚举（华东/华南/华北），工艺与项目类型由 IE 团队约定后写入，前端用受控下拉（硬编码枚举 + 预留扩展）。字典表 + 维护界面是"帮管理层管住 IE"的功能，按产品哲学延后。二期若需自定义，加表即可，数据不丢。

3.1 产线成为一等实体后的连带简化

  • 工位清单页的"选线下拉"改为读 t_line（带名称/工艺/产品），不再从工位反推——多公司时反推会串味
  • GET /lines/:lineId/analysis 响应 enrich：附带 line_name / process_type / product / region / company（现有计算口径零变化）
  • 新建工位时 line_id 从对象树带入（已是现为），新增产线由建工位时顺带创建 t_line 记录（line_id 不存在则插入，默认工艺'装配'）——一期不单独做"产线管理"页

5.1 设计要点

  • 筛选条置顶、全卡联动：区域/公司/工艺/产品类型/项目类型五个下拉改变后，KPI、五张分布、产线汇总表全部重算——这就是"按维度分类展示综合结果"的交互落点
  • 分布卡即可视化按钮：点"华南"行 = 加区域筛选；点"注塑"= 加工艺筛选；点公司行 = 加公司筛选并更新面包屑——没有独立下钻页，下钻即筛选

  • 空态分级：无任何数据 → 三步引导（建公司数据/导演示/看帮助）；有数据但筛选为空 → "该组合暂无数据，重置筛选"

5.2 L4 改善任务清单页（从工位清单底部抽出）

现有建议表嵌在工位清单页底部，只能看一条线。独立为 #/improvements 后支持跨产线、跨公司浏览：筛选 = 公司 / 区域 / 工艺 / 项目类型 / 状态；表格增加"项目类型"列；三态流转（待实施→已完成→已验证）交互不变；导出 CSV 带全部筛选条件。工位清单页底部只保留"本线建议"摘要 + 跳转链接。

6. 跨公司可见性与数据隔离安全边界

铁律不变：跨公司视图只含聚合指标（计数/均值/汇总），绝不包含工位要素明细；任何下钻到工位级数据的请求，仍走现有租户隔离 Guard（越权返回空/404，与"他租户读建议→空"行为一致）。
场景规则
新增权限点 group:read种子角色：sys_admin / ie_admin 授予；ie_engineer / line_leader / viewer 不授予（二期按需开放公司级）

11. 待确认决策项D1–D4，影响实施细节

D1 · 区域维度挂在哪一层？ 已确认：挂公司

区域存 t_tenant.region，按区域汇总 = GROUP BY 公司区域，一条 SQL 最简，符合"工厂在某区域其产线就在该区域"的现实模型。

D2 · 登录后首页默认落哪？ 已确认：落集团综合驾驶舱

有 group:read 的用户（sys_admin / ie_admin）登录默认落 #/dashboard；无权限用户落产线驾驶舱 #/stations。

D3 · 演示数据何时灌入？ 已确认：立即灌入

迭代 1 完成后立即执行 SEED_DEMO=true：3 区域 / 4 公司 / 12 产线 / 68 工位 / ~35 建议，固定随机种子可复现，提供一键清理。

D4 · 产品维度做到多深？ 已确认：产品类型 + 产品项目编号

用户指定产品维度为两个属性：product_type（产品类型，如 电机/控制板/连接器）+ product_project（产品项目编号，如 P-2026-018）。两条产线字段承载，驾驶舱支持按产品类型筛选、汇总表显示项目编号——比单产品字段更贴近制造业"类型归类 + 项目追溯"的实际用法。
