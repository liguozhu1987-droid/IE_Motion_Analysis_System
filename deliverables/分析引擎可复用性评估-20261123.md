# 分析引擎可复用性评估（旧引擎 → 新引擎合并建议）

> 日期：2026-11-23　性质：代码+规则只读评估，无代码改动
> 对象：现有确定性分析引擎与规则集 —— `analysis/engine.ts`、`suggestions/engine.ts`、`ai-suggest/validator+calculator`、`ai-waste/validator`，以及 `va_rules / waste_triggers / ecrsa_map / redline_keywords` 规则集。
> 结论一句话：**旧分析引擎的确定性内核是系统里最专业、最值得整体保留的部分；新引擎应该是“在它外面套一层方法链 + 闭环”，而不是重写或替换它。**

---

## 1. 现有“分析引擎”实际由四块组成

| # | 能力 | 代码 | 规则集 |
|---|---|---|---|
| A | 增值/非增值判定 | `analysis/engine.ts:classifyElements` | `va_rules`（RV3.64） |
| B | 浪费识别（确定性） | `analysis/engine.ts:detectWastes` | `waste_triggers`（RV1.4） |
| C | 措施制定（规则候选） | `suggestions/engine.ts:buildCandidates` | `ecrsa_map`（RV1.1）+ `redline_keywords` |
| D | 措施/浪费（LLM + 数字回算） | `ai-suggest`、`ai-waste` 的 validator/calculator | 同类规则 + 提示词 |

---

## 2. 逐块评估

### A. 增值/非增值判定 —— 专业，整体保留

**怎么算的（三级优先）**
1. 人工标记优先：`desc` 含 `[VA改判]` / `[VA确认]` → 跳过自动归类，`confidence=human`。
2. 规则例外：每类的 `exceptions[].when` DSL 首个命中，产出 `va_effective / va_confidence / va_reason / rule_id`。
3. 类型默认：`type → default VA|RNVA|NVA`，`confidence=high`。
4. 低置信进 `pending` 待人工确认；异常要素独立出 `outliers`。

**专业在哪**
- 判定结论都带 `rule_id` + `confidence` + `reason`，可追溯、可审计。
- `va_rules` 已并入公司《VA N-VA Definition》22 类，并有 RV3.63/RV3.64 两轮 IE 勘误（检查统一 RNVA、操作族按对象条件改判、返检归 NVA）。
- “观测值 + 方法层 + 置信分层 + 人工兜底”正是 MTM 与经典 IE 的标准立场（deep research 已佐证其方向）。

**唯一要注意的口径点（非缺陷）**
- 默认把伸手/握取/移物/放手归 VA，属“动素三分法”对企业口径的约定；规则里已用例外与注释覆盖争议场景，本质是**可配置口径**，不是算法问题。

**结论：`classifyElements` 纯函数 + 规则注入 + 人工标记机制，全部带入新引擎。** 新引擎只加一件事：按 `element_source` 过滤（阶段 0 已落地），并把每要素的 `rule_id/va_reason/confidence` 一并写进 Case 溯源。

---

### B. 浪费识别（规则触发）—— 专业，保留为确定性基线

**怎么算的**
- 元素级 `when` 谓词 DSL（`type=持住 AND dur_s>2`）；工位级 `agg`（filter + sum/ratioOf CT/count + op + value）。
- `evidence` 模板插值：`dur_s / element_id / pct / count / sum`。
- `same_desc_count` 做“同对象计数”，并有 `NOT desc~=裸动词` 防误判（RV1.3 实测修复）。
- `basis` 字段分流证据等级：【既有】=确定性锚点计收益、【建议】=待现场标定、route=pool 不计收益（RV1.4 / v3.57 route）。

**专业在哪**
- 把“浪费”规则化、带证据、带阈值、带证据等级；这是**可审计的确定性锚点**，是 LLM 无法替代的部分。
- 已经内置“未被标定就不计收益”的诚实护栏（动作浪费 basis=建议）。

**弱项（需在合并时补齐）**
- 阈值（5% / 8% / 10% / 15%、>6 次等）是经验值，缺系统标定来源。
- `basis=建议` 的高价值项（走动/转身/弯腰）只展示、不计值，尚未形成“待标定→回填→升既有”的闭环。

**结论：保留 `detectWastes` 作为唯一规则浪费来源。** 新引擎里：
- 每条浪费带 `trigger_id` + `basis` + `route`，作为 Case 的“浪费依据”。
- LLM 浪费识别降级为“在规则浪费之上的语义证据补充”，`waste_type` 必须 ∈ **由规则动态生成的 whitelist**，禁止自造分类名 —— 顺带根治当前 AI 建议提示词与白名单不一致导致的静默丢弃。
- 把阈值/basis 与 `actual_save_s` 回填联动：实测数据反哺“待标定→既有”。

### C. 建议措施制定 —— 有专业骨架，需要统一与补强

**规则候选（`suggestions/engine.ts:buildCandidates`）怎么算**
- 输入 `analysis.wastes` × `ecrsa_map.mappings`（waste → method/measure/factor/difficulty/note）。
- `involvedStd` = 证据涉及要素 `std_time` 合计 → `est_save_s = involvedStd × factor`。
- 检验冗余无映射 → 追加人工评估项（0.5 折算）；定位专项 M06/M09。
- `priority = est_save_s × 日频次 ÷ difficulty`，批内归一化，P1≥60 / P2≥30 / P3<30。
- 红线 `checkRedlines`：质量（检验冗余 + 取消/弱化关键词）、人因（弯腰/扭转/高举…），确认后放行，标记写回 `measure` 留痕。

**LLM 建议/浪费（`ai-suggest` / `ai-waste`）怎么算**
- LLM 只产出语义（waste_type、method、factor、measure、ecrs、suggestion）。
- 数字全部回服务端：`est_save_s`（E 全额 / 其余 × factor）、`priority/tier`、`annual_yuan`。这是“LLM 不产数字”铁律的专业落地。

**专业在哪**
- ECRS 映射把“浪费 → 手法 → 措施模板 → 难度 → 折算系数”结构化，factor 用于收益折算而不是拍脑袋。
- 品质 + 人因两道红线，是制造场景里稀缺的安全网关。
- LLM 数字剥离 + 三轮校验（R1–R3 / W1–W3）+ `validation_trace` 落库，质量治理意识在线。

**不专业 / 需整改之处（正好是阶段 1 要干的）**
1. **三套评分公式并存**：规则建议 P1≥60、AI 建议同公式但红线封顶、浪费识别 P1≥40（占 CT 归一化）——同一列 `priority` 三义。
2. `ecrsa_map` 的 factor 标注“经验初值，W7 校准、W8 冻结”，但**没有用实际节省反哺校准**。
3. 缺 **5W1H** 与 **动作经济原则**。
4. 规则候选不落库、拒绝不汇总，无法学。
5. AI 建议提示词的分类名（等待延迟/返工重做/过度加工·检验冗余/预对·定位浪费）与动态白名单不一致 → R1.2 静默丢弃。

**结论：保留 ECRS 映射与红线，规则资产原样带入；把“三套算法”收敛为“一个”。**

## 3. 合并到新引擎的做法（而不是替换）

目标：新分析引擎 = **确定性内核（旧强模块）+ 方法链补全 + 统一契约**。

| 旧引擎资产 | 处置 | 说明 |
|---|---|---|
| `classifyElements` 三级判定 | ✅ 整体保留 | 加 `source` 过滤；`rule_id/confidence/reason` 写入 Case 溯源 |
| `detectWastes` 规则触发 | ✅ 保留为唯一确定性浪费源 | 带 `trigger_id/basis/route`；LLM 只在之上补语义 |
| `ecrsa_map`（12+3 条映射） | ✅ 保留为唯一 ECRS 源 | 作为措施生成的规则层 |
| `redline_keywords`（品质 + 人因） | ✅ 保留 | 扩展到 Case 审核前统一执行 |
| LLM 数字剥离 + validator 枚举校验 | ✅ 保留 | 金额/priority 改走统一 ScoringService |
| `buildCandidates` 的收益/优先算法 | ⚠️ 收敛 | 抽成唯一 `ScoringService`；删除 ai-waste `scoreIssues` 与 ai-suggest 重复折算 |
| 三张机会表（suggestion/waste/规则候选） | ⚠️ 收敛 | 统一为 Case 契约，`producer` 只作溯源标签，不影响评分 |
| 5W1H / 动作经济 / actual_save_s / R1–R8 / eval | ➕ 新增 | 阶段 1 补全（见最小架构文档） |

**新引擎内部的分工（单一方向）**

```
Element(snapshot, source)
  → classifyElements（规则 VA，保留三级判定 + rule_id)
  → detectWastes（规则浪费，trigger_id + evidence + basis）
  → 5W1H（对每条规则浪费做 Why/What/Where/When/Who/How）       —— 新增
  → ECRS(ecrsa_map) + 动作经济(MEn) → measure 候选               —— 保留+新增
  → ScoringService（唯一算 est_save_s / priority / annual）       —— 收敛
  → ImprovementCase（producer 标签 + 全链路溯源）                 —— 统一
```

**校准闭环（把“专业性”从静态提到动态）**
- `actual_save_s` 与复测 ΔCT 回填后，反哺三处：
  1. `ecrsa_map.factor`（E 全额 / 其余折算系数）用实测达成率重标定；
  2. `waste_triggers.basis`：动作浪费“建议→既有”按现场标定推进；
  3. 高频拒绝原因反哺提示词负样本与规则阈值（衰减 + 上限 + 留出集，沿用 deep research 护栏结论）。

---

## 4. 最终判断

| 模块 | 是否专业 | 能否引用到新引擎 |
|---|---|---|
| 增值/非增值判定 | **专业**（三级优先 + 置信分层 + 可追溯） | 整体保留，只加 source 过滤 |
| 规则浪费识别 | **专业**（证据 + 阈值 + 证据等级） | 保留为确定性基线，LLM 降为语义补充 |
| 措施制定（规则映射 + 红线） | **有专业骨架**（ECRS + 折算 + 红线 + LLM 不产数字） | 保留规则资产；三套算法收敛为一套 |
| 缺口（5W1H / 动作经济 / 实际节省 / 结构化反馈） | — | 阶段 1 补全 |

一句话：**不是把旧引擎替换掉，而是把它作为确定性核心里子，套上“5W1H → ECRS/动作经济 → Case → 审核 → 实施 → 实际节省”的外壳；同时把三套并行的评分/候选收敛成一个 ScoringService + 一个 Case 契约。**
