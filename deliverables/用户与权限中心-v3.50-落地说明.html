一、行业报告给出的标尺与本系统改前差距

行业报告的共性骨架是「五层 + 一柱」，其中贯穿柱第一条就是 权限 / 角色 / 租户隔离，第二条是审计日志（输入与更改全记录）， 并明确写入「方法认证（MTM / Blue Card）：分级认证、有效期 4 年、复训与再认证—— 把人的因素纳入体系，跨分析员一致性靠制度而非靠工具」。 报告结论原话：这一柱的厚薄，决定了「数据能否被审计、被复用、被信任」。

二、改造成果：四个能力面

① 人员

  • 建号即带档案：部门 / 岗位 / 工号 / 数据范围 / 方法资质（等级 + 有效期）
  • 列表新增部门、数据范围、资质三列；按部门筛选；搜索覆盖工号与岗位
  • 「档案」弹窗可单独维护，与停启用、口令处置互不干扰
  • 保留原有：注册审批、代置临时口令、下发重置码、停用即吊销会话

② 角色

  • 系统角色（5 个，蓝标）不可删除、不可改名，可改说明
  • 自定义角色可新建 / 改名 / 改说明 / 删权限 / 删除（有成员不可删）
  • 种子内置示例角色 quality_auditor（质量审核员）演示「按岗位建角色」
  • 每个角色显示成员数，删除前必须先解除授权

③ 权限分配

  • 权限点字典按 11 个模块分组，勾选即全量提交（含模块全选/取消）
  • 用户侧：单人角色维护 + 多选批量授权（替换 / 追加两种模式）
  • 「生效权限」弹窗按角色展开并给出并集——授权前先回答「他现在能干什么」
  • 权限改完即时失效相关成员缓存（30s → 0s），不等过期

④ 追溯

  • 13 类 RBAC 动作全留痕：建号 / 改资料 / 改角色 / 批量授权 / 审批 / 建角色 / 改权限 / 删角色 …
  • 审计含改前 / 改后 JSON、操作人、来源 IP、时间
  • 前端「变更审计」页签，audit:read 可见

三、安全保护规则（写进服务端，不靠前端自觉）

  • 防锁死：sys_admin 的 user:read / user:write / role:read / role:write 为强制保留项，即使矩阵里全部取消勾选，服务端也会补回——避免「改完权限全站没人能再改权限」。
  • 自我保护：批量授权时若目标包含操作者本人且新角色不含 sys_admin，该账号被跳过并计入 skipped，管理员不会把自己改下线。
  • 删除保护：系统角色不可删；仍有成员的角色不可删（返回 400 并提示人数）。
  • 白名单校验：角色 code 小写字母开头 2–24 位且租户内唯一；权限点必须存在于字典；data_scope 与资质等级走枚举。
  • 安全默认：所有新端点显式声明 @RequirePermission，未声明的路由被全局守卫直接 403。
  • 越权拦截：IE 工程师（无 role:read）访问 /admin/roles 与改权限接口均返回 403（已回归覆盖）。

六、未验证项与已知限制（如实披露）

  • UI 未做真机点击验证：本轮仅完成类型检查、生产构建与 API 层回归，页面交互（矩阵勾选、批量授权弹窗）尚未用浏览器逐项点过，建议人工在 #/admin-users 三页签各走一遍。
  • data_scope 目前是「标注 + 排序/提醒」态：字段已落库并在界面可选，但尚未接入工位/要素查询的行级过滤；接入前不影响现有 ACL（owner / 协作者）行为。
  • 方法资质仅提醒不阻断：资质过期在列表红标提示，不做登录或提交拦截；是否要「无 L2 不得签发标准时间」属于管理制度，需人工决策后再上规则。
  • 租户范围：与原有用户管理一致，仅覆盖 DEFAULT 租户；多租户开通时角色与权限需按租户复制。
  • dashboard 集团视图越权（v3.42 遗留：viewer/他租户应 403 实 200）不在本轮范围，仍待修。
  • 行业对标部分为桌面调研结论（未做实机基准对比），资质分级借鉴 MTM Blue Card / MOST 认证体系，具体等级定义需结合本厂实际校准。
