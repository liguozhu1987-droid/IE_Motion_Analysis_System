## 0. 一句话定位（先纠正认知）

**「AI 自动分解」不是一个 AI 模型，而是一套跑在浏览器里的确定性规则算法**：
帧差运动能量（默认）或 MediaPipe 手部关键点（可选）→ 启发式切点 → 手写阈值分类 → 产出候选草稿。
它**只产候选、不落库**；人工勾选确认后才经 `submitElements(source='ai_assisted')` 写入新版本。
后端**没有任何分解推理**，只提供素材（上传/转码/派生/场景切分/私有读）与落库通道。

- 算法主入口：`app/web/src/ai-segment/motion.ts:174`（`analyzeMotion`）、`segmentation.ts:146`（`analyzeVideo`）。
- 页面分流：`AiSegmentPage.tsx:626` — `detector === 'hand' ? analyzeVideo(v) : analyzeMotion(v)`。
- 铁律原文：`ai-segment/types.ts:1-4`「候选只是草稿，永不直接写入 draft / start_ms」。
- 后端反证：`ai.controller.ts:38-57` 只有 `polish / tasks / usage / status`，**无 segment 端点**；
  `ai-task.service.ts:102-116` worker 只认 `suggestion_polish`；`ai-usage.service.ts:47` 的 feature 集合
  只有 `waste_analysis / improvement_suggestion`，**无 `ai_segment` 维度**。

### 4.1 关键缺陷展开：落库时间与视频脱钩（P0 候选）

`AiSegmentPage.tsx:661/665/670` 的 `cursor` 逻辑把入选候选按序重排为 `0, dur1, dur1+dur2, ...`；
`:693` 又写死 `video_id: 'ai-segment'`。后果：
- 导出 JSON 里**有**真实 `start_ms/end_ms`（`:778-783`），落库后**丢了**；
- 「点数字跳源帧」对 AI 写入的要素不成立（工作台按 `video_id` + `start_ms` 定位）；
- 审计链断裂：无法从要素回指到原视频的哪一帧。

**修法方向（零 DDL，两个字段都存在）**：落库时改用 `r.start_ms` 原值、`video_id` 用真实视频名
（`videoFrom==='server'` 用 uuid.mp4，本地文件需先上传或显式留空并标注）。
**注意**：改后会触发真实的时间重叠校验 `validation.ts:116-131`（V2 FAIL）——这是**正确暴露**历史候选重叠，
不是新缺陷；须在导入前做重叠处理/人工合并，不能直接放宽校验。此改动涉及业务口径，需先确认。

## 5. 优化改善建议（按产品哲学排序）

> 哲学约束：工具做薄（帮 IE 看出问题＝留，帮管理层管住 IE＝砍）；主线「人拆 AI 校」；
> 零 DDL 优先、成本敏感；三层 AI（规则引擎禁产数字）、AI 建议永远待审。
> 质量总闸门：**QA No-Go**，0a✅ / 0b✅ / 0c⛔（缺人工真值，见 §1.4）。

### P0 — 正确性与可辩护性（建议优先，全部零 DDL）

1. **修复落库时间/视频脱钩**（§4.1）：`start_ms` 用候选原值、`video_id` 用真实来源。
   这是「人拆 AI 校」闭环的审计前提；改前先确认重叠处理策略。
2. **证据帧走精确帧基准**：复用 `useVideoEngine.snapToFrameGrid` + `metadata.mediaTime`，
   去掉 `+80/-80ms` 经验偏移，判合格＝0 帧偏差（与工作台 P0-2 判据一致）。
3. **修 `confAdj` 死字段**：要么让类型置信真正参与分档（需口径确认），要么删掉，避免误读。
4. **把 motion 分类阈值配置化**：现硬编码 `motion.ts:73-87`，与「规则集单一来源」背离。
   注意纪律：改 JSON 不生效，须 `POST /rules/:code/publish`（`rules.service.ts:129-145`）。

### P1 — 效率提升（复用现有地基，低成本）
