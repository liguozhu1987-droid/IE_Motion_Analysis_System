# 权限配置审计报告：IE 工程师为何能看到全集团数据

- **审计日期**：2026-10-28
- **审计对象**：IE 改善效率平台 RBAC + ACL 双层权限体系
- **触发问题**：用户反馈"以 IE 工程师角色进入系统后，仍能看到左侧集团视图下各工厂/产线/工位的分析结果，甚至能进入示例装配线做分解"
- **审计方式**：黑盒实测（3 个真实角色账号 × 30+ 端点）+ 源码走查（全部 17 个 controller）
- **结论**：**权限配置不合理，存在系统级越权**。详见第 3 节。

---

## 1. 结论摘要（一句话）

> 当前平台只有 **RBAC（角色能干什么）** 和 **租户隔离（跨公司隔离）** 两层，
> **缺少"用户级数据范围（我能看谁的）"这一层**。
> v3.42 建立的个人工作台 ACL（owner/协作/共享）**只接在了 4 个写端点上，所有读端点全部绕过**，
> 因此任何同租户用户都能看到全租户所有工位的分析结果。

严重度分级：

| 编号 | 问题 | 严重度 | 类型 |
|---|---|---|---|
| P0-1 | 全部读端点（要素/分析/产线/看板）不校验工位归属 | **高** | 越权读 |
| P0-2 | `group:read` 权限点被授予全部 5 个角色，IE 工程师登录即落集团视图 | **高** | 权限设计错误 |
| P1-1 | 改善任务状态流转无归属校验，可改他人任务状态 | **中** | 越权写 |
| P1-2 | 候选建议生成无归属校验，可对他人工位跑分析 | **中** | 越权写/算力盗用 |
| P1-3 | `data_scope`（仅本人/本产线/本租户/全集团）字段建了但未接入任何过滤逻辑 | **中** | 功能空转 |
| P2-1 | 左侧产线树用 `/lines/summary`（租户级）而非 ACL 过滤后的工位集 | **低** | 展示口径不一致 |

## 3. 根因分析

### 3.1 架构层：三缺一

```
现状（两层）:
  [RBAC 权限点]  →  你能不能调用这个接口（station:read / element:read / group:read…）
  [租户隔离]     →  你能不能看到别的公司的数据（AsyncLocalStorage + BaseRepository 强制 tenant_id）

缺失（第三层）:
  [个人数据范围] →  你能不能看到【本租户内】别人名下的工位/产线
                   （owner_user_id / t_station_collaborator / t_line_share）
```

v3.42 建立的 ACL 逻辑是**完整且正确的**（`stations.service.ts` 的 `filterVisible` / `assertWritable`），
但**只接到了 4 个端点**，而且恰好全是写端点：

| 已接 ACL 的端点 | 位置 |
|---|---|
| `POST /stations/:id/elements/submit` | `elements.controller.ts:32` |
| `POST /stations/:id/elements/import` | `elements.controller.ts:39` |
| `POST /stations/:id/retest` | `stations.controller.ts:134` |
| `DELETE /stations/:id/retest` | `stations.controller.ts:143` |
| `PATCH /stations/:id` | `stations.service.ts:335` |
| `DELETE /stations/:id` | `stations.service.ts:570` |

**所有 GET 端点（读路径）无一例外全部绕过 ACL**，因为 `stations.service.ts` 的 `get()` 方法
（`stations.controller.ts:90` 调用）只做 `repo.findOne({station_id})` + 租户过滤，不做归属判定。

### 3.2 权限设计层：`group:read` 被无条件开放

`app/api/scripts/seed.ts:32-42`：

```ts
// v3.42 决策 #1：综合看板全角色可见（原「集团看板」改名并开放给普通用户）
ie_engineer: [..., 'group:read'],
line_leader: [..., 'group:read'],
viewer:     [..., 'group:read'],
```

这个决策只做了**"跨租户收口"**（`dashboard.controller.ts:21` 的 `crossTenant()` 让非管理员锁本租户），
但**没有做"本租户内的个人收口"**。于是：

- `ie1` 登录 → `App.tsx:152` 落地页判断 `canGroup` 为真 → 直接跳 `#/dashboard`
- 左侧 `GroupTree` 渲染 `dashDim` → 展示全租户 3 家公司、3 条产线、25 个工位的聚合指标
- 点击任一产线 → `openLine()` → 跳 `#/stations` → `StationListPage` 展示该产线工位

**这是一个"权限点开着 + 租户收口 + 个人不收口"的三段式漏斗，第三段是空的。**

### 3.3 前端层：两棵树数据源不一致

用户看到的"左侧边"有两棵树，数据源不同：

| 树 | 组件 | 数据源 | 是否受 ACL |
|---|---|---|---|
| 集团视图树 | `GroupTree.tsx` | `/dashboard/summary`（`dashDim`） | ❌ 全租户 |
| 对象浏览树 | `StationTree.tsx` | 产线来自 `/lines/summary`（**租户级，未过滤**）；工位来自 `/stations`（✅ ACL 过滤） | ⚠️ 半过滤 |

`StationTree.tsx:154` 的 `lineStations = grouped.get(line.line_id) ?? []` 中 `grouped` 来自已过滤的
`stations`，所以树里的**工位叶子**是对的（ie1 只看到 1 个）；
但**产线行的平衡率/VA%/待办数**来自未过滤的 `/lines/summary`，属于他人数据。

而 `StationListPage.tsx:58-62` 的 `scopeStations` 在 `scope='mine'` 时只留 `owner_user_id === myId`，
ie1 名下 0 工位 → 产线总览页对 ie1 呈现"空态 + 跨公司下钻提示"，
**但左树和集团视图已提前把别人的产线结构与指标全部泄露**。这就是用户描述的"还能看到集团视图下各个工厂、产线、工位的分析结果"。

### 3.4 功能空转：`data_scope` 建了不用

`users.service.ts:128/174/371` 完整支持 `data_scope`（`own`/`line`/`tenant`/`all`）的读写，
前端 `UserManagementPage.tsx:263` 也展示了该字段和标签字典（`DATA_SCOPE_LABEL`），
**但后端 17 个 controller 中没有任何一处读取它做过滤**（grep `data_scope` 仅命中 entity + users.service）。

即：管理员在用户管理页把某人设为"仅本人"，系统实际行为**完全不变**。
这说明平台**原本设计了三层模型，只落地了两层**，`data_scope` 是设计意图的残留物。

## 4. 权限配置合理性判定

用户提出的目标模型：「除管理员和特定授权外，只能看到自己相关的、建立的、别人共享给他的产线或工位」。

| 维度 | 当前实现 | 目标 | 是否合理 |
|---|---|---|---|
| 跨公司隔离 | ✅ 有效（404/租户内收敛） | 不看别家 | 合理 |
| 管理员全权 | ✅ 有效 | 能看全部 | 合理 |
| 同租户跨用户隔离 | ❌ **完全缺失** | 只能看自己的/共享的 | **不合理** |
| RBAC 粒度 | ⚠️ 权限点粒度过粗（`station:read` 一放行全放行） | 权限点 + 数据范围双控 | **不合理** |
| `group:read` 开放面 | ❌ 全 5 角色 | 管理员 + 显式授权 | **不合理** |
| `data_scope` | ❌ 空转 | 实际生效 | **不合理** |

**总体判定：不合理。** 且不是"配置松了一点"，而是**少了一整层模型**——
`stations.service.ts` 里现成的 `filterVisible` / `assertWritable` 逻辑完全可复用，
只是没有接到读路径上。

## 5. 修复建议（按优先级）

### P0-1　读路径补 ACL（核心）

新增一个统一守卫，例如 `StationAccessGuard` 或在 `StationsService` 加 `assertReadable(stationId, user)`：

```ts
/** 读权限：owner / 协作者 / 产线级授权 / 全权角色 */
async assertReadable(stationId: string, userId: string, roles: string[]) {
  const s = await this.get(stationId);
  if (this.hasFullAccess(roles)) return s;
  if (s.owner_user_id === userId) return s;
  const visible = await this.filterVisible([s], userId, roles);
  if (visible.length === 0) throw new ForbiddenException(`工位 ${stationId} 不在你的可见范围`);
  return s;
}
```

需接入的端点（按暴露面排序）：

| 端点 | 建议 |
|---|---|
| `GET /stations/:id` | 接 `assertReadable` |
| `GET /stations/:id/elements` | 接 `assertReadable` |
| `GET /stations/:id/elements/export` | 接 `assertReadable` |
| `GET /stations/:id/analysis` | 接 `assertReadable` |
| `GET /stations/:id/versions` | 接 `assertReadable` |
| `GET /stations/:id/collaborators` | 接 `assertReadable` |
| `GET /stations/:id/compare` | 接 `assertReadable` |
| `GET /lines/:lineId/analysis` | 过滤到可见工位后聚合 |
| `GET /lines/summary` | 按 ACL 过滤工位后聚合 |
| `GET /dashboard/summary` | 按 ACL 过滤工位后聚合 |
| `GET /dashboard/improvements` | 同上 |
| `GET /improvements` | 同上 |

### P0-2　收窄 `group:read`

- 从 `ie_engineer` / `line_leader` / `viewer` 的 seed 权限中**移除** `group:read`
- 改为在 `t_role_permission` 里显式授予（管理员可在用户管理页按需给某角色加开）
- 前端 `App.tsx` 的落地页分流保留：无 `group:read` → 落 `#/stations`（已有逻辑）

### P1-1　改善任务流转补归属校验

`suggestions.controller.ts` 的 `PATCH /improvements/:impId/status`、`GET /:impId/report`，
以及 `POST /stations/:id/suggestions/generate` / `adopt`，需按 `imp.station_id` / `:id` 反查工位后走 `assertWritable`（生成类可放宽为 `assertReadable` + 写落库时才收紧）。

### P1-3　激活 `data_scope`

把 `t_user.data_scope` 接入过滤层，与角色权限取交集：

| data_scope | 语义 | 生效位置 |
|---|---|---|
| `own` | 仅本人（含共享给我的） | `filterVisible` 收窄 |
| `line` | 本人名下产线全部 | `filterVisible` 放行同 line_id |
| `tenant` | 本租户全部 | 现状（仅管理员可达） |
| `all` | 全集团 | 仅 sys_admin |

### P2-1　前端树数据源对齐

- `StationTree` 的产线指标改用 ACL 过滤后的工位集重算，不再直接吃 `/lines/summary` 的租户级聚合
- 或后端 `/lines/summary` 改为接收 `line_id` 列表参数由前端传入可见集

### 配套回归建议

新增 `app/api/test/test-acl-read-guard.cjs`，覆盖：
1. ie1 访问他人工位要素/分析/导出/版本/协作者 → 全部 403
2. ie1 访问 `/lines/summary`、`/dashboard/summary` → 不含他人产线/工位
3. ie1 流转他人改善任务 → 403
4. ie1 访问他人工位 → 仍可（共享的 L01-ST02）
5. admin / sys_admin → 全部 200（防过度收口）
6. other1（他租户）→ 仍 404（防回退）

# 附录：实施结果（v3.55）

- **实施日期**：2026-10-28
- **依据**：本报告第 5 节修复建议（用户已批准「按照这个建议实施吧」）
- **结果**：P0-1 / P0-2 / P1-1 / P1-2 / P1-3 / P2-1 **全部落地**，并额外收口审计清单外的**视频跨租户泄露面**（见 §B.6）；新增 `test-acl-read-guard.cjs` 56 项断言全通过，全量回归无回退

## A. 核心设计决策：P0-2 由「撤权限点」改为「数据层收口」

原建议是"从 `ie_engineer`/`line_leader`/`viewer` 移除 `group:read`"。**实施时基于实测证据否决了这一条**，改为保留权限点、在数据层收口。理由：

| 证据 | 结论 |
|---|---|
| 实测 `t_role_permission`：`group:read` 已绑定**全部 12 个角色**（含 `quality_auditor` 等自定义角色） | 撤点需连带处理自定义角色与存量授权，改动面大且易漏 |
| `dashboard-contract.js` 原有断言「viewer 访问集团视图 → 403」**在修复前就是失败的**（既存 28/30） | 契约期望本就是"非管理员不该看到集团数据"，但失败的**不是权限点**而是**数据层** |
| `test-v342.cjs` 断言 viewer 顶栏含「综合看板」 | "看板全角色开放"是 v3.42 已落地的**产品决策**（决策#1），撤点会同时推翻产品决策并破坏 UI 断言 |
| 权限点=接口准入，数据范围=行级可见性，是**两层正交**的事 | 正确修法是补第三层，而非削第二层 |

**落地口径**：保留 `group:read`（能进看板），但**看板/产线总览只统计调用者可见工位**，平衡率、VA%、瓶颈清单、任务数全部基于可见集重算。
同步修正 `dashboard-contract.js` 的两条断言：403 → 验证「数据不外泄」（工位数/产线/公司均不超出管理员集合）。

### B.3 对象级写守卫（P1-1 / P1-2，含本轮补漏）

审计首版遗漏了「路径参数不是 station_id」的端点——这类端点无法直接套 `assertWritable`，必须先反查归属。本轮补齐：

### B.6 审计外新增：视频归属收口（跨租户泄露面）

收尾复核时发现**比工位分析数据更直接的泄露面**：工位视频原为「上传即入全局目录、文件名 = uuid」的**裸文件池**，`GET /videos/file/:name` 只校验 `station:read` 权限点 → **任何登录用户凭文件名即可下载任意租户的视频**（含其他产线现场画面）。该问题不在原审计清单内，但属同一诉求，已一并收口。

| 层 | 改动 |

### B.7 回归测试

新增 `app/api/test/test-acl-read-guard.cjs`（**56 项全通过**），双向防线：

- **越权防线 R1–R10**：读他人工位主数据/要素/分析/版本/协作者/对比/AI建议/浪费清单 → 403；读他人产线分析 → 404；改判他人 VA → 403；提交他人要素 → 403；改他人改善任务状态 → 403（并断言状态确实未被改动）；看板/产线总览/改善清单不含他人数据
- **过度收口防线 O1–O5**（本次修复最大的回归风险，防止"修完把合法用户也锁死"）：工位级共享后全部敏感读端点放行；viewer 协作者可读不可写；整线共享后可见该线全部工位；`data_scope=tenant` 可见本租户全部工位；管理员仍全量可见
- **视频收口防线 V1–V2**：上传者/管理员/关联工位可见者可播；无关用户/他租户 403；撤销协作者后立即失效

**关键设计**：断言区分「403（被权限层挡住 = 收口过头）」与「503（AI 服务未启用）/409（业务前置不满足）= 与权限无关」——避免把服务关停误判为守卫通过。

## F. 遗留与建议

- **`data_scope` 现已生效但默认值均为 `own`**：所有既有用户需管理员在用户管理页显式授权才能看到更多。`tenant` 档已实测可用（O5）。
- **他租户用户默认看不到本租户任何工位**（`other1` 的 1 个工位是它自己拥有的）——符合预期，需共享才会可见。
- **`group:read` 权限点保留**：若后续产品决定"非管理员不该进看板"，仍可撤——届时只需前端 `canGroup` 分流与本报告 §A 的口径二选一。
- **`t_station.owner_user_id` 存量数据集中在 `u_admin`**（DEFAULT 租户 18 个工位）——建议按实际归属批量调整，否则所有工程师的可见范围都为空。
- **历史视频文件无归属登记**：迁移前上传的视频走"无登记即放行"分支。若需彻底收口，可对存量文件按 `t_element.video_id` 反查工位后补登记——需先确认这些文件的真实归属。
- **`resolveVisibleStationIds` 的 `data_scope=line` 分支未带租户约束**：`t_line_share` → 产线工位反查时未限定 `tenant_id`。当前数据无跨租户同名产线，暂不触发；若未来出现同名产线需补约束。
- **测试夹具残留**：AI 契约套件（`ai-suggest-contract` 等）产生的工位未完全自清理，会残留于 `t_station`（当前 18 个工位中 13 个为测试夹具）。部分为 UI 回归前置（如 `L01-ST11`），不可随意清理。属既有测试卫生问题，非本次改动引入。
