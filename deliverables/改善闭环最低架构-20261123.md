# 改善闭环最低架构（需求 → 差距 → 目标链路）

> 日期：2026-11-23
> 性质：架构设计，未改代码。本文改写上一版「Opportunity 统一契约」：把**改善闭环**从“一条建议产线”提升为产品主干。
> 用户给定的最低要求：AI/手工分解不得混在一起比较与分析；每个要素做 VA/RNVA/NVA 判定并识别浪费；对浪费做 5W1H；按 ECRS + 动作经济原则产出措施清单与潜在节省秒数；人工审核采纳/拒绝（拒绝给理由并汇总反哺 AI）；采纳项进入闭环措施清单；实施完成后回填实际改善秒数，跟踪实际效果。

---

## 0. 一句话结论

**当前系统能算 VA/浪费，也能生成建议、采纳成任务，但缺少「分析依据 → 问题 → 措施 → 决策 → 实际效果」的同一主键链路；AI 与手工两条分解线在下游默认混合，且没有 5W1H、动作经济原则、拒绝原因结构化、实际节省秒数。** 这四点必须补齐，才算满足最低要求。

## 2. 目标链路（唯一主干）

```text
Snapshot(tenant, task_id, station_id, bol_version, element_source)
  │
  ├─ 1. VA 判定（每要素）            → VA / RNVA / NVA（规则 + 人工改判留痕）
  ├─ 2. 浪费识别（每条浪费）          → waste_type + evidence + trigger/LLM 溯源
  ├─ 3. 5W1H 问题分析（每条浪费）      → What / Why / Where / When / Who / How
  ├─ 4. 措施生成（每个问题点）         → ECRS + 动作经济原则 + 措施文案 + est_save_s
  ├─ 5. 人工决策                      → 采纳 / 拒绝（结构化原因码 + 说明）
  ├─ 6. 闭环措施清单                  → 采纳项进入实施任务
  ├─ 7. 实施回填                      → 实际措施 / 完成日期 / 实际节省秒数
  └─ 8. 效果验证                      → 复测 ΔCT + 实际 vs 预估 + 拒绝反馈汇总
```

**每一步都必须带同一组溯源键**：`case_id`、`tenant_id`、`task_id`、`station_id`、`bol_version`、`element_source`、`element_ids[]`、`producer`、`rule_versions`、`prompt_version`。

## 3. 来源线隔离（解决“分不清针对哪个”）

### 3.1 产品规则

1. **AI 分解线与手工分解线是两条并行基线，不是前后版本。**
   - 每条线各自独立跑：VA → 浪费 → 5W1H → 措施 → 审核 → 实施 → 效果。
   - 跨线**禁止**做“改善前后对比”；对比只在同一来源线内、改善前后两个版本之间。
2. **删除/停用 `mixed` 作为可执行口径。**
   - `mixed` 仅可用于只读总览；任何措施、任务、审核、导出都必须落到单一 `element_source`。
   - 旧存量 `mixed` 批次标记为 `legacy`，只读，不再新增。
3. **每条措施必须显示“四要素”**：来源线、分解任务、工位版本、涉及要素（seq + element_id）。
4. 若同一工位同任务下两条线都存在，页面提供「切换分析来源」而不是合并列表。

### 3.2 代码落点

| 位置 | 现状 | 必须改 |
|---|---|---|
| `compare.service.ts:497` | 只校验版本存在 | 校验 `v1.element_source === v2.element_source`；跨线 409 并给明确文案 |
| `ComparePage.tsx` / `DiffPage.tsx` | 版本下拉不区分来源线 | 按来源线分组；跨线选择禁用 |
| `analysis.service.ts:31` | 分析当前版本，响应无来源线 | 入参 `source`；响应带 `element_source`，全量 active 要素按来源过滤 |
| `ai-suggest.service.ts` | source 缺省 `mixed` | 缺省改为当前线；`mixed` 仅只读 |
| `ai-waste.service.ts:786` | `items` 合并 AI + 人工条目 | 默认按来源线/来源分组，合并视图仅“总览” |
| `t_improvement` | 无 `element_source`/`bol_version`/`producer` | 增列（见 §5） |

## 4. 5W1H 与改善措施（方法层）

### 4.1 5W1H 的结构化字段

每条浪费/问题点必须产出并持久化：

| 字段 | 含义 | 示例 |
|---|---|---|
| `what` | 问题是什么（哪个动作/现象） | 右手持住壳体 2s，左手等待 |
| `why` | 为什么存在（根因） | 无治具固定，需手扶防位移 |
| `where` | 发生在哪里（工位/区域/工序） | ST010 装配工位，壳体定位区 |
| `when` | 何时发生（循环阶段/频次） | 每循环 1 次，装配前 |
| `who` | 谁执行/影响谁 | 作业员右手；影响左手装配节奏 |
| `how` | 如何发生（机制/条件） | 壳体无自锁，需持续施力 |
| `how_much` | 量化（可选） | 占 CT 的 18%，2.1s |

> 用户口径是 5W1H；`how_much` 作为量化补充，不替代五项。

校验要求：
- `what/why/how` 不能为空且 ≥8 字；
- 每条浪费至少一条 5W1H；
- 问题点必须引用真实 `element_seqs`，且属于同一来源线/版本；
- 5W1H 内容与浪费类型一致性检查（例如「持住」的 why 不得只写“效率低”）。

### 4.2 ECRS + 动作经济原则

- ECRS：沿用 `ecrsa_map` 的 E/C/R/S；VA 禁止 E（现有校验保留）。
- **动作经济原则**新增为规则集 `motion_economy`，每条措施可选 1–3 个编码：

| 编码 | 原则 | 典型措施 |
|---|---|---|
| ME1 | 双手同时开始/结束 | 双手并行取放 |
| ME2 | 对称反向动作 | 对称布局、双手对向装配 |
| ME3 | 连续圆滑曲线 | 弧形滑道、减少折返 |
| ME4 | 利用重力/惯性 | 重力滑槽、自落供料 |
| ME5 | 正常作业范围 | 料架移入前臂 50cm |
| ME6 | 固定位置、消除寻找 | 一穴一件、定置定位 |
| ME7 | 治具/脚动装置替代手持 | 夹具、脚踏开关 |
| ME8 | 节奏化/自动化 | 节拍送料、自动打螺丝 |
| ME9 | 减少视线移动 | 指示化、灯号、目视化 |
| ME10 | 合并/简化动作 | 合并取放、一次多件 |

措施对象必须包含：`ecrs`、`motion_economy[]`、`measure`、`est_save_s`、`difficulty`、`risk_flags`。

### 4.3 数字口径

- `est_save_s`：服务端计算，LLM 只给 factor/方法，不产数字（保留现有铁律）。
- `actual_save_s`：用户回填的实际减少秒数；与 `est_save_s` 并存，计算 `effect_gap = actual - est`、`effect_ratio = actual / est`。
- 效果验证优先用复测 ΔCT；`actual_save_s` 是措施级归因，两者都保留，避免“预估当实际”。

## 5. 数据模型（最小闭环）

### 5.1 推荐：统一 `t_improvement_case`

> **新增表须按 `CLAUDE.md` §1.2 先经用户书面同意，并把白名单 33 → 34。** 未获同意前不得落 DDL。

| 分组 | 字段 |
|---|---|
| 主键/溯源 | `case_id`、`tenant_id`、`task_id`、`station_id`、`line_id`、`bol_version`、`element_source`、`producer`（rule/ai_suggest/ai_waste/manual）、`source_ref`、`rule_versions`、`prompt_version` |
| 依据 | `element_ids`、`element_seqs`、`va_classes`、`waste_type`、`waste_evidence`、`trigger_ids` |
| 5W1H | `what`、`why`、`where_`、`when_`、`who`、`how`、`how_much` |
| 措施 | `ecrs`、`motion_economy`、`measure`、`est_save_s`、`difficulty`、`risk_flags`、`validation_trace` |
| 决策 | `status`（pending/accepted/rejected/ignored）、`reviewed_by`、`reviewed_at`、`reject_code`、`reject_reason` |
| 实施 | `imp_id`、`owner`、`due`、`actual_measure`、`actual_completed_at`、`actual_save_s` |
| 验证 | `verified_by`、`verified_at`、`before_ct`、`after_ct`、`effect_gap`、`effect_ratio` |
| 时间 | `created_at`、`updated_at` |

状态机：
```
pending → accepted → in_progress → completed → verified
pending → rejected（终态，进入反馈汇总）
pending → ignored（终态，重复/无效）
```

### 5.2 备选：不新增表

- 扩展现有 `t_ai_suggestion` / `t_ai_waste_issue` / `t_improvement`：加 5W1H、动作经济、`actual_save_s`、`element_source`、`bol_version` 等列。
- 限制：规则候选没有持久化载体，拒绝记录无法统一；三表状态机需各自维护，闭环查询要 UNION。**能满足字段，但满足不了“统一审核与统一反馈”**。

### 5.3 `t_improvement` 的补充列（无论选哪种方案）

`case_id`、`element_source`、`bol_version`、`producer`、`actual_save_s`、`verified_at`、`verified_by`。

## 7. 前端调整（满足“分得清”）

1. 工位工作区页签增加「改善闭环」；分析结果、浪费识别、AI 建议都提供「进入改善闭环」入口。
2. 所有列表固定显示：`来源线 | 任务号 | 版本 | 要素 seq`；按来源线分组，默认单线。
3. Case 详情页按链路展示：
   `要素 → VA 判定 → 浪费证据 → 5W1H → ECRS/动作经济 → 措施与预估 → 审核 → 实施 → 实际节省`。
4. 审核弹窗：采纳 / 拒绝；拒绝必须选原因码（证据不足/不可行/成本高/影响品质/违反工艺安全/已有措施/收益不实/其他）+ 说明。
5. 效果页：预估 vs 实际、差值、达成率；未复测时标记“待验证”。
6. 对比页：来源线选择器；跨线选项禁用，并显示原因。

## 8. 反馈闭环（拒绝理由 → 提升 AI）

1. **结构化原因码**（R1–R8）替代自由文本关键词切分。
2. 汇总维度：`tenant × waste_type × ecrs × element_type × reason_code`。
3. 反哺方式：
   - 提示词负样本：按 waste_type 分组，带时间衰减与条数上限；
   - 规则阈值校准：当某类措施反复因“收益不实”被拒，回看 `factor`/`est_save_s`；
   - 生成前置规则：高频拒绝模式直接进入校验器（例如“无依据的取消检验”）。
4. 保留留出集与漂移监控：不是所有拒绝都注入提示词；按周观察采纳率/拒绝率变化（与 deep research 的偏差护栏结论一致）。

## 9. 实际效果跟踪

- 措施完成时用户必须填 `actual_save_s`（或选择“待验证”）。
- 复测后系统计算 `ΔCT`，与措施级 `actual_save_s` 汇总对比：
  - `effect_gap = actual_save_s - est_save_s`
  - `effect_ratio = actual_save_s / est_save_s`
  - `station_delta_ct` vs `sum(actual_save_s)` 差异提示（措施间重叠/协同）。
- 驾驶舱/改善任务页展示：预估总节省、实际总节省、达成率、未验证数。

## 11. 验收标准（最低）

1. 任取一条措施，能在一个页面看到：来源线、任务、版本、要素 seq、VA 判定、浪费证据、5W1H、ECRS/动作经济、预估秒数、审核人、拒绝理由（如有）、实施状态、实际秒数。
2. AI 线与手工线的分析/措施/任务列表默认不混合；跨线对比被系统拒绝并给出原因。
3. 每条浪费都有 5W1H；缺字段不能进入审核。
4. 每条措施至少一个 ECRS；至少一个动作经济原则（或显式“无适用原则”）。
5. 拒绝必须带原因码；汇总页可按 waste_type/ECRS/原因码查看。
6. 完成措施必须回填实际节省秒数（或标记待验证）；效果页能对比预估与实际。
